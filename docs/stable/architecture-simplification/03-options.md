# 架構方案比較與推薦

本文回答：要達成「簡化、內聚」有哪些整體做法，各自的代價，以及推薦哪一個。

## 整體方向

| 選項 | 內容 | 優點 | 缺點與風險 | 結論 |
|---|---|---|---|---|
| A. 維持模組數，責任歸位 | 6 個模組不變；資源型別知識集中到 accessors、engine 內部改為功能切片並禁止循環、core 只留契約、analyzer 共用 core 的模型 | 每步小、可獨立回退；不改建置拓撲與部署產物；直接處理 [02](02-current-state.md) 的四個發現 | 套件邊界只靠自動檢查維持，不如模組邊界由編譯器強制 | **推薦** |
| B. 併模組減少數量 | 例如 core 併入 runner、accessors 併入 engine | 模組數變少 | core 併入 runner 會把執行器帶進撰寫者的編譯路徑並擴大受信任面；accessors 併入 engine 使 devkit 無法使用資源實作（devkit 不得依賴 engine）。模組數少不等於複雜度低 | 否決 |
| C. 拆 engine 為多個 Gradle 模組 | 例如 engine-api、engine-runs、engine-resources | 功能邊界由編譯器強制 | 建置與打包變複雜、大量內部型別被迫公開；engine 約 1.4 萬行，單一模組仍可管理；與「簡化」目標相反 | 暫不採用；engine 主程式超過約 2.5 萬行或多人並行開發時再評估 |

推薦 A：複雜度的主要來源不是模組數量，而是責任分散與依賴方向混亂。A 用最少的結構變動處理根因，並以自動檢查取得 C 的大部分好處。

## 資源型別的歸屬

| 選項 | 內容 | 結論 |
|---|---|---|
| R1. accessors 擁有型別全部知識 | 每個型別在 accessors 內提供一份完整的型別定義：設定驗證、正規化、對外描述、檢查、實體與存取端建立、可觀測事件；engine 與 devkit 只透過與型別無關的介面使用 | **推薦**（[ADR-022](adr/ADR-022-resource-type-ownership.md)） |
| R2. engine 擁有型別知識 | devkit 不得依賴 engine，只能另寫一份 | 否決 |
| R3. 每型別一個 Gradle 模組 | 模組數翻倍，與簡化目標相反；型別集合封閉，不需要外掛級的隔離 | 否決 |

金鑰庫與 OpenTelemetry 仍屬 engine：accessors 只表達「需要某別名的機密」與「發生了某可觀測事件」，由 engine 提供機密與轉成 metric、trace。devkit 以本機組態提供同樣的兩者。

## Engine 內部組織

| 選項 | 內容 | 結論 |
|---|---|---|
| E1. 功能切片 + 單向依賴 + 自動檢查 | 每個功能套件擁有路由、組態段、服務、儲存、可觀測；共用層不依賴功能；功能之間依固定方向依賴；建置檢查違規 | **推薦**（[ADR-023](adr/ADR-023-engine-feature-slices.md)） |
| E2. 依技術分層（routes／services／stores） | 一個功能散在三層，與內聚目標相反 | 否決 |
| E3. 只消除循環，不搬路由與組態 | 成本低，但功能仍分散在根套件、組態與組裝 | 否決：只解決一半 |

## core 與 analyzer

| 選項 | 內容 | 結論 |
|---|---|---|
| K1. core 只留撰寫契約，執行期實作移到 runner 的 run 側 | 縮小受信任面，core 一眼可讀完 | **推薦**（[ADR-024](adr/ADR-024-core-contract-only.md)） |
| K2. 維持現況 | 無成本，但受信任面過大的問題持續 | 否決 |
| M1. analyzer 主程式依賴 core 的 metadata 模型 | 模型一份；位元組讀取仍只在 analyzer；core 只依賴 JDK 與標準函式庫，不破壞 analyzer 的純函式性 | **推薦**（[ADR-025](adr/ADR-025-analyzer-shares-core-metadata.md)） |
| M2. 抽出新的共用模型模組 | 多一個模組，只為了放一組資料型別 | 否決 |
| M3. 維持兩份模型與對照測試 | 每加一個欄位改兩處 | 否決 |

## 模組名稱

accessors 在 R1 之後擁有「資源型別」而非只有「存取端」，名稱略失準。決定**不改名**（[01](01-requirements.md)「決定」）：改名不帶來行為或結構上的簡化，卻牽動建置、套件名稱與所有匯入；以 stable 文件的模組責任表說明即可。
