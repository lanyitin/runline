# ADR-018 存活與就緒探測端點

狀態：已核可（2026-10-05）。補充 [ADR-012](ADR-012-api-authentication.md)（免認證端點清單新增兩項）；調整 [08-api](../08-api.md)「關閉中」的 503 規則（探測端點為例外）。回答：部署平台（Docker 與 systemd）如何判斷 Engine「還活著」與「可以接流量」，端點的認證、檢查內容、回應、與優雅關閉及重啟政策的關係。

## 背景

- Engine 是單一 JVM 加 PostgreSQL（[04](../04-deployment.md)）。部署平台負責重啟（[07](../07-nfr-risks.md) 把 pipeline 結束 JVM 的風險交給平台自動重啟），但原本沒有專供平台使用的探測端點。
- Engine 啟動時檢查 schema 是否為最新、run 執行期目錄是否完整，不通過即拒絕啟動；啟動後把進行中的 run 標記為中斷並處理待處理的觸發。
- 收到終止訊號後，Engine 對新請求回 503 `shutting_down` 並關閉連線，進行中的請求在寬限時間內完成（08-api「關閉中」）。
- 平台無法持有 Bearer token（token 由組態提供，ADR-012），探測必須免認證。
- [ADR-016](ADR-016-engine-build-info-endpoint.md) 的 `/info` 是給人與 Console 看的版本資訊，不檢查任何依賴。

## 選項

| 選項 | 說明 | 結論 |
|---|---|---|
| A. 不新增，平台用 `/info` 或任一既有 API 探測 | 零成本 | 否決：`/info` 不檢查依賴，無法表達就緒；既有 API 需認證；且關閉中的 503 會被誤判為故障 |
| B. 單一 health 端點，同時檢查資料庫與目錄 | 簡單 | 否決：資料庫短暫中斷會讓平台重啟 Engine，重啟既不能修好資料庫，還會中斷所有進行中的 run（重啟時 run 一律標為中斷），造成重啟風暴 |
| C. 存活與就緒分開兩個端點 | 重啟與流量控制各自判斷 | 採用 |
| D. 探測需認證 | 不暴露任何資訊 | 否決：平台無法持有 token；token 會進入平台組態；回應本身不含機密 |

## 決策

**端點與認證**

- `GET /api/v1/health/live`：存活探測，免認證。
- `GET /api/v1/health/ready`：就緒探測，免認證。
- 兩者只接受 GET，回應不快取，不含版本、組態、主機名稱、連線字串或例外原因。路徑放在 `/api/v1` 之下，使既有的路由列舉測試、「`/api` 下不存在的路徑回 404」與 Console 的 fallback 規則（[ADR-015](ADR-015-console-frontend.md)）都不需特例。
- 兩個端點加入 ADR-012 的免認證清單；「新增端點預設需要認證」的原則不變。

**存活（live）**

- 語意：Engine 的行程能接受並回應 HTTP 請求。失敗代表重啟有機會修好。
- 不檢查任何外部依賴（資料庫、目錄、run 的狀態），不依賴 run 執行緒或資料庫連線；資料庫故障不得讓它失敗。
- 回應：200，本文 `{"status": "up"}`。
- 優雅關閉期間仍回 200（見下），避免平台在寬限時間內因存活失敗而提前強制終止。
- 無法回應（逾時、連線被拒）即為失敗，不需要失敗本文。

**就緒（ready）**

- 語意：Engine 現在可以正常服務請求。失敗代表平台應暫停導流，不應重啟。
- 全部通過才為就緒。檢查項目與名稱（固定、穩定）：

| 檢查 | 通過條件 |
|---|---|
| `startup` | 啟動階段已完成：遷移已確認為最新、run 執行期目錄檢查通過、「進行中的 run 標記為中斷」與待處理觸發的啟動處理已完成、排程器已啟動 |
| `database` | PostgreSQL 在短逾時內可連線並完成一次輕量查詢 |
| `runtime` | run 執行期目錄仍存在且必要的部分齊全（只檢查存在，不重做啟動時的完整類別掃描；用於發現磁碟區被卸載或誤刪）|
| `shutdown` | Engine 未處於關閉流程中 |

- 回應：全部通過回 200 `{"status": "ready"}`；任何一項失敗回 503，本文 `{"status": "not_ready", "checks": {"startup": "ok", "database": "failed", ...}}`，每項只有 `ok` 或 `failed`（`startup` 可為 `pending`），不含原因細節；原因寫在 log 與 metric。關閉流程中 `shutdown` 為 `failed`，且 `status` 為 `shutting_down`（已確認），使平台與人都看得出是正常關閉。
- 資料庫檢查的成本受控：結果可短暫快取（秒級），逾時小於平台探測逾時，並發探測不會放大成對資料庫的壓力；探測不佔用 run 使用的資源，也不計入 run 並行額度。
- 就緒只影響導流，不影響 Engine 行為：就緒為否時，進行中的 run 與排程不被停止；Engine 仍接受請求並回應（資料庫故障時多數 API 本來就會失敗）。

**與優雅關閉及 `shutting_down` 的關係**

- 收到終止訊號的當下，就緒立即轉為失敗（先於寬限時間開始），讓平台先停止導流，再進入進行中請求的完成階段。
- 兩個探測端點是 08-api「關閉中」503 規則的例外：關閉期間 `live` 仍回 200，`ready` 回 503 且 `status` 為 `shutting_down`（與 08-api 既有的錯誤代碼同名）；不關閉連線的要求不適用於這兩個端點，其餘請求維持現行規則。
- 寬限時間結束或行程結束後，端點自然無法連線，平台視為已終止。

**與部署平台的關係（平台中立的原則）**

部署目標同時支援 Docker 與 systemd。探測語意不依賴任何平台，平台各自把它對應到自己的機制：

- 存活失敗才可成為「重啟」的依據；就緒只用於導流、等待啟動完成與相依順序，不觸發重啟。
- 啟動期間以就緒等待 `startup` 完成，並給較寬的失敗容忍；啟動失敗（遷移未完成、目錄不符）由 Engine 自己結束行程，由平台依重啟政策處理（04 既有）。
- Engine 單實例（v1）：就緒為否時沒有其他實例可接流量，等同服務暫停；這是預期行為，比對失敗的 API 持續回 500 更明確。多實例時語意不變，探測不需修改。
- 速率限制由部署層負責（與 webhook、`/info` 相同）。
- 兩個平台共同的前提：終止訊號必須送達 JVM（行程本身接收訊號，不經由不轉送訊號的殼層包裝），且 JVM 因終止訊號結束時的結束代碼不被平台視為失敗而觸發重啟（見下）。

**Docker 的對應**

- 平台行為：Docker 的重啟政策只在行程結束時重啟容器；容器被標為不健康（unhealthy）時，單機 Docker（含 Compose）不會重啟它，健康狀態只用於顯示、`depends_on` 的等待與外部編排器。因此單機 Docker 的重啟只來自「Engine 行程結束」（包含 pipeline 結束 JVM，07 既有風險）。使用者已接受：單機 Docker 不因行程卡死而重啟，以監控告警補位。Swarm 或其他會依健康狀態重啟的編排器則不同，見下方規則。
- 健康檢查：單機 Docker／Compose 對應到就緒（`/api/v1/health/ready`），用途是顯示與 `depends_on` 等待，不會造成重啟，所以資料庫短暫中斷只會顯示 unhealthy。若部署在會依 unhealthy 重啟的編排器，健康檢查改指向存活，否則資料庫短暫中斷會造成重啟風暴。Docker 每個容器只有一個健康檢查，需依平台二選一。
- 啟動期間的等待：對應到健康檢查的啟動寬限（`start_period`，期間的失敗不計入重試次數）；若 Docker 版本支援，另設啟動期間較短的探測間隔（`start_interval`）使就緒盡快被偵測到。
- 重啟政策：建議「除非手動停止否則重啟」類型（`unless-stopped`），使 JVM 被結束或崩潰後自動回來；手動停止的容器不被重啟。
- 健康檢查的執行需要容器內有能發出 HTTP 請求的工具；JDK 基底映像不一定附帶，提供方式見「部署檔案與需評估的事項」。
- 遷移是獨立的一次性步驟（04）：Compose 以相依於「遷移容器成功完成」表達，Engine 容器在其後啟動。
- 訊號與關閉：容器的主行程必須是 JVM 本身（或由容器內的最小 init 轉送訊號），不使用不轉送訊號的殼層；否則停止時 Docker 在逾時後以強制終止收場，優雅關閉不會發生。

**systemd 的對應**

- 服務類型與重啟：使用一般的前景行程型態；`Restart` 設為失敗時重啟（行程非正常結束才重啟），搭配重啟間隔與啟動頻率上限，避免無限快速重啟。JVM 對終止訊號的結束代碼為 143，被 systemd 視為失敗；若 Engine 優雅關閉後的結束代碼不是 0，須把 143 列為成功的結束代碼，否則正常的 `systemctl stop` 後單元被標為 failed。
- 就緒檢查：systemd 的 `Type=simple` 與 `exec` 不等待應用就緒。需要「就緒後才算啟動完成」（例如讓相依單元等待）時，可在啟動後的步驟（`ExecStartPost`）輪詢就緒端點並設有總逾時，逾時則使單元失敗；也可由外部的檢查單元或維運腳本呼叫就緒端點。腳本內容不在本 ADR 範圍。
- `sd_notify` 與 `Type=notify`：不採用。JVM 沒有內建的 sd_notify 支援，需額外的原生程式庫或輔助程序，且 Engine 已有 HTTP 就緒探測，行為重複；`Type=notify` 與 watchdog 都需要 Engine 主動通知，v1 不引入。
- `WatchdogSec`：不採用，原因同上（需要應用程式主動送出心跳，JVM 需 sd_notify 支援）。以外部的存活檢查取代：由 systemd 計時器定期呼叫存活端點，連續失敗達閾值才重啟主單元。這是選用的；沒有它時，systemd 的重啟只來自「行程結束」，與單機 Docker 相同。
- 遷移是獨立的一次性步驟：以相依且先於 Engine 的一次性單元，或 Engine 啟動前的步驟表達，失敗則 Engine 不啟動。
- 組態與密鑰：以環境檔（權限限制為服務帳號可讀）提供環境變數，不寫在單元檔中（12-Factor）；共享目錄與 run 私有目錄使用單元管理的持久與暫存目錄。

**建議的閾值**

| 項目 | Docker | systemd |
|---|---|---|
| 探測對象 | 單機：就緒；依 unhealthy 重啟的編排器：存活 | 外部存活檢查（選用）；啟動等待使用就緒 |
| 探測間隔 | 10 秒 | 15 秒（計時器） |
| 單次逾時 | 3 秒 | 3 秒 |
| 連續失敗次數 | 3 次 | 3 次後重啟主單元 |
| 啟動寬限 | 60 秒（`start_period`）；啟動期間探測間隔 2 秒 | 就緒等待總逾時 60 秒 |
| 重啟政策 | `unless-stopped` | 失敗時重啟，間隔 5 秒；300 秒內最多啟動 5 次 |
| 停止等待 | Engine 寬限時間加 15 秒（預設 45 秒）| 同左（預設 45 秒）|

啟動寬限 60 秒涵蓋 JVM 啟動、遷移確認、中斷標記與觸發處理；數值待實測校正。就緒與資料庫檢查的服務端逾時須小於單次逾時（3 秒）。

**優雅關閉寬限與平台停止等待**

- Engine 的寬限時間（`RUNLINE_SHUTDOWN_GRACE_SECONDS`，預設 30 秒，指進行中請求完成的時間）之外，關閉還包含：將進行中的 run 標記為中斷、釋放資料庫連線、行程結束。
- 平台的停止等待（Docker 的 `stop_grace_period`，預設 10 秒；systemd 的 `TimeoutStopSec`，預設 90 秒）必須大於 Engine 的寬限時間加關閉收尾時間，否則平台在 Engine 完成前強制終止（Docker 預設 10 秒小於 Engine 預設的 30 秒，不調整就會中斷優雅關閉）。建議：停止等待 = Engine 寬限時間 + 15 秒。
- 調高 `RUNLINE_SHUTDOWN_GRACE_SECONDS` 時，平台的停止等待須同步調高；此關係寫入 04 的組態說明。就緒在收到訊號的當下失敗，所以停止等待期間不會再有新的導流。

**與 ADR-016 `/info` 的關係**

- `/info` 回答「這是哪個版本」，`/health/*` 回答「現在能不能用」，兩者互不取代。探測回應不含版本與 commit hash；`/info` 不檢查依賴，不得被平台用作探測。
- Console 的連線狀態點仍由「最近一次 API 呼叫是否成功」判斷（ADR-016），不呼叫探測端點。

**部署檔案的位置與文件**

- Dockerfile、Compose 檔與 systemd 單元檔納入版本庫，放在專案根目錄的 `deploy/` 目錄，與應用程式碼模組分開；其下依平台分子目錄（Docker、systemd）。
- 兩個平台的設定項目、建議值與組態檔用途，寫在 [04-deployment-docker.md](../04-deployment-docker.md) 與 [04-deployment-systemd.md](../04-deployment-systemd.md)；`deploy/` 內的檔案是這兩份文件的實例。

## 取捨

| 項目 | 優點 | 缺點 |
|---|---|---|
| 存活與就緒分離 | 資料庫故障不會引發重啟風暴，也不會中斷進行中的 run | 多兩個端點與兩份語意要維護 |
| 存活不檢查依賴 | 只在行程真的無法回應時才重啟 | 行程「活著但卡住在別處」（例如所有 run 執行緒被占用而 HTTP 仍可回應）不會被偵測到；由 run 並行上限與 metric 觀察 |
| 公開探測且回應含各檢查的 ok／failed | 排查迅速 | 對外洩漏「資料庫不可用」這類狀態；內部工具且由入口層控管暴露，接受 |
| 就緒立即在關閉訊號時失敗 | 平台先停止導流再等待請求完成 | 探測在關閉期間不遵守「新請求一律 503 並關閉連線」的通則，需明文例外 |
| 單機 Docker 不因卡死而重啟 | 避免誤判造成的重啟與中斷 | 行程卡死需人工或監控告警介入（已接受）|

## 後果

- 08-api 的「關閉中」段落註明兩個探測端點的例外；`ApiDocumentationTest` 會要求兩個端點各有「### `GET 路徑`」標題與「認證：無」。
- ADR-012 的免認證清單變為：API 文件與 schema、Webhook 入口、`GET /api/v1/info`（ADR-016）、Console 靜態檔（ADR-015）、兩個探測端點。
- 驗收（行為層級）：端點無 token 可存取；`live` 不因資料庫停止而失敗；`ready` 在資料庫無法連線、run 執行期目錄不完整、啟動未完成與關閉流程中都回 503 且 `checks` 與實況相符；關閉訊號後 `ready` 先轉為 503、`live` 仍為 200；回應不含原因細節與組態值；在打包後的 Engine 行程上驗證關閉期間的行為（沿用 `packagedTest`）。資料庫故障以測試用的真實資料庫容器停止與恢復來製造，不使用替身。
- 新增 metric 為可選：探測失敗計數，按檢查名稱區分。
- 實作見 [WI-29](../work-items/WI-29-health-probes.md)、[WI-38](../work-items/WI-38-deployment-entry-points.md) 與 [WI-39](../work-items/WI-39-deployment-files.md)。

## 部署檔案與需評估的事項

檢查對象：04 的打包形態、`engineDistribution`（`engine.jar` 加 `run-runtime/`，以 `RUNLINE_RUNTIME_DIR` 指向）、單一 Engine 加 PostgreSQL 的拓撲。

結論：產物形態與兩個目標相容，不需改變。兩個平台都只需要 `engine.jar` 與同層的 `run-runtime/` 目錄；Console 在 `engine.jar` 內（[ADR-015](ADR-015-console-frontend.md)），`run-runtime/` 不含它；`packagedTest` 驗證的就是這個形態。

下列事項屬實作層面，由 tdd-coder 評估後回報，經架構決定後定案（[WI-38](../work-items/WI-38-deployment-entry-points.md)）：

| 事項 | 說明 |
|---|---|
| 容器內的健康檢查工具 | 映像若只含 JDK，不保證有 HTTP 用戶端；可選：映像加入輕量的 HTTP 工具，或由 Engine 的打包產物提供自我檢查的命令列入口 |
| 遷移的呼叫方式 | 遷移目前是 Gradle 任務；部署環境沒有 Gradle，須以打包產物執行同一段遷移（行為相同、使用同一組環境變數）|
| 優雅關閉的結束代碼 | JVM 因終止訊號結束的代碼為 143；建議 Engine 完成優雅關閉後以 0 結束，使平台不需特例 |

共享目錄的持久化不是新決策：Docker 需掛載磁碟區，systemd 需持久目錄（ADR-009、04），在兩份平台指南寫明。
