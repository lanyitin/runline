# WI-1476 被取消的 run 要記錄結束狀態

本文回答：被取消或中斷的 run 結束時，如何仍然把結果寫進資料庫。狀態：已完成（2026-10-15），T 的 dd354fb；已核可。相依：WI-1467（已完成）。本項是順帶修正的缺陷，不依賴 [ADR-069](../adr/ADR-069-accept-what-can-be-used.md) 的決策。儲存庫：T。

## 背景

取消一個進行中的 run（Engine 的取消）時，log 出現：資料庫的更新失敗（CANCELLED），以及「end of run not recorded」。結果是 `run` 表的 `result`、`result_note`、`finished_at`、`degraded` 都是 NULL，`runs` view 看到一個沒有結果的 run。續跑的驗證會拒絕「沒有記錄結束」的 run，所以這種 run 不能當續跑來源。另外，取消要等進行中的模型呼叫結束才生效（實機約 1 分鐘）。

## 行為與驗收條件

1. **取消或中斷的 run 記錄結束**：run 以 `stopped`（取消、逾時、Engine 重啟中斷）結束時，`result`、`result_note`（取消的原因）、`finished_at`、`degraded`（各階段降級數加總）照常寫入，與其他結束狀態一致。
2. **寫入不受中斷影響**：結束紀錄在取消的中斷之後仍然能寫入；寫入失敗仍然只記錄警告，不改變 run 的結果，也不遮蓋原本的取消。
3. **階段列**：被取消時正在進行的階段，其階段列標記為被中止，並保留已累計的計數。
4. **續跑**：被取消或中斷且已記錄結束的 run 可當續跑來源（WI-1467 條件 2 的「中斷」）；已經是「沒有記錄結束」的舊 run 維持被拒絕，訊息不變。
5. **取消的反應**：取消送達後，進行中的模型呼叫盡快中止（連線關閉），不等到該次呼叫自然結束；若現行的取消已經如此，只需確認並回報實測的反應時間。
6. **重現情境**：用真實的 devkit 與真實資料庫，在階段執行中送出取消；斷言 run 列有結果、完成時間與降級數；斷言該 run 能被當作來源續跑；斷言取消的反應時間在合理範圍（由測試定義，不依賴模型的回應時間）。
7. 其餘行為不變。

## 架構約束

- 不改 Engine；不新增參數；不改 schema。
- 嚴格 TDD；測試不使用 Stub 或 Mock。
- 測試範圍依 tdd-coder 定義的 §1.1，不跑全套；涵蓋取消相關測試（`CancelledRunTest`、`StageRunnerTest`、`StageInterruptionTest`）、store、resume、views。
- 回報時列出測試範圍與結果、jar 路徑與 sha256、提交。
