# WI-21 靜態分析的 IO 敏感成員判定

本文回答：靜態分析如何在成員層級判定 IO 敏感成員，使預設白名單不會使 context 的限制被繞過。狀態：已核可（2026-10-05）。相依：WI-05、WI-16、WI-19。

## 背景

[ADR-013](../adr/ADR-013-io-sensitive-members.md) 決定：參照 IO 敏感成員在成員層級判為 unsafe，不受套件白名單豁免。analyzer 目前只對 JVM 結束成員（[ADR-011](../adr/ADR-011-jvm-exit-calls.md)）做成員層級比對。

## 行為與驗收條件

- 被分析的程式碼（含展開到的第三方函式庫類別）參照 ADR-013 所列的 IO 敏感成員時，判 unsafe 並註明原因。成員涵蓋三類：啟動外部行程、載入原生程式碼、位於預設受信任基礎套件內且可直接開啟檔案或網路的成員。
- 比對在成員層級，不受套件白名單豁免：即使 `java.lang`、`java.util` 或 `kotlin` 在白名單內仍然成立。
- 違規附上從起點到該參照的完整路徑，並以獨立於「JVM 結束」與「白名單外節點」的原因類別呈現。
- 具體成員清單由實作依 JDK 25 評估後回報：逐類列出成員、為何屬於該類、以及考慮過但不納入的成員與理由；經架構決定後定案。清單與其涵蓋限度寫在 analyzer 的說明文件。
- 涵蓋透過方法句柄與 Kotlin 編譯產生的呼叫形式參照這些成員的情況，與 JVM 結束成員的涵蓋方式一致。
- 輸出的限度說明（繁體中文）補充：判定只涵蓋已列出的 IO 敏感成員；反射與動態載入、白名單內類別的內部呼叫不被涵蓋。測試斷言新增的要點出現。
- 既有的判定行為不變：WI-05、ADR-011 的條件與既有的分析測試全部通過，測試數量不減少。
- 既有的消費端同步調整：Engine 的上傳回應與儲存、devkit 的判定顯示都能辨識並呈現新的原因類別；Engine 的 API 回應中原因類別新增一個值，其餘欄位不變；已儲存的舊判定仍可被讀取與顯示，不被自動重判。
- analyzer 的主程式維持只依賴 JDK 與 Kotlin 標準函式庫，不依賴 core 或其他專案模組。
- 建置、全部測試（含打包形態的測試）在 JDK 25 下通過，`ktfmtCheck` 通過。

## 架構約束

- 依 [ADR-013](../adr/ADR-013-io-sensitive-members.md) 與 [ADR-011](../adr/ADR-011-jvm-exit-calls.md)：只做靜態判定，Runner 不加入執行期攔截。
- 不執行 pipeline 邏輯，也不觸發其靜態初始化（[ADR-003](../adr/ADR-003-jar-and-discovery.md)）。
- 修改範圍限於 analyzer，以及為辨識新原因類別所需的 Engine 與 devkit 的最小調整；不改變其他行為。
- 測試使用真實編譯的 jar（Java 與 Kotlin 皆有），每一類成員至少一個測試；成員清單的比對邏輯須做突變驗證（暫時破壞再還原，確認測試會失敗）。
- 不新增外部相依；不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
