# WI-60 Console：先預覽再確認的版本刪除對話框

本文回答：管理員在 Console 刪除版本時看到什麼、如何確認並完成刪除。狀態：已核可（2026-10-13）。相依：[WI-59](WI-59-engine-delete-impact-and-force.md)。

## 行為與驗收條件

- 管理員按下刪除時，對話框先向預覽端點取得影響，再顯示：run 總數與依狀態分布、最早與最晚的時間、log 筆數、仍引用的 trigger 名稱、jar 內容是否一併移除。數字來自預覽端點，不由前端推算。
- 取得影響期間與失敗時：顯示載入中或錯誤，不能確認刪除。
- 不可刪時（有 trigger 或進行中的 run）：對話框說明原因並列出 trigger 或進行中筆數，確認鈕停用，並導向 trigger 頁面（既有連結機制）。
- 可刪時：對話框明確說明 run 與 log 將一併刪除且不可回復；確認鈕送出帶預覽 run 數的刪除；沒有 run 時說明只刪除版本。
- 確認時回 `impact_changed`、`runs_active` 或 `in_use`：對話框以最新資訊重新顯示，不關閉、不刪除。其他錯誤沿用既有的錯誤呈現。
- 成功後沿用既有的刪除後流程（版本頁導離）。
- 防重送：處理中不可重複送出；沿用既有 `ConfirmDialog` 的互動與無障礙行為。
- 文案走既有多語系機制，所有支援的語言都有；伺服器回傳的名稱以不可信內容的顯示機制呈現。
- 移除前端以最新 200 筆 run 推算引用者的邏輯。
- 單元測試在 Fake 後端通過；契約測試在真實打包的 Engine 上通過，涵蓋可刪、有 trigger、有進行中 run、確認時影響改變四種情境。

## 架構約束

- 只用同源 `/api/v1`，不改變 Bearer API 契約。
- Fake 後端的行為須與 [05-ipc](../05-ipc.md) 一致。
- 測試不使用 Stub 或 Mock。
