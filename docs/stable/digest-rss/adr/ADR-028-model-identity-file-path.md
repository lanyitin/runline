# ADR-028 模型身分比對接受以檔案路徑回報的模型

狀態：已核可（2026-10-10）。補充 WI-1007 的模型身分比對規則（[01-requirements.md](../01-requirements.md)「模型身分比對與現行一致」）。回答：服務回報的模型名稱格式與請求的模型 id 不同時，什麼情況視為同一個模型。

## 背景

讀者與摘要的每次模型呼叫，都把回應所回報的模型與 `readerModel` 比對，不符則 run 立即失敗並丟棄這次 run 的數字，以防服務悄悄換成別的模型。現行規則要求兩者逐字相同。

目標服務 Lemonade（底層 llama.cpp）在串流回應中回報的模型是模型檔案的完整路徑，結尾是請求的 id 加副檔名 `.gguf`。實際出現的情形：請求的 id 為某個含量化版本的名稱，回報的是 Hugging Face 快取目錄下同名的 `.gguf` 檔案的完整路徑。逐字比對因此在第一次呼叫就失敗，而服務並沒有換模型。

`readerModel` 的長度上限是 100 字元，完整路徑遠超過，無法以參數填入回報字串來繞過。

## 選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| **A. 回報值是檔案路徑時，以最後一段檔名去掉 `.gguf` 後與請求的 id 比對（採用）** | 不需要新參數；規則確定、可測；檔名含量化版本，仍能分辨不同的模型或不同的量化 | 只針對路徑格式；同檔名但內容不同的檔案無法分辨 |
| B. 新增選用參數，宣告服務回報的身分字串 | 明確，適用任何回報格式 | 字串太長，需放寬長度限制；每次換模型多一個參數，容易漏填 |
| C. 取消串流回應的身分比對，只靠模型可用性檢查 | 簡單 | 失去「模型被中途換掉」的保護，與原始需求衝突 |

## 決策

採 A。比對規則：

1. 回報的模型與請求的 id 逐字相同：相符（現行行為）。
2. 否則，若回報的值是檔案路徑（含路徑分隔符），取最後一段檔名，去掉副檔名 `.gguf`，與請求的 id 逐字相同：相符。
3. 其他情況：不符，行為不變（run 失敗、丟棄這次 run 的數字，訊息仍列出請求值與回報值）。

規則套用在所有模型呼叫（條件判定與摘要）。不放寬 `readerModel` 的格式與長度限制。

## 後果

- 同一規則在判定與摘要兩處共用，只有一個定義。
- 比對只信任檔名，不信任目錄；目錄不同但檔名相同會視為同一個模型，這是已接受的限度（來源是同一個服務的同一個模型庫）。
- 未來若遇到其他回報格式，再以新的決策擴充，不在本規則內臆測。
- 上線手冊的對應排錯列需補上這種格式的說明。
