# WI-1451 量測報告：經 gateway 以 GPU 強制對齊

本文回答：Qwen3-ForcedAligner 在 Lemonade 主機的 GPU 上，對齊 30 秒片段的速度與失敗率是否通過關卡，以及如何重跑量測。狀態：**速度與失敗率的關卡通過（2026-10-14）；時間精度延後到成品字幕核對**。工作項見 [WI-1451](../../stable/transcribe-scenes/work-items/WI-1451-feasibility-forced-alignment.md)，決策見 [ADR-051](../../stable/transcribe-scenes/adr/ADR-051-long-chunks-and-forced-alignment.md)、[ADR-056](../../stable/transcribe-scenes/adr/ADR-056-alignment-on-gateway-gpu.md)。

## 結論

| 通過條件 | 門檻 | 結果 | 判定 |
|---|---|---|---|
| 一小時影片（約 120 片段）的對齊總時間，含兩次 GPU 切換 | 不超過 30 分鐘 | 約 1 分鐘（對齊）加約 13 秒（兩次切換） | 通過 |
| 失敗片段 | 少於 10% | 對齊 0 個；12 個片段中 1 個（n04）轉錄被截斷，若計入為 1/12（約 8.3%） | 通過 |
| 時間精度 | 不在關卡內 | 延後到成品字幕核對 | 延後 |

## 量測環境

- 影片：run 8（日語）；片段計畫含 12 個 30 秒片段，涵蓋對白密集、長停頓、雜音或喘息。
- 轉錄：Qwen3-ASR，經 gateway，套用 WI-1461 的生成上限（每秒 12 token 加 64）。
- 對齊：從 arr 經 gateway（Lemonade 主機的 8098 埠）呼叫；工具來自 runline-transcribe 的 `5dd7d6e`。
- GPU：NVIDIA GeForce RTX 5070 Laptop，記憶體 12,231 MiB。

## 與 CPU 的對照

2026-10-14 在 arr（8 vCPU、31 GiB）以 CPU 做的初步量測（已不採用）：

| 項目 | 數值 |
|---|---|
| 每片段耗時中位數（float32） | 17.3 秒，其中約 8 秒是啟動與載入 |
| 一小時推估 | float32 約 35 分鐘；bfloat16 約 87 分鐘 |
| 峰值記憶體 | 約 6.1 GB（float32） |
| 映像增加 | 約 1.9 GB（壓縮後） |

GPU 版每片段快約 170 倍，一小時推估從約 35 分鐘降到約 1 分鐘，且 Engine 映像不增加。這是 [ADR-056](../../stable/transcribe-scenes/adr/ADR-056-alignment-on-gateway-gpu.md) 改用 GPU 的依據。

## 觀察

1. **轉錄文字與 CPU 版相同**：11 個有文字的片段，GPU 版與 CPU 版的轉錄逐片段相同，字詞切分也一致，所以一份人工標記可以兩邊共用。
2. **生成上限有效**：n04 是 CPU 量測時讓 Lemonade 持續生成數分鐘的雜音片段；加上限後在數秒內被截斷，不再佔住 Lemonade。
3. **尾端字詞的堆疊**：逐字稿比語音長時，最後的字詞被壓到音訊結尾，起點等於終點（例如最後兩個字詞「か 26.88–29.68」「こう 29.68–29.68」）。符合契約，但表示時間精度要在成品字幕核對。
4. **正規化已修**：日語的相容字元（全形英數、半形片假名等）原本會被改寫，已在 gateway 修正為保留原字元；本次量測的片段沒有這類字元。
5. **其他容器的負載**：量測時 arr 上 jellyfin 約 21% CPU，其餘低於 7%；對齊在 GPU 上，影響很小。

## 延後的驗證

起點精度需要聽得懂日語的人標記字詞起點，使用者無法執行。改為 WI-1460 完成後，以成品字幕對照影片抽查字幕出現與開口的時間差，見 [WI-1451](../../stable/transcribe-scenes/work-items/WI-1451-feasibility-forced-alignment.md) 的「延後的驗證」。量測工具保留人工標記的流程，日後有人能標記時可補量。

## 重跑量測的步驟

工具與選項以 runline-transcribe 的 `align/README.md` 為準，這裡只寫流程。

1. **取得工具**：在筆電以要量測的 commit 重建對齊量測 jar，放到 arr，檔名帶 commit；舊 jar 不動。
2. **前置**：Engine 沒有進行中的 run；記下當時的容器負載概況；確認 gateway 已部署到要量測的版本，且 `ALIGNER_MODEL_DIR` 已設定。
3. **片段計畫**：沿用 arr 上既有的計畫檔（12 個片段，含 n04），每行是片段代號、起點秒數、種類。種類為對白密集、長停頓、雜音或喘息。
4. **量測目錄**：GPU 與 CPU 各用自己的目錄，因為每次對齊都會重寫 `runs.tsv`。
5. **順序**：先取出片段並轉錄全部片段，再對齊全部片段，最後立刻執行 `resume` 步驟（對齊後第一個 Lemonade 請求），再產生報告。轉錄與對齊都經 gateway 的位址，不直接連 Lemonade。
6. **對齊步驟的選項**：給 gateway 的位址與對齊模型名稱（`Qwen3-ForcedAligner-0.6B`），單次逾時要容納 GPU 切換與模型載入（預設 300 秒）。轉錄的生成上限可用 `--asr-tokens-per-second`、`--asr-token-margin` 覆寫。
7. **看結果**：量測目錄的 `report.md`，其中時間精度與失敗比例在沒有人工標記時標為「未量測」。
8. **人工標記（選做）**：把片段複製到有聲音的電腦，用波形工具標記 `marks.tsv` 中字詞的起點，放回量測目錄後重跑報告步驟。
9. **在 Lemonade 主機上的效能紀錄**：用 gateway 的 `tools/measure_alignment.py`，說明見該儲存庫的 README「效能量測」。

## 風險與後續

1. 時間精度到成品字幕才驗證；若偏移明顯，來源可能是對齊、長片段切點或條目組成規則，停下由架構決定。
2. 只量了 11 個片段；其他素材（快節奏、暗場）的失敗率未知。
3. 對齊的第一個請求含 GPU 切換與模型載入，逾時設定需容納。
4. gateway 沒有認證且綁在 `0.0.0.0`，對齊端點同樣暴露在區網（[ADR-056](../../stable/transcribe-scenes/adr/ADR-056-alignment-on-gateway-gpu.md) 已列為取捨）。
