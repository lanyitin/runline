# ADR-047 刪除版本時，確認後連同終態 run 一併刪除

狀態：已核可（2026-10-13）。修訂 [ADR-020](../../pipeline-engine/adr/ADR-020-per-uploader-artifact-versions.md) 決策 8：`in_use` 只在 trigger 引用時成立，run 不再單獨阻擋刪除；ADR-020 的其他決策不變。回答：舊版 pipeline 有 run 紀錄時，如何在管理員確認影響後刪除。

## 背景

版本被 trigger 或 run 引用就不能刪除。run 是歷史紀錄，受保留期限清理管理，卻能永久擋住舊版的刪除；管理員只能等清理或改資料庫。管理員要的是看過影響後明確確認並刪除。

## 決策

1. 刪除版本時，該版本的終態 run 與其 log 可一併刪除，前提是管理員明確確認。
2. 確認以「預覽時看到的 run 總數」表達；與當下不符就拒絕並要求重新預覽。不帶確認而有 run 時仍拒絕，所以既有 API 呼叫端不會意外刪掉歷史。
3. trigger 仍阻擋刪除（`in_use`），須先改綁或刪除 trigger。
4. 進行中的 run 阻擋刪除（`runs_active`），須先取消或等待結束。
5. 影響由 Engine 的預覽端點計算並回傳，Console 不自行推算。
6. 觸發紀錄保留並清除對被刪 run 的參照，與保留期限清理一致。
7. 資料庫外鍵維持「拒絕刪除」；連帶刪除由刪除流程在單一交易內明確完成，不改成資料庫層的連鎖刪除。
8. 契約見 [05-ipc](../05-ipc.md)。

## 取捨

| 選項 | 優點 | 缺點 |
|---|---|---|
| 採用：run 連帶、trigger 與進行中 run 仍擋住 | 解決實際問題；不產生靜默失效的排程；無執行中 run 的競態 | 管理員要先處理 trigger 與進行中 run，多一步 |
| 連 trigger 一併刪除 | 一次完成 | 排程與 webhook 悄悄消失，難回復 |
| 自動取消進行中 run | 一次完成 | 取消與刪除的競態、run 私有目錄與 class loader 的釋放時機都要處理 |
| 資料庫改為連鎖刪除 | 實作少 | 失去第二道保證，任何誤刪路徑都會連帶刪歷史 |

## 後果

- 刪除版本是不可回復的操作，歷史 run 與 log 一併消失；Console 須讓管理員看清數量。
- `in_use` 的語意收窄為 trigger；依賴舊語意的呼叫端（含 Console 現行的說明邏輯）須更新。
- 預覽在 run 與 log 很多時有計算成本；範圍受保留期限清理限制。
- stable 的 06-data-model、08-api 與 ADR-020 須同步修訂（見 [WI-59](../work-items/WI-59-engine-delete-impact-and-force.md)）。
