# ADR-002 協作式 context 限制與 unsafe 判定

狀態：已核可（2026-10-05）。回答：限制如何作用、怎樣算 unsafe。

## 背景
Context 要依 metadata 限制檔案與連線，但最寬鬆設定下必須不阻擋任何 IO。JVM 沒有可靠的行程內沙箱。第三方函式庫與 pipeline 一同打包，同樣可能執行任意 IO。

## 決策
- Context 是協作式能力模型：經由 context 進行的 IO 會依 metadata 檢查；不經 context 的 IO 不受控。
- IO 類別：檔案、網路連線、外部行程執行。
  - 檔案：只限 pipeline 共享目錄與 run 私有目錄（[ADR-009](ADR-009-file-scopes.md)），本質上已受限。
  - 網路連線與外部行程：限制可以是明確的允許範圍，或不限制。
- Unsafe 判定，符合任一條即 unsafe 並記錄原因：
  1. 網路連線或外部行程未提供限制，或宣告為不限制。
  2. 類別參照樹中出現未列入白名單的節點（見下）。
  3. 參照 JVM 結束的成員（見 [ADR-011](ADR-011-jvm-exit-calls.md)）。
  4. 參照 IO 敏感成員（見 [ADR-013](ADR-013-io-sensitive-members.md)）。
- 類別參照樹：
  - 起點是 pipeline 定義所在的類別。
  - 逐層展開：分析每個節點所參照的類別，再分析被參照類別所參照的類別，直到沒有新節點。
  - 分析對象是編譯後的類別參照，不是原始碼的 import 語句；因此涵蓋以完整名稱直接引用的類別。
  - 每個節點對照白名單。白名單條目可以是套件，或完整類別（[ADR-014](ADR-014-class-level-allow-list-entries.md)）：
    - 套件條目涵蓋該套件及其子套件，可標記為「僅此套件」排除子套件。
    - 類別條目只涵蓋該類別及其巢狀類別。
  - 節點已在白名單時視為受信任，不再向下展開；但 JVM 結束成員與 IO 敏感成員的比對不受白名單豁免（ADR-011、ADR-013）。
  - Pipeline 自身的類別視為允許並繼續展開。
  - core 模組視為受信任的葉節點，不向下展開：core 的公開契約本身參照網路等 JDK 類別，展開會使所有 pipeline 都因這些套件不在白名單而被判 unsafe。
  - 節點不在白名單即為違規（例如樹中出現 `java.io.File` 而 `java.io` 未列入白名單）。
- 樹的範圍包含 jar 內夾帶的第三方函式庫。
- jar 內夾帶的 core 類別不納入分析。Run 實際使用的 core 以 Runner 載入的版本為準（[ADR-001](ADR-001-isolated-classloader.md)）。
- 每個違規回報從起點到該節點的路徑，讓作者知道是哪條依賴引入。
- 分析在上傳時進行，不執行 pipeline 程式碼。
- 白名單由管理員維護，判定記錄所用白名單版本；白名單變更時立即重判所有既有定義。

## 取捨
- 得到：低成本、上傳時即可判定、結果可解釋、能追溯到引入風險的依賴。
- 失去：反射與動態載入可繞過；unsafe 是風險提示，不是安全保證；白名單過窄會使含第三方庫的 pipeline 大量被判 unsafe。

## 後果
- 文件與 API 回應須明說此限度。
- 白名單條目因為被視為受信任，其內部依賴不再檢查；加入條目是管理員的信任決定。
- 不展開 core 與忽略 jar 內夾帶的 core 類別，其安全性依賴 Runner 的 class loader 優先載入自己的 core；該載入順序改變時須重新評估本決策。
