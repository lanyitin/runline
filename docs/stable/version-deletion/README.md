# 版本刪除：確認影響後連同 run 一併刪除

本文回答：管理員刪除一個已有 run 的舊版 pipeline 時，系統如何呈現影響、確認後如何真的刪除，以及這與現行規則的差異。狀態：已核可（2026-10-13）。修訂 [ADR-020](../pipeline-engine/adr/ADR-020-per-uploader-artifact-versions.md) 決策 8 中「`in_use` 含 run」的部分、[06-data-model](../pipeline-engine/06-data-model.md) 的版本刪除條款，以及 [08-api](../pipeline-engine/08-api.md) 的 `DELETE /api/v1/artifacts/{contentHash}`；同步修訂列為 WI-59 的驗收條件。

## 1. 需求摘要

- 目標：舊版 pipeline 因為 run 紀錄存在而無法刪除；管理員要能在看過影響後，確認並真的刪除。
- 角色：管理員（刪除版本本來就只有管理員）。
- 範圍內：影響預覽、確認後連同該版本的 run 與 log 一併刪除、Console 確認對話框。
- 範圍外：連帶刪除 trigger、自動取消進行中的 run、artifact 的保留期限清理、批次刪除多個版本。
- 假設（已由使用者確認採推薦值）：trigger 仍擋住刪除；進行中的 run 擋住刪除；對話框顯示 run、log、trigger 與 jar 內容的影響。
- 待確認問題：無。

## 2. 現況觀察

- 版本被 trigger 或 run 引用時，刪除回 409 `in_use`；資料庫以「拒絕刪除」參照 definition，作為第二道保證。
- Console 的確認對話框先送出刪除，被拒絕後才說明原因，之後沒有繼續刪的路。其說明的 run 數由前端取最新 200 筆計算，超過時偏小。
- run 保留期限清理（WI-20）已能刪除終態的 run 與其 log，並保留觸發紀錄、清除其 run 參照；本提案沿用同樣的資料關係，不新增資料表。

## 3. 方案比較與推薦

| 方案 | 內容 | 評估 |
|---|---|---|
| A（採用） | 預覽端點提供影響；刪除端點在明確確認後連同終態 run 與 log 刪除；trigger 與進行中 run 仍擋住 | 只解決「run 擋住」的問題；不會讓排程或 webhook 悄悄消失；沒有與執行中 run 的競態 |
| B | 同上，並連帶刪除 trigger 與其觸發紀錄 | 一鍵完成，但會刪掉排程與 webhook，影響面大且不易回復 |
| C | 同 A，進行中的 run 自動取消再刪除 | 要處理取消的完成時機與刪除的競態；風險高、收益小 |

決策與取捨見 [ADR-047](adr/ADR-047-delete-version-with-runs.md)。

## 4. 部署架構

不適用：不新增 process、組態或部署項目；仍是一個 Engine 加一個 PostgreSQL。

## 5. IPC 模型

預覽端點、刪除確認參數與錯誤碼見 [05-ipc](05-ipc.md)。Console 只用同源的 `/api/v1`。

## 6. 資料模型

不新增資料表或欄位，也不改變外鍵的「拒絕刪除」性質。刪除在單一交易內依序移除該版本 definition 的 run 與 log，清除觸發紀錄對這些 run 的參照，再刪除版本（內容移除規則不變）。

## 7. 非功能性考量與風險

| 風險 | 緩解 |
|---|---|
| 誤刪歷史紀錄 | 預設仍拒絕；必須帶預覽時的 run 數確認；Console 對話框明確列出數量與時間範圍 |
| 預覽與刪除之間影響改變 | 確認的 run 數與當下不符時回 409，要求重新預覽 |
| 刪除與新建 run 競態 | 同一版本的建立 run 與刪除互斥；刪除成立後建立 run 得到與「不存在」相同的結果 |
| 大量 run 的刪除交易過長 | 受保留期限清理約束的資料量為上限，接受單一交易。量測（真實 PostgreSQL）：3 萬 run／30 萬 log，預覽 0.2 秒、刪除 0.9 秒；10 萬 run／100 萬 log，1.8 秒、5.2 秒；5 萬 run／500 萬 log，24 秒、65 秒，期間該版本無法建立 run。保留期限很長而 log 極多的環境才會碰到後者，不另做分批 |
| 稽核 | 刪除記錄管理員名稱、版本、刪除的 run 與 log 數 |
