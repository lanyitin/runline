# ADR-065 測試套件的速度：分組、並行與去等待

本文回答：T 的測試套件耗時過長（全套約 20 分鐘）時，如何縮短而不降低檢查力。狀態：已核可（2026-10-15）。不改變 tdd-coder 定義中「只跑相關測試」的規則（見 `.claude/agents/tdd-coder.md` §1.1），本 ADR 處理的是全套與相關測試本身的成本。

## 背景

- 最近一次有逐類別計時的全套（T，195 個類別，約 1,230 個測試）：各類別耗時加總約 1,277 秒，單一序列執行；建置檔沒有設定測試並行。目前測試數約 1,280，全套約 22 至 23 分鐘。
- 耗時集中：前 24 個類別佔 80%。最大的幾個：
  - 量測工具的測試（`feasibility.*`）：約 290 秒，約 23%。
  - 各階段的端到端測試（`*RunTest`，含 `TranslateRunTest`、`TranscriptionRunTest`、`ChunkedRunTest`、`PolishRunTest`、`SummaryRunTest`、已移除階段的 `VerifyRunTest`）：每個 45 至 95 秒，合計約 500 秒以上。
  - 需要外部工具的測試（`AlignToolTest` 等）。
- 慢的代價：每項工作都要等 20 分鐘才能確認沒有破壞其他地方；tdd-coder 與使用者的中斷（誤按）常讓整輪重來；並行派工時各自的全套互相搶資源。
- 4 個 `DenoiseFixtureTest` 在非 Linux 環境固定失敗，使「全綠」永遠不成立，每次驗收都要人工比對基準線。

## 決策

1. **先量測再動手**：改動前先產出每個類別與每個測試的耗時、分類（純單元、假服務加真實資料庫的端到端、起外部行程、量測工具）與等待來源（固定的 sleep、重試退避、逾時、行程啟動）。後續每項改動都用同一份量測比較。
2. **去掉人為等待**：測試不應真的等待退避與逾時。設定退避與逾時為測試用的極短值（使用既有參數，不改 production 預設），或讓假服務回應立即；不以降低斷言換速度。
3. **共用昂貴的啟動**：起真實 Engine、外部行程、資料庫 schema 的成本，在不影響隔離的前提下由同一類別內的測試共用，不每個測試重啟。
4. **並行**：在確認測試彼此隔離（埠、暫存目錄、資料庫檔、環境變數）後，以類別為單位並行執行；不隔離的類別（用固定埠、共用檔案）先改成隨機埠與獨立目錄，再開並行。
5. **分組，不刪測試**：
   - 量測工具（`feasibility.*`）的測試獨立成自己的任務，在預設全套中保留，但只在量測工具的原始碼或其相依變動時需要跑（相關測試規則已涵蓋）；預設的 `test` 任務是否包含它由量測後決定，原則是**每個測試屬於且僅屬於一個任務**，總數與改動前相同，驗收時逐一核對。
   - 依賴特定平台的測試（如降噪基準 `DenoiseFixtureTest`）在不符平台時以前提條件跳過並註明原因，在 Linux（開發容器與部署環境）照常執行，不再讓非 Linux 的全套固定紅燈。
6. **不採用**：
   - 以 `@Disabled`、刪測試、放寬斷言換速度（tdd-coder 定義已禁止）；
   - 把慢測試移到「很少跑」的流程而不保證有人跑；
   - 用 Stub 或 Mock 取代假服務與真實資料庫（違反測試原則）。

## 取捨

- 得到：全套時間縮短，相關測試的回饋更快；基準紅燈消失，驗收可以直接看「全綠」。
- 失去：
  - 並行需要先讓測試隔離，初期有改動成本與偶發的並行問題風險，由每項改動後重複跑多次確認穩定。
  - 共用啟動可能讓測試之間產生順序相依；以隨機順序執行驗證。
  - 平台前提條件讓非 Linux 本機無法驗證降噪基準，改由 Linux 環境把關。

- 目標值見下方待確認問題；兩個建議值在核可時一併採用，量測報告若顯示不可行，由 tdd-coder 回報後調整。

## 待確認問題

- 全套時間的目標：建議本機全套 ≤ 8 分鐘、單一階段的相關測試 ≤ 2 分鐘。
- 量測工具的測試是否放進預設 `test`：建議保留在預設全套之外的獨立任務，並在量測工具變動時由相關測試規則要求執行；這會讓預設全套少約 23%。
