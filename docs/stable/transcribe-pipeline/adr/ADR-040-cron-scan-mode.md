# ADR-040 cron 觸發時由 pipeline 掃描收件目錄，每個 run 處理一部尚未產生字幕的影片

狀態：已核可（2026-10-12）。補充 [ADR-037](ADR-037-unsafe-pipeline-and-intake-root.md)、[ADR-039](ADR-039-subtitle-files-beside-video.md)；與既有文件衝突：[01-requirements](../01-requirements.md) 第 1 條與參數表（觸發只有 webhook、`file` 必填）、runbook 的參數表（`file` 必填），以本文為準，由 [WI-1423](../work-items/WI-1423-cron-scan.md)、[WI-1424](../work-items/WI-1424-cron-scan-docs.md) 同步修訂。回答：cron 觸發時如何找出待處理的影片、如何避免重複與無限重試、如何與其他 run 共存。

## 背景

目前每個 run 處理一部由 webhook 指定的影片（`file` 必填）。使用者希望以 cron 排程：觸發時自動在收件目錄尋找還沒產生過字幕的影片來處理。Engine 的 cron trigger 沒有呼叫端輸入（`callerParameters` 一律為空）、錯過的時間不補跑、沒有「上一個 run 未結束就跳過」的政策（ADR-005）。每個 run 處理一部影片需數小時，Lemonade 資源容量為 1，run 級持有並先進先出（01 假設 4、8）。

## 選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 掃描模式：`file` 為空時 pipeline 掃描收件根目錄，挑一部處理 | 單一 pipeline、單一 trigger；run 模型不變（一 run 一影片）；容量 1 使各 run 自然序列化 | 掃描規則在 pipeline 內；積壓的排隊 run 見風險 | 採用 |
| B. 掃描模式，且單一 run 處理所有待處理影片 | 一個 run 清完積壓 | run 長達數天；單片失敗與取消的語意複雜；紀錄模型要改 | 否決 |
| C. 外部腳本掃描後呼叫 webhook | pipeline 不變 | 多一個元件與排程；重複觸發要自行處理 | 否決 |

## 決策

**入口。** `file` 改為選填；為空（或未提供）即掃描模式。webhook 的 `file` 由管理員列入 `callerParameters`，呼叫端應提供；`file` 選填使 Engine 不再以「缺少必填參數」拒絕，所以 webhook 帶空的或沒有 `file`、或 trigger 沒有把 `file` 列入 `callerParameters` 時，run 也進入掃描（掃描只處理尚未產生字幕的影片，範圍與 cron 相同，可接受）。cron trigger 不設 `file`，其餘參數照常固定在 trigger。

**候選條件。** 掃描收件根目錄（遞迴），影片檔必須全部符合：

- 是一般檔案，不跟隨符號連結（檔案與目錄皆然）；名稱與路徑中的任何一段不以點開頭；
- 副檔名（不分大小寫）在允許清單中，預設 `mp4`、`mkv`、`mov`、`m4v`、`webm`，可由參數調整；
- 修改時間距現在至少 `scanMinAgeSeconds`（預設 600 秒），避免處理仍在複製的檔案；
- 同目錄沒有名為「影片檔名_zh-TW.srt」的路徑（任何型別都算已存在）。繁體中文字幕固定為 `zh-TW`、且與來源字幕同時寫出（ADR-039），所以它是「已產生過字幕」的唯一標記；
- 所在目錄可寫（ADR-039 的前置條件）；不可寫者排除並記入 log，不使整個佇列停住；
- 未達失敗上限：同一檔案（相對路徑，且檔案大小與修改時間相同）已有 `scanMaxAttempts`（預設 3）次結果為 `failed` 的 run 者排除。檔案被取代或修改後，視為新檔案重新計數。`stopped` 與被中斷的 run 不計。

**挑選與處理。** 候選依修改時間由舊到新（相同則依路徑）排序，取第一部，之後的流程與指定 `file` 的 run 完全相同。沒有候選時 run 立即成功結束，結果說明為專用的「無待處理」分類，不進入音訊以後的階段。每次掃描的 log 記錄掃描總數、候選數與各排除原因的計數，不列出路徑清單以外的內容。掃描數有上限（預設一萬個檔案），超過時以已掃到的為準並在 log 標示。

**共存與重複。**

- 掃描的正確性仰賴 `llm` 資源容量為 1：run 於建立後依先進先出取得資源，前一個 run 結束且字幕寫出後，後面的 run 才開始掃描，因此不會有兩個 run 挑到同一部。文件明列此前提；容量改大須另行處理。
- webhook 指定的檔案永遠處理（即使字幕已存在，覆蓋，見 ADR-039）；掃描不會重做已有字幕的影片。想重做時刪除其 `_zh-TW.srt` 或重送 webhook。
- cron 間隔短於單部影片的處理時間時，等待資源的 run 會累積，每個在輪到時各自掃描（無待處理則立即結束）。排程的間隔應不小於典型的處理時間；Engine 的「前一個 run 未結束就跳過」政策為獨立議題，不在本決策內。

## 取捨

- 得到：丟影片進目錄即可，不需外部程式；失敗的檔案不會每次都重試而塞住佇列；run 模型與紀錄不變。
- 失去：每次 cron 觸發只處理一部，積壓以觸發次數消化；「已產生過字幕」以檔案存在判定，刪除或搬走字幕檔會導致重做；掃描規則成為 pipeline 的契約。

## 後果

- 參數表新增 `scanExtensions`、`scanMinAgeSeconds`、`scanMaxAttempts`，`file` 改選填；run 紀錄新增影片檔的大小與修改時間（檔案指紋），供失敗上限判定。
- 「無待處理」的 run 也留下 run 紀錄（受既有保留規則清理）。
