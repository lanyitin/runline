# ADR-029 建置輸入以雜湊固定

狀態：已核可（2026-10-11）。補充 [ADR-027](ADR-027-forgejo-action-image-publishing.md)。回答：映像檔建置所依賴的外部輸入（CI 的 action、容器基底映像）以什麼方式固定，以及如何更新。

## 背景

推送 `v*` tag 的工作流程持有能推送映像檔的憑證，產出的映像檔由維運者手動上線到 arr。因此建置輸入若被上游悄悄替換，後果會直接傳到部署環境。目前兩類輸入只以可移動的標籤引用：

- 工作流程使用的 action 以版本標籤引用（標籤可被上游改指到別的提交）。
- 容器基底映像以名稱加標籤引用（同一標籤的內容會隨上游重新發佈而改變），建置結果因此不可重現。

## 選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| **A. 所有 action 與容器基底映像都以內容雜湊固定，更新是明確的人工動作（採用）** | 上游替換標籤也不影響建置；建置可重現；變更可在版本庫審閱 | 需要手動更新雜湊才能取得安全修補 |
| B. 維持標籤，靠定期人工檢視 | 自動取得修補 | 無法防止被替換；不可重現 |
| C. 固定雜湊，並由自動化工具提出更新 | 兼得固定與修補 | 需要額外的工具與維運，現階段規模不值得 |

## 決策

採 A。

1. 工作流程使用的每個 action 以完整提交識別（不是標籤）引用，旁邊以註解標明對應的版本，供人閱讀。
2. 建置與執行所用的每個容器映像（Engine 的基底映像、PostgreSQL）以內容雜湊（多平台索引的雜湊）引用，旁邊標明對應的標籤供人閱讀。
3. 雜湊的更新是人工動作：維運者決定升級後，取得新的雜湊、確認來源、更新引用並重新驗證。升級時機由維運者決定，不排程。
4. 固定的雜湊只出現在引用處一次，不在多處各寫一份。

## 後果

- 取得上游的安全修補不再自動發生；維運者需自行留意基底映像與 action 的更新通告。這是為了可重現性與供應鏈完整性而接受的代價。
- `deploy/publish-image` 的架構檢查必須對實際建置所用的那個基底映像執行，不得另用浮動標籤。
- 本決策不涵蓋 Chrome 安裝套件：它維持以版本號固定、從 Google 的網址下載，不驗證內容雜湊。這是已接受的限度，Chrome 的完整性仰賴下載來源與傳輸安全。
