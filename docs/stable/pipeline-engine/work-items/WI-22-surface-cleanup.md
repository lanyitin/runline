# WI-22 對外介面清理與目錄名稱規則共用

本文回答：如何移除範本遺留的未認證端點，並讓 Engine 與 Runner 共用同一條目錄名稱規則。狀態：已核可（2026-10-05）。相依：WI-18。

## 背景

- Engine 保留了範本遺留的對外端點：Engine 關閉端點（不需認證即可讓 Engine 停止服務）、回聲 WebSocket、範例 JSON。它們不屬於產品功能（[ADR-012](../adr/ADR-012-api-authentication.md)）。
- 目錄名稱規則（字母、數字、`.`、`_`、`-`，`.` 與 `..` 被拒絕）定義在 Runner，Engine 的上傳驗證目前以建立一個指向不存在根目錄的目錄服務、呼叫其唯讀方法的方式間接詢問，並重用其例外訊息。這個繞道脆弱，且會留下不必要的遙測事件。

## 行為與驗收條件

### 對外介面清理
- Engine 的關閉端點、回聲 WebSocket 與範例 JSON 端點被移除；對這些路徑的請求得到「不存在」。Log 串流的 WebSocket 與 API 文件端點不受影響。
- Engine 的關閉只經由終止訊號觸發；[WI-18](WI-18-upload-hardening.md) 的優雅關閉行為與其打包形態測試維持通過。
- 測試列舉所有已註冊的路由：除 ADR-012 明列的免認證端點（API 文件與其 schema、webhook 入口）外，無 token 的請求一律被拒絕。新增的免認證端點會使此測試失敗。
- API 文件（[08](../08-api.md)）同步更新，並仍與實作一致（既有的文件一致性測試維持通過）。
- 與已移除端點相關的既有測試與說明一併移除或更新；其他既有測試不被刪除或放寬。

### 目錄名稱規則共用
- Runner 公開目錄名稱規則：提供一個無副作用的方式驗證 pipeline 名稱與 run 識別碼，結果與其目錄準備使用的規則完全相同；規則只有一份。
- Engine 的上傳驗證改用這個公開的規則，移除繞道的實作；錯誤語意（錯誤代碼、列出不合規的 pipeline 與允許的字元範圍）與改動前相同。
- 保留既有的一致性測試，證明上傳規則與 Runner 目錄準備的結果一致。
- Runner 的對外行為與既有測試不變；Runner 仍只依賴 core。

### 共同
- 建置、全部既有測試（含打包形態的測試）在 JDK 25 下通過，`ktfmtCheck` 通過；除被移除端點專屬的測試外，既有測試數量不減少，並說明被移除的測試。

## 架構約束

- 修改範圍限於 engine 與 runner 的上述部分；core、analyzer、devkit 不受影響。
- Runner 公開規則不得引入對 Engine、Ktor 或資料庫的相依。
- 不改變既有 API 的成功行為與認證、權限語意（[ADR-012](../adr/ADR-012-api-authentication.md)）。
- 不新增外部相依；不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
- 測試使用真實 PostgreSQL（Testcontainers）與打包形態的真實行程，不使用 Stub 或 Mock。
