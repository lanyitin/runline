# ADR-021 資源型別目錄以唯讀端點公開，Console 不保留複本

狀態：提案中（2026-10-08）。補充 [ADR-019](../../../stable/pipeline-engine/adr/ADR-019-typed-shared-resources.md) 第 11 點與決策 13，不取代。回答：Console 的資源表單從哪裡取得 Engine 內建、隨版本發佈的型別資訊。

## 背景

- ADR-019 決策 13：`openai-compatible` 的端點目錄是版本化、隨 Engine 發佈擴充的；新條目對既有資源預設不啟用。
- `jdbc-pool` 的資料庫種類與允許的連線屬性同樣由 Engine 內建的資料庫設定檔決定，新增資料庫需要發佈新版 Engine（ADR-019 決策 7）。
- 08-api 沒有任何端點提供這些資訊，因此 WI-50 在 Console 內保留了端點目錄、請求參數清單與資料庫種類的複本。Engine 仍以 `invalid_endpoint`、`unsupported_database`、`property_not_allowed` 拒絕不在其目錄的值，安全性不受影響；但 Engine 的目錄一變，Console 就會顯示錯誤的選項（少列新條目、或列出已移除的條目），需要人工同步。
- Console 由同一個 Engine 提供（[ADR-015](../../../stable/pipeline-engine/adr/ADR-015-console-frontend.md)），所以執行中的 Engine 就是正確目錄的唯一權威來源。

## 方案比較

| 方案 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A 只公開 `openai-compatible` 端點目錄 | 一個只回傳端點條目與請求參數清單的端點 | 範圍最小 | 資料庫種類與允許屬性仍留在 Console 複本；下一個型別或資料庫又要新端點 |
| **B 單一型別描述端點（推薦）** | 一個端點回傳封閉型別集合，以及各型別由 Engine 固定的選項（端點目錄、請求參數、資料庫種類與允許屬性） | 所有複本一次消除；新增型別或資料庫只擴充回應內容，不新增路由；與「型別集合封閉、隨 Engine 發佈」的模型一致 | 回應結構需容納不同型別的內容，08-api 的描述較長 |
| C 維持複本，加一致性測試 | 不新增 API；以測試比對 Console 複本與 Engine 目錄 | 不動 API | 仍是兩份資料；只是把不同步提前到建置時失敗，仍要人工改；使用者已選擇新增端點 |

推薦 B：資料只有一份，且路由數量不隨型別或資料庫增加而增加。

## 決策

1. **新增唯讀端點 `GET /api/v1/resource-types`**，回傳執行中 Engine 內建的型別描述。內容：
   - 封閉的型別集合，依 Engine 的固定順序列出。
   - `openai-compatible`：端點目錄的每個條目，包括識別名稱、所屬群組、HTTP 方法、相對路徑樣板、請求本文種類、回應種類、是否可串流、是否預設啟用、是否為有狀態或會刪除服務端資料的條目；可設定預設、鎖定或上限的請求參數清單，包括名稱與值的種類，以及是否可設上限。
   - `jdbc-pool`：每個資料庫設定檔的種類識別，以及該設定檔允許的連線屬性與各屬性的值規則（例如長度上限、可選值）。
   - 不含任何個別資源的設定、使用量或機密，也不含 Engine 的組態值（例如資源根目錄）。
2. **唯一事實來源是 Engine 內部的型別描述**：端點回應、建立與修改資源時的驗證，以及 `invalid_endpoint`、`unsupported_database`、`property_not_allowed` 的判定，全部取自同一份描述，不得各自維護清單。
3. **授權**：需要 Bearer，限管理員；開發人員得到 403，沒有 token 得到 401，與 `/api/v1/resources` 一致。理由是目前只有管理員的資源表單需要它；開發人員撰寫 pipeline 時以文件為準。
4. **版本語意**：不另設目錄版本號。回應永遠代表執行中的 Engine，其版本由 `GET /api/v1/info` 提供。回應在同一個 Engine 行程內不變。
5. **Console**：資源表單以此端點為唯一來源，移除前端的端點目錄、請求參數清單與資料庫種類的複本。端點讀取失敗時，Console 顯示錯誤並停用需要目錄的型別表單（`openai-compatible`、`jdbc-pool`），不退回任何內建清單。`counter` 與 `file` 的表單不依賴目錄。
6. **Fake Engine**：Console 測試用的 Fake Engine 提供同一個端點，並以契約測試對齊真實 Engine 的回應結構與內容。

## 契約

- 呼叫者：Console（同源）。被呼叫者：Engine。同步 HTTP GET，無副作用，可安全重試。
- 回應：200，JSON。結構與欄位名稱由 08-api 記載，沿用既有命名慣例；新增型別或條目只擴充內容，不改既有欄位的意義。
- 錯誤：401（無 token）、403（開發人員）。
- 快取：Console 每次載入資源頁時讀取一次即可，不需輪詢。

## 取捨

- 回應結構需容納不同型別的內容，比單一型別的端點複雜，換得往後不需新增路由。
- 限管理員讀取，日後若開發人員需要（例如 devkit 或 pipeline 頁要顯示可用條目），須另行決定是否開放。

## 後果

- 08-api 新增一個路由，`ApiDocumentationTest` 隨之更新；08-api 目前對端點目錄的文字列舉保留為說明文件，事實來源改為端點回應。
- WI-50「實作結果」所述的 Console 複本由 WI-55 移除，該段描述隨之改寫。
- 風險：Engine 的內部描述與驗證邏輯若分離維護，端點會與實際驗證不一致。因此決策 2 要求兩者共用同一份描述，並由驗收條件驗證。

## 待確認問題

- **讀取權限**：採管理員專屬。若希望開發人員也能讀取，例如 pipeline 詳情頁要顯示可用條目，影響授權規則與測試範圍。
- **設定預設值是否一併公開**：例如 `openai-compatible` 的逾時與大小上限預設、`jdbc-pool` 的連線額度預設。公開之後，Console 可顯示「留空時的實際值」，而不只是「Engine 預設」；但回應範圍會擴大，而且預設值須與正規化邏輯共用同一來源。本提案暫不納入，Console 維持「留空即 Engine 預設」的現行顯示。
