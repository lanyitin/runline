# WI-14 ktfmt 格式化可用於專案

本文回答：如何讓 tdd-coder 在每次完成程式碼變更時，都能用 ktfmt 格式化並驗證格式。狀態：已核可（2026-10-03）。無相依，可與其他項並行。

## 背景

[tdd-coder 的工作習慣](../../../../.claude/agents/tdd-coder.md)要求每次完成程式碼變更時先以 ktfmt 格式化。專案目前沒有任何格式化工具的設定，工具無法使用時 tdd-coder 只能回報而無法繼續。

## 行為與驗收條件

- 在 devcontainer 內與本機，開發人員與 tdd-coder 都能用單一、文件化的方式，對全部 JVM 模組（`core`、`runner`、`engine`）的 Kotlin 原始碼執行 ktfmt 格式化。
- 同一方式可只檢查格式而不改檔；有未格式化的程式碼時檢查失敗，並指出哪些檔案不合規。
- 對已格式化的程式碼重複執行不再產生變更。
- 格式化範圍涵蓋主程式與測試程式；不涵蓋 `build/` 等產生物。
- 既有程式碼一次性格式化到合規狀態，且該次變更只包含格式差異，不夾帶行為改變；建置與既有測試在 JDK 25 下通過。
- 使用方式寫入專案說明文件；說明包含在 devcontainer 與本機的差異（若有）。
- ktfmt 的版本固定，不同環境得到相同結果。

## 架構約束

- 不改變任何行為；`core` 與 `runner` 的依賴邊界不受影響，ktfmt 不得成為它們的執行期相依。
- 工具版本與設定在專案內單一處管理，不散落在個人環境（12-Factor 的 Dev/prod parity）。
- 不新增 git hook 或 CI 流程；若需要，另開工作項。
- 沒有網路或 ktfmt 無法取得時，行為是明確失敗並回報，不靜默略過。

## 待確認問題

- ktfmt 的取得與執行形式（獨立執行檔、Gradle 外掛，或其他）。影響：決定放在 devcontainer 映像、建置檔，或兩者；工作項不預先指定，由 tdd-coder 評估後回報。
- 是否要把「格式檢查」納入 `check` 這類既有的驗證流程。影響：納入後格式不合規會讓整體建置失敗。
- 格式規則是否採用 ktfmt 預設。影響：自訂規則需另行記錄在專案文件中。
