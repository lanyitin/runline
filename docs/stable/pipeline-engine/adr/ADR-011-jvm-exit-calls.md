# ADR-011 JVM 結束呼叫由靜態分析判為 unsafe

狀態：已核可（2026-10-04）。補充 [ADR-002](ADR-002-context-and-unsafe.md)，與 [ADR-006](ADR-006-unsafe-policy.md) 搭配。回答：pipeline 呼叫會讓整個 JVM 結束的方法時，系統如何處置。

## 背景

所有 run 在同一個 JVM 內執行（[ADR-001](ADR-001-isolated-classloader.md)、[ADR-008](ADR-008-execution-model-and-jdk.md)）。Pipeline 若呼叫 JVM 結束的方法，會使 Engine 與所有其他 run 一併終止。Context 是協作式限制，不經 context 的行為不受控（ADR-002）。

ADR-002 的白名單只到套件層級，而 `java.lang` 幾乎必然列入白名單，因此套件層級的比對無法識別這類呼叫，需要成員層級的比對。

Pipeline 以 Kotlin 撰寫。Kotlin 標準函式庫的行程結束函式是 inline-only：編譯後，呼叫端的位元碼直接含有 JDK 的結束成員參照，不含標準函式庫成員的參照。因此以 Kotlin 呼叫該函式的 pipeline 由 JDK 成員的比對涵蓋。標準函式庫成員的比對只對非內嵌形式的位元碼參照有作用，例如其他語言或工具產生、直接參照該成員的類別。

## 決策

- 編譯後的程式碼中，只要參照下列任一成員，即為 unsafe 的第三個判定條件（與 ADR-002 的兩條並列，任一條成立即 unsafe）：
  - 系統類別的 JVM 結束成員。
  - 執行期類別的結束成員。
  - 執行期類別的強制終止成員。
  - Kotlin 標準函式庫 `kotlin.system` 套件中的行程結束函式（涵蓋非內嵌形式的參照）。
- 這組成員的比對在成員層級，不受套件白名單豁免：即使所屬套件在白名單內，參照仍判為違規。
- 違規回報從起點到該參照的完整路徑，與 ADR-002 的路徑回報一致。
- 判定範圍與 ADR-002 相同：起點為 pipeline 定義所在的類別，逐層展開，包含 jar 內夾帶的第三方函式庫；已在白名單的節點視為受信任、不向下展開，其內部不檢查。
- 不在執行期攔截：Runner 不加入任何阻擋 JVM 結束的機制。
- Unsafe pipeline 在管理員允許後執行（ADR-006），等同接受此風險；此時 pipeline 終止 JVM 屬於被授權的行為。
- 結果與文件須明說：反射與動態載入可繞過此判定，與 ADR-002 的限度相同。

## 取捨

| 項目 | 優點 | 缺點 |
|---|---|---|
| 靜態判定 | 上傳時即可得知、可解釋並追溯到引入的依賴；不增加執行期成本，不改變同一 JVM 的決策 | 反射與動態載入可繞過；白名單內的第三方庫內部呼叫不被檢查 |
| 不在執行期攔截 | Runner 保持簡單，不引入已被棄用或不可靠的機制 | 被繞過或被授權的 unsafe pipeline 仍可終止 JVM |
| 保留 Kotlin 標準函式庫成員 | 涵蓋非內嵌形式的參照，清單與標準函式庫的公開行程結束函式一致 | 對一般 Kotlin 原始碼不增加偵測能力；成員清單需隨標準函式庫變動維護 |

被否決的做法：每個 run 使用獨立子行程（與 ADR-001、ADR-008 的同一 JVM 決策衝突，成本高）；接受風險而不處置（任何 pipeline 都能停止 Engine，與 unsafe 授權模型不符）。

## 後果

- WI-05 增加這組成員的判定條件與對應原因。
- 管理員決定允許 unsafe 時，應知道這包含終止 Engine 的可能；使用者介面或回應文件須明說。
- 需要抵禦被授權的 unsafe pipeline 或反射繞過時，需另開 ADR 評估行程隔離。
- 本決策需要分析範圍涵蓋方法層級的參照，不只類別層級；分析的其他規則不變。
- 成員清單的內容是本 ADR 的一部分；清單變動時修訂本 ADR。
- Kotlin 標準函式庫若將行程結束函式改為非 inline-only，Kotlin 呼叫端的位元碼將參照標準函式庫成員，此時清單中的標準函式庫成員即成為主要的偵測依據。
