# WI-1479 量測一次工作回饋的完整成本

本文回答：T 的測試回饋時間花在哪裡。狀態：已核可（2026-10-15）。相依：無。決策見 [ADR-072](../adr/ADR-072-test-pyramid-and-relaxed-test-doubles.md) 決策 1。儲存庫：T。這是量測項，不改測試與 production 行為。

## 行為與驗收條件

1. **量測報告**：交一份報告，涵蓋下列成本，並說明量測環境（機器、核心數、是否冷快取）：
   - Gradle 組態、編譯（主程式、測試、量測與假服務來源集）、依賴與資源準備（含 `fetchAligner` 等下載任務）、打包；
   - 每個測試類別與每個測試的耗時，前 30 名；
   - 分類：純邏輯、行程內整合、端到端（完整 devkit 行程）、外部行程、量測工具；每類的測試數與耗時加總；
   - 並行利用率（四個 JVM 是否都忙、是否有單一長類別拖尾）；
   - 端到端測試單價的拆解：JVM 啟動、資料庫初始化、VAD 工具、ffmpeg、假服務啟動各占多少。
2. **三種情境的實測**：改動一個階段（例如翻譯）後，下列各需多久：(a) 現行規則的相關測試、(b) 全套預設任務、(c) 冷快取全套。每種至少兩次，列出差異。
3. **歸因**：說明 30 分鐘以上的回饋時間由哪些部分組成，並指出：若端到端測試不改，單靠並行與機器資源能壓到多少；若所有端到端測試改成行程內執行（不起子行程），估計能省多少。估計的依據要附數據。
4. **方法可重現**：量測指令寫在 README，不新增 production 行為，不新增只為測試存在的 production 後門。
5. **不改測試內容**：不刪、不跳過、不改斷言；報告以外只新增量測用的建置任務或腳本。
6. 回報時給報告路徑、量測指令、關鍵數字摘要。

## 架構約束

- 不改 Engine、不改 schema、不改 production 行為。
- 量測不得干擾其他進行中的工作：在獨立 worktree 與分支，並避免同時啟動兩個 Gradle。
- 數字如實回報，不為達標而調整量測方法。
