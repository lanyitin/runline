# ADR-020 版本以「內容雜湊 + 上傳者」識別：相同位元組由不同人上傳時各自成為一個版本

狀態：已核可（2026-10-07）；「待使用者確認」所列的點採推薦值，待使用者確認。修訂 [ADR-003](ADR-003-jar-and-discovery.md) 的「以內容雜湊辨識版本」一句，補充 [ADR-012](ADR-012-api-authentication.md) 的擁有權語意；[ADR-006](ADR-006-unsafe-policy.md)、[ADR-002](ADR-002-context-and-unsafe.md)、[ADR-005](ADR-005-trigger-binding.md) 的語意不變。回答：兩位上傳者上傳位元組完全相同的 jar 時，Engine 如何識別版本、保存位元組、判定、授權、刪除，以及如何不洩漏他人是否上傳過。

## 背景

現行以內容雜湊作為版本的唯一識別（`pipeline_artifact.content_hash` 唯一）。第二位開發人員上傳相同位元組時，Engine 回 200 並指向第一位的版本；開發人員只看得到自己上傳的版本（[ADR-012](ADR-012-api-authentication.md)），因此第二位看不到、也不能用該版本（查詢回 404，建立 run 回 `definition_not_found`），且回應本身洩漏「有人上傳過相同內容」。使用者決定：Engine 為第二位另建版本。

## 決策

1. **版本的識別是（內容雜湊，上傳者）**。上傳者是 token 對應的名稱（[ADR-012](ADR-012-api-authentication.md)；名稱相同即同一身分，與現行擁有權比對一致）。同一內容雜湊可有多個版本，每個上傳者最多一個。Engine 內部以既有的代理鍵關聯，definition、trigger、run 仍以代理鍵參照版本內的 definition，不因本決策而改變。
2. **API 路徑與欄位仍以 `contentHash` 為主，不破壞既有呼叫**。開發人員只看得到自己的版本，因此 `contentHash` 對開發人員永遠足以指到唯一版本。管理員可能看到同一雜湊的多個版本，以選填的 `uploader`（版本的上傳者名稱）消歧義：
   - 查詢參數：`GET`／`DELETE /artifacts/{contentHash}`、`PUT /definitions/{contentHash}/{pipeline}/unsafe-execution`。
   - 請求本文欄位：建立 run、建立與修改 trigger 的 `contentHash` 旁。
   - 解析規則：呼叫者可見的版本恰好一個時，`uploader` 可省略；有多個且未給 `uploader`，回 409 `ambiguous_version`，本文列出 `uploaders[]`；給了 `uploader` 但沒有該版本，或呼叫者不得使用，回與「不存在」相同的 404。管理員的解析不偏好「自己的版本」，避免對 unsafe 設定、trigger 綁定、刪除等有授權意義的操作靜默選錯版本。
   - 開發人員給 `uploader` 時，只有等於自己的名稱才被接受，其他值回 404（與不存在相同）。
   - 回應（artifact、definition 列表、run、trigger、白名單 `changes[]`、資源的 `declaredBy.definitions[]`）一律帶出版本的 `uploader`，作為管理員消歧義的來源；artifact 與 definition 的 `uploadedBy` 欄位維持。
3. **上傳語意**：
   - 同一上傳者重複上傳相同位元組：200，回傳該上傳者自己的既有版本，不產生新紀錄（維持冪等）。
   - 不同上傳者上傳相同位元組：建立新版本，回 201，內容與全新上傳的回應無法區分，只含呼叫者自己的版本資料。
   - 解壓上限、分析、名稱規則等拒絕（413、422）只取決於位元組與目前白名單，不因他人是否上傳過而不同。
4. **判定與設定逐版本獨立**。definition 仍屬於版本：safe／unsafe 判定、`allowListVersion`、`allowUnsafeExecution` 與設定者各版本獨立保存，不共享、不繼承（沿用 [ADR-006](ADR-006-unsafe-policy.md)）：管理員核准甲的版本以 unsafe 執行，不等於核准乙的版本；乙需另行核准。新版本的 unsafe 設定一律為不允許。
5. **判定一律以目前白名單重新分析，不複製他人版本的判定**。第二位上傳走完整的解壓檢查與分析路徑，與全新上傳相同；這使判定永遠依目前白名單、回應時間不暴露「已有人上傳過」。
6. **白名單變更的重判**逐版本處理（沿用「同一交易、持白名單鎖」的現行規則，[06](../06-data-model.md)）。Engine 可對同一內容雜湊只分析一次、結果套用到該雜湊的每個版本（效能最佳化，不改變結果）。影響摘要（`examinedArtifacts`、`examinedDefinitions`、`becameUnsafe`、`becameSafe`）以版本與其 definition 計；`changes[]` 每個受影響的版本各列一筆，並含 `uploader`；「收回允許 unsafe 執行」逐版本判斷。
7. **位元組去重儲存**：jar 位元組以內容雜湊為鍵只存一份，各版本以內容雜湊參照；版本是只含上傳者、時間與其 definition 的輕量紀錄。位元組（含大小）屬於內容，不屬於版本。最後一個參照某內容的版本被刪除時，該內容在同一交易內移除；並行上傳與刪除下不得出現版本指向已不存在的內容。
8. **刪除與保留**：刪除以版本為單位，仍只有管理員；`in_use` 以該版本的 definition 是否被 trigger 或 run 引用判斷，甲的版本被引用不阻擋乙的版本被刪除。Artifact 沒有保留期限清理（只有 run、log、觸發紀錄有），本決策不新增。
9. **Trigger 綁定**維持綁到特定版本內的 definition，永不隨新版本移動（[ADR-005](ADR-005-trigger-binding.md)）；管理員綁定時以 `contentHash` 加 `uploader` 指到某位上傳者的版本。cron 與 webhook 觸發建立 run 的來源與權限語意不變。
10. **不洩漏存在性**（開發人員的視角）：
    - 回應只含呼叫者自己的版本；`uploadedBy`、`uploadedAt` 是呼叫者自己的。
    - 第二位上傳不回 200 或任何專屬代碼；與全新上傳同為 201。
    - 查詢、建立 run 對他人版本與不存在的回應位元組級相同（既有行為，擴及 `uploader` 參數）。
    - 沒有任何針對開發人員的「雜湊是否存在」端點、錯誤代碼或訊息；`ambiguous_version` 只可能出現在管理員（開發人員永遠只有一個可見版本）。
    - 時間：第二位上傳走完整分析（決策 5），主要成本與全新上傳相同；殘餘差異只在「寫入位元組」被去重略過的部分，相對解壓與分析可忽略，列為已知殘餘風險，不另加人為延遲。
    - 日誌與 trace 可記錄「該雜湊已有其他版本」供管理員排查，但不出現在任何開發人員可取得的回應中。

## 方案比較

| 方案 | 說明 | 評估 |
|---|---|---|
| A 內容雜湊 + 上傳者（推薦） | 每位上傳者一個版本；路徑沿用 `contentHash`，管理員以 `uploader` 消歧義 | 不破壞既有路徑、請求與資料；開發人員零變更；多版本只在管理員視角出現，由明確的 409 或 `uploader` 處理；版本、unsafe 授權、刪除各自獨立。代價是管理員對同雜湊的操作多一個參數 |
| B 獨立版本識別碼 | 版本有不透明 id，API 改以 id 為主 | 消歧義最乾淨，但所有路徑、請求、trigger 回應與 Console 都破壞相容；開發人員也要改用 id；本需求不需要這麼大的變更 |
| C 同一版本、多位擁有者 | 版本不變，另存擁有者集合 | 使用者已決定「另建版本」，且 unsafe 授權、刪除與「誰是上傳者」在共享版本下語意含糊；不採用 |

位元組儲存另有「每版本各存一份」與「去重」兩種做法：每版本各存一份最簡單，但相同的大 jar（上限 50 MiB）按上傳者數倍增；去重只需要一次遷移並使刪除多一條規則，採去重。

## 取捨

- 得到：第二位上傳者得到自己可見、可用的版本；既有 API、既有資料、開發人員流程與 trigger 綁定不變；unsafe 授權與刪除維持逐版本的最小授權；不洩漏他人是否上傳過。
- 失去：管理員對同一雜湊的操作可能需要 `uploader`；同一 jar 被多人上傳時，definition 與判定各存一份（但位元組只存一份）；重判成本隨版本數增加（可由同雜湊只分析一次緩解）。

## 後果

- 資料模型：[06](../06-data-model.md) 的「Pipeline Artifact」改為版本（內容雜湊 + 上傳者唯一）並新增內容實體；本決策的實作工作項（[WI-54](../work-items/WI-54-per-uploader-artifact-versions.md)）同步更新 06 與 08-api，之前兩份文件維持現狀。
- 遷移：既有每個版本成為其內容雜湊的唯一版本，沒有資料需要拆分或合併；definition、trigger、run 的參照不變。遷移為單向前進，遵循現行遷移策略（[06](../06-data-model.md)）。
- Console：管理員頁在同雜湊有多個版本時顯示並攜帶 `uploader`；上傳結果的 200 只表示「你已上傳過相同內容」。
- 開發入口與 Runner 不受影響。

## 待使用者確認

| 問題 | 影響 | 推薦 |
|---|---|---|
| 管理員對同雜湊多版本且未給 `uploader` 時，回 409（推薦），或預設選「最早上傳的版本」？ | 後者與舊行為最接近，但對 unsafe 設定、trigger 綁定、刪除可能靜默作用在非預期的版本 | 409 `ambiguous_version`；Console 一律帶 `uploader` |
| 管理員核准某版本以 unsafe 執行時，是否提供「套用到同內容雜湊的所有版本」的便利操作？ | 本決策為逐版本獨立；便利操作屬 UI／API 擴充 | 本次不做；有需求時另開項目 |
| 重判是否採「同雜湊只分析一次」最佳化？ | 只影響效能，不影響結果 | 採用；若實作成本高可延後，不影響驗收 |
