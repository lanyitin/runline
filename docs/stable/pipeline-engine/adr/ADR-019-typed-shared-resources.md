# ADR-019 共享資源對應實體：型別化資源、Engine 中介存取與金鑰庫保存機密

狀態：已核可（2026-10-06）。補充 [ADR-007](ADR-007-shared-resources.md) 與 [ADR-009](ADR-009-file-scopes.md)，不取代：ADR-007 的整體取得、先進先出、無死結與釋放語意全部保留。回答：共享資源如何對應到實際的檔案、資料庫連線池與 OpenAI 相容服務，Engine 如何把它們交給 run，機密如何保存與使用，資源如何刪除。

## 背景

ADR-007 的資源只有名稱與容量：pipeline 宣告名稱，Engine 在記憶體計數，run 持有至結束。資源不對應任何實體，鎖是約定式的；API 沒有刪除端點（[08-api](../08-api.md)「共享資源」）。使用者期望資源能實際對應到一個檔案或一個連線，涵蓋三種情境：

1. 多個 run 寫同一個檔案，需要互斥，並由 Engine 保證路徑可用。
2. 多個 run 共用同一個資料庫連線池，連線池由 Engine 持有，密碼不外洩給 pipeline 原始碼或 log。首階段只支援 PostgreSQL，設計須可擴充到任何 JDBC 資料庫。
3. 多個 run 對同一個 OpenAI 相容 API 服務（例如本機的 lemonade server，也可能是其他相容服務）發出請求，需要並行限制，端點、金鑰與請求預設由管理員管理。

現況事實會影響方案：

- Run 與 Engine 在同一個 JVM，以獨立 class loader 隔離，每個 run 一條專屬平台 thread（[ADR-001](ADR-001-isolated-classloader.md)、[ADR-008](ADR-008-execution-model-and-jdk.md)）。沒有子行程，因此「連線池跨行程共享」的問題目前不存在：Engine 持有的物件可以經邊界交給 run，只要邊界上的型別是 JDK 內建型別（[05](../05-ipc.md)）。
- Context 是協作式能力模型；pipeline 直接使用 JDK 的檔案、網路與資料庫類別不受阻擋，但會被判為 unsafe。預設白名單刻意不含資料庫連線與網路套件，要求這些能力「經由 context」（[ADR-002](ADR-002-context-and-unsafe.md)、[ADR-013](ADR-013-io-sensitive-members.md)）。core 是受信任的葉節點，經 core 契約提供的能力不影響 safe 或 unsafe。
- Context 的檔案操作只接受兩種範圍（pipeline 共享目錄、run 私有目錄）（ADR-009）。
- 機密現有兩種處理：API token 由組態提供（[ADR-012](ADR-012-api-authentication.md)），webhook 密鑰只存雜湊且只顯示一次（[ADR-005](ADR-005-trigger-binding.md)）。兩者都不是「Engine 需要取回明文使用」的機密。
- 資源與 pipeline 定義以名稱鬆散關聯，資料庫不以外鍵連結（[06](../06-data-model.md)）。
- Console 資源頁目前提供：容量與持有量、持有者與等待者、定義、修改容量與啟用、強制釋放；沒有型別、設定、實體狀態與刪除。

## 方案比較

### 一、Engine 如何把資源交給 run

| 選項 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A 提供設定 | Engine 把位址、帳密、路徑交給 pipeline，pipeline 自己連線 | 實作最簡單；pipeline 可用任何函式庫 | 機密進入 pipeline 與其 log；連線上限與並行限制無法強制；pipeline 因直接使用 JDK 網路與資料庫類別而被判 unsafe，與預設白名單的方向相反 |
| B Engine 中介（採用） | Engine 持有實體（檔案路徑、連線池、HTTP 用戶端與金鑰），run 只拿到受控的存取端，操作在 Engine 側執行 | 機密不穿過邊界；上限由 Engine 強制；經 core 契約存取，pipeline 維持 safe；與 ADR-001 後果一致（改子行程時契約可沿用） | core 需新增契約；pipeline 只能使用契約提供的操作；需開發入口的本機實作 |
| C 本機代理 | Engine 在本機開代理埠，run 以 per-run 憑證連代理 | 對子行程模型也成立；pipeline 可用現成函式庫 | 現行同 JVM 模型下沒有必要；多一層網路與憑證管理；pipeline 仍需使用網路類別而被判 unsafe |

結論：採 B。C 只作為日後 run 改為子行程時的實作路徑，契約不變。

### 二、資源型別模型

| 選項 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A 不型別化的設定中心 | 資源是任意鍵值，Engine 只轉交 | 彈性最大 | 等同方案一的 A；Engine 無法驗證實體、無法中介、無法遮罩 |
| B 內建的封閉型別集合（採用） | 每個型別有固定的設定欄位、實體驗證、存取契約與容量語意，由 Engine 內建 | 每個型別的機密、沙箱與可觀測性都可審核；管理員表單可依型別呈現 | 新增型別需要 Engine 發佈 |
| C 外掛式型別 | 第三方以擴充點註冊型別 | 擴充性最高 | 外掛執行在 Engine 信任域，會碰到機密；需要外掛載入、版本與信任模型，超出需求 |

結論：採 B。擴充方式是新增內建型別，不開放外掛。

### 三、OpenAI 相容服務：專用型別或通用 HTTP 型別

| 選項 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A 只做 `openai-compatible`（採用） | 型別理解 OpenAI 相容 API 的請求與回應：固定的端點集合、模型與請求參數的預設與覆寫、串流 | 請求參數可分層管理；pipeline 無法自選路徑與標頭；可依 `usage` 欄位產生 token 指標；攻擊面小 | 只服務這一類 API |
| B 通用 `http-endpoint` | 任意方法、路徑、標頭、本文的受控轉送 | 可涵蓋其他 HTTP 服務 | 管理員要自行約束路徑與標頭；注入金鑰的標頭可被回射；轉送面大，且與 OpenAI 相容的需求沒有直接關係 |
| C 兩者並存 | 同時提供專用與通用 | 涵蓋最廣 | 首版範圍擴大，兩者的重疊部分增加維護 |

結論：首版只做 `openai-compatible`。通用 `http-endpoint` 不納入；有具體的非 OpenAI 相容 HTTP 服務需求時另開 ADR。

### 四、機密的保存

| 選項 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A 環境變數或機密檔參照 | 資料庫只存參照，Engine 使用時才讀取 | 簡單；符合 12-Factor | 每個機密一個環境變數或一個檔案，數量多時不易管理；環境變數需重啟才能更換 |
| B 金鑰庫檔案（採用）：PKCS12 | 所有機密放在一個受密碼保護的金鑰庫檔案，資源以別名參照 | 單一檔案、標準格式、有標準工具管理；Engine 與資料庫都不存明文；可整檔更換與備份；格式本身加密 | 需要保管金鑰庫密碼；寫入需要金鑰庫工具或 Engine 的寫入功能 |
| C 資料庫內加密 | 機密經 API 寫入，Engine 以主金鑰加密後入庫 | 管理員可在 Console 完整自助 | 主金鑰的保管、輪替與遺失處理；密碼學實作與審核成本高；備份含密文 |
| D 明文入庫 | 直接存資料庫 | 最簡單 | 備份與任何資料庫存取者都能取得機密；否決 |

金鑰庫格式比較（B 內部的選擇）：

| 格式 | 能否存任意機密字串 | 評估 |
|---|---|---|
| JKS | 不能：只存私鑰與憑證項目，無法存放任意機密 | 否決。傳統專屬格式，已被 PKCS12 取代 |
| JCEKS | 能（秘密金鑰項目） | 不採用。專屬舊格式，加密強度較弱，不是現行預設 |
| PKCS12（採用） | 能，但經 JDK 的金鑰庫工具匯入密碼項目時只有可列印 ASCII 的字串能原樣往返；非 ASCII 會被破壞且無法還原（實測，見決策 6 的「機密字元集」與「實測結果」） | 現行 JDK 的預設金鑰庫格式，標準格式，現行預設的加密與完整性演算法較強；JDK 內建的金鑰庫工具提供匯入與列出密碼項目的功能 |

結論：採 B，格式為 PKCS12。使用者提議的 JKS 因無法存放任意機密而不適用，PKCS12 滿足同一意圖（單一加密檔案）。A 的參照模型改為「金鑰庫別名」，不再支援環境變數與機密目錄兩種來源；機密提供者保持可替換（同 ADR-012 的原則），日後可加入其他來源。C 為需要自助管理機密時另開 ADR 的方向。

## 決策

### 1. 資源型別

資源由「名稱、型別、容量、啟用旗標、型別專屬設定、機密別名」構成。型別在建立後不可修改（要改型別就刪除重建），名稱不可修改。首版型別為封閉集合：

| 型別 | 對應的實體 | 存取端的語意 |
|---|---|---|
| `counter` | 無實體，只有名稱與容量 | 純互斥或限流，與 ADR-007 現行語意完全相同；不提供存取端 |
| `file` | Engine 主機上的一個檔案 | 對該檔案的受控讀取、寫入、附加；不暴露路徑 |
| `jdbc-pool` | 一個資料庫的連線池 | 受控的 SQL 存取；不暴露連線字串與帳密 |
| `openai-compatible` | 一個 OpenAI 相容 API 服務 | 對固定的 API 端點集合發出請求；金鑰與固定參數由 Engine 注入 |

`counter` 是正式型別而非過渡：它仍適合「保護一個 Engine 不中介的外部系統」。

### 2. 管理與宣告

- 只有管理員可建立、修改、刪除、檢查資源與重載機密（沿用 ADR-012 的角色）；開發人員不能讀取資源設定。
- Pipeline 在 metadata 以「名稱」宣告需要的資源，另可指定期望的「型別」。宣告只含邏輯名稱與型別，不含位址、路徑或機密；管理員更換底層實體不需要重新上傳 jar。
- 只宣告名稱（既有 pipeline）：只取得容量，不取得存取端，語意與現行完全相同，對任何型別的資源皆成立。
- 宣告型別：run 才能取得該資源的存取端。資源的型別與宣告不符時，建立 run 被拒絕（`resources_unavailable` 的 `problem` 新增 `type_mismatch`）。
- 宣告的資源不存在或已停用，沿用現行行為：上傳只產生警告，建立 run 時拒絕。
- 資源宣告仍不影響 safe 或 unsafe 判定（ADR-007）。理由：存取端經 core 契約提供，core 是受信任葉節點，且存取端本身就是受控能力。

### 3. 交給 run 的方式

- 取得時機不變：run 初始化階段，由 Engine 整體取得所有宣告資源的容量（ADR-007）。
- 取得容量成功後，Engine 為每個「宣告了型別」的資源備妥存取端，初始化完成時存取端已可用。Pipeline 程式只能依名稱取用「自己宣告且已持有」的存取端；沒有「執行中取得資源」的操作，ADR-007 與 [WI-09](../work-items/WI-09-shared-resources.md) 的該約束維持。取用已持有的存取端不是取得資源。
- 存取端跨越 class loader 邊界時只使用 JDK 內建型別；機密與實體的 Engine 內部型別不穿過邊界（[05](../05-ipc.md)）。
- 存取端綁定該 run 與取得當下的資源設定。Run 終止時 Engine 回收該 run 的所有存取端與其佔用的實體（連線歸還、進行中請求取消）；管理員強制釋放持有者時，存取端同時失效，之後的操作失敗並註明原因（決定 5）。
- 開發入口提供同契約的本機實作：以本機組態（不連 Engine）提供資源定義，機密由開發人員的本機環境提供。錄製在開發入口記錄「使用了哪個資源與動作類別」，供 metadata 提案產生宣告（[ADR-004](ADR-004-recording.md)）。

### 4. 各型別的行為

**`file`**
- 路徑由管理員設定，且必須落在 Engine 組態指定的資源根目錄之下；任意絕對路徑、跳出根目錄的相對路徑、符號連結解析後跳出根目錄的路徑都被拒絕。資源根目錄不得與 pipeline 共享目錄、run 私有目錄的位置重疊，避免繞過 ADR-009 的範圍。
- Engine 在資源建立、修改與「檢查」時驗證路徑可用：父目錄存在或可建立、可讀寫。Run 初始化階段取得容量後再確認一次，不可用則 run 失敗並註明資源不可用，不進入 pipeline 本體。
- 容量 1 即互斥寫入。容量大於 1 時 Engine 只限制同時持有的 run 數，不提供檔案內容層級的協調；管理員需明白這一點。
- 存取端的操作限於這一個檔案，不能列出或存取同目錄的其他檔案。
- 資源根目錄所在的持久儲存與備份不在本 ADR 範圍，由 container 與部署環境負責（掛載、容量、備份、還原）；Engine 只要求根目錄存在且可讀寫，不符合時「檢查」與初始化失敗。

**`jdbc-pool`**
- 設定欄位分為非機密（主機、埠、資料庫名、使用者名稱、每 run 連線額度、逾時、依資料庫設定檔允許的額外連線屬性）與機密（密碼，只以金鑰庫別名設定）。不接受自由格式的連線字串（見下方「可擴充性」）。
- 容量仍是「同時持有的 run 數」；每個 run 有固定的連線額度（預設 1）。連線池大小由 Engine 推導為「容量 × 每 run 連線額度」，不能獨立設定。因此持有容量的 run 一定拿得到額度，池內不會有等待，ADR-007 的無死結性質得以保留；資料庫端的連線上限由管理員調整容量與額度來對應。
- 連線池由 Engine 持有，在第一次需要時才建立；實體連不上時，使用存取端的操作失敗，不阻擋容量的取得。管理員可用「檢查」主動驗證連線。
- 存取端提供的是 core 定義的窄 SQL 存取（查詢、更新、顯式交易，參數與結果列只用 JDK 的集合與基本型別），不暴露 JDBC 的型別，也不暴露可取出底層驅動物件的途徑。Pipeline 因此不會參照資料庫套件，維持 safe。需要 JDBC 型別的第三方資料存取函式庫不在首版範圍（決定 4）。
- Engine 不解析或限制 SQL；SQL 文字原樣交給資料庫，作者自行撰寫該資料庫的方言。權限由資料庫帳號決定。營運建議使用最小權限的獨立帳號，不使用 Engine 自己的資料庫帳號。

*可擴充性（首階段只有 PostgreSQL，設計可擴充到任何 JDBC 資料庫）*
- **資料庫設定檔：** 每種資料庫在 Engine 內有一份內建的設定檔，資源設定以「資料庫種類」選用。設定檔集中該資料庫的所有差異：驅動、連線位址的組成規則、允許的額外連線屬性清單、輕量健康查詢、錯誤分類（把驅動錯誤對應到統一的錯誤類別）、驅動型別到 JDK 型別的對應。首版只有 PostgreSQL 一份；新增資料庫是新增設定檔，不改資源模型、API 欄位結構與 core 的存取端契約。
- **連線位址：** 由 Engine 依設定檔以結構化欄位（主機、埠、資料庫名）組成，管理員不提供完整連線字串。理由：JDBC 連線屬性中存在可載入類別或寫入檔案的項目（例如指定 socket 工廠、日誌檔），自由格式字串會把它們帶進 Engine 信任域。額外屬性只接受設定檔允許清單內的項目，且不得含機密。
- **方言差異：** 放在設定檔（連線與錯誤層面）與作者自己的 SQL 文字（語法層面）。存取端契約只定義各資料庫共通的型別對照，資料庫特有型別以文字或位元組呈現，不擴充契約。
- **驅動如何提供：** 驅動隨 Engine 發佈，由 Engine 的 class loader 載入，不由 pipeline jar 或管理員上傳（決定 7）。理由：驅動執行在 Engine 信任域並接觸機密，必須與 Engine 一同被鎖定版本、納入可重現建置（[WI-32](../work-items/WI-32-reproducible-release-build.md)）與相依漏洞檢查。因此新增資料庫需要發佈新版 Engine。放置驅動 jar 的目錄於啟動時載入（免重新建置）列為日後另開 ADR 的選項，須同時決定信任與供應鏈。
- **與沙箱和相依的關係：** Pipeline 不參照驅動，驅動也不在 run 的 class loader 內，因此不增加 pipeline 的相依與靜態分析負擔。Pipeline jar 內夾帶的驅動不會被存取端使用，也不影響存取端的行為；若 pipeline 自己載入並使用它，屬直接使用 JDK 的 unsafe 行為。

**`openai-compatible`**
- **由資源設定固定、pipeline 不能覆寫：** 根位址（只允許 `http` 或 `https`，不含使用者資訊）、API 金鑰（機密，選填，以金鑰庫別名設定，本機服務可能不需要）、organization 與 project 這類選填識別（作為標頭送出，非機密）、管理員指定的額外標頭（非機密，不得是授權相關標頭；機密不放在額外標頭）、可用的 API 端點集合、並行與逾時上限、每 run 同時請求數上限。
- **由資源設定預設、pipeline 呼叫時可覆寫：** 模型、取樣與長度相關的請求參數（例如 temperature、top_p、max_tokens、stop、seed、回應格式等）。合併規則：資源預設在先，pipeline 在呼叫時提供的值覆蓋同名項目；請求本文其餘部分（訊息、工具定義等）完全由 pipeline 提供。
- **管理員對覆寫的限制（選填）：** 允許的模型清單（空代表不限）、各參數可標為「鎖定」（pipeline 不能覆寫）、數值型參數的上限（例如 max_tokens 的天花板）。逾時方面 pipeline 只能縮短，不能超過資源設定的上限。
- **Engine 負責：** 路徑固定在端點集合內，pipeline 不能指定任意路徑或主機；注入金鑰與識別標頭；不跟隨離開根位址的重新導向；回傳給 pipeline 的回應標頭剝除授權相關者；`stream` 由本型別管理（見下）。Engine 不自動重試，錯誤（含 429 與 5xx）以類別回傳，是否重試由 pipeline 決定（與「Engine 不自動重跑」一致）。
- **容量：** 容量是「同時持有的 run 數」，每個 run 同時進行的請求數受上限約束，因此端點的實際並行請求不會超過「容量 × 每 run 上限」（決定 6）。
- **串流回應（支援，分兩步交付，決定 8）：** pipeline 是循序阻塞的平台 thread（ADR-008），以「逐塊拉取」的方式消費串流是自然的，且不需要讓 Engine 內部的非同步型別穿過邊界；長時間生成也需要串流來避免整體逾時過短。首步先交付一次完整回傳，且存取端契約預留串流；第二步加入串流。串流的規則：串流佔用請求額度直到串流結束、被 pipeline 關閉或 run 終止；以「兩塊之間的閒置逾時」取代整體逾時；run 取消時關閉串流；回傳的每一塊只含 JDK 內建型別；token 用量取自串流結尾的用量欄位（若服務有提供）。
- **相容性的限度：** 「OpenAI 相容」的範圍由端點集合與請求參數的傳遞定義；Engine 不驗證服務端是否支援某個參數，不支援的錯誤由服務端回報並以類別回傳。
- Pipeline 經此型別連到服務時，不需要在 metadata 的 `network` 宣告其主機，也不使 `network` 變成不限制。`network` 清單與資源的位址是兩套獨立機制，互不隱含（見第 7 點）。

### 5. 容量與實體的關係

- 容量一律是「同時持有此資源的 run 數」，持有從初始化階段到 run 終止，與 ADR-007 相同；本 ADR 不引入請求級或交易級的取得與釋放。
- 實體層級的上限由容量與型別的額度推導（連線池大小、同時請求數），不獨立設定，使實體永遠不會超出容量所代表的承諾。
- 降低容量不收回持有者的資源（ADR-007）。修改設定或機密被重載時，已持有者繼續使用其取得當下的設定與機密（連線池與用戶端的舊世代待持有者全部結束後關閉）；新設定只對之後取得的 run 生效。停用資源使等待者失敗，不影響持有者。

### 6. 機密：PKCS12 金鑰庫

- **保存：** 所有機密放在一個 PKCS12 金鑰庫檔案，每個機密一個別名。資源設定只存別名；機密值不進入資料庫、metadata、effective metadata、run 紀錄、事件、log、trace、錯誤回應，也不穿過 Engine 與 run 的邊界。別名比對不分大小寫（金鑰庫工具會將別名轉為小寫），Engine 一律正規化。
- **金鑰庫位置與密碼的提供：** 金鑰庫檔案路徑與金鑰庫密碼由 Engine 的組態提供（12-Factor）。密碼的來源是環境變數，或由組態指定的密碼檔路徑；密碼檔為部署平台的機密檔（Docker secret、systemd 的憑證機制）時為建議做法，因為環境變數易被子行程與診斷輸出帶出（決定 9）。密碼不寫入版本庫、資料庫或映像檔。
- **寫入者：** 首階段只有維運在部署時以 JDK 的金鑰庫工具管理金鑰庫（新增、刪除別名；更新是先刪後建），Engine 以唯讀方式開啟，管理 API 與 Console 不接受機密值，只接受別名（決定 2）。理由：機密值不經過 HTTP 請求本文、反向代理與請求 log；Engine 不需要金鑰庫的寫入權限與並行寫入處理；符合 ADR-012「憑證由部署層提供」的原則。由管理員經 API 寫入金鑰庫是日後另開 ADR 的選項。
- **機密字元集：** 機密項目（字串機密，例如資料庫密碼、API 金鑰）的值限可列印 ASCII；此限制只針對機密項目，憑證與私鑰是二進位結構，不受影響（含空白與各種符號，長度實測 700 字元可原樣往返）。理由：金鑰庫工具匯入密碼項目時經 JDK 的 PBE 編碼，非 ASCII 字元（連單一 é）會被破壞且無法還原，純 Java API 同樣如此（實測依據見下方「實測結果」）。需要非 ASCII 機密的服務端憑證（例如含非 ASCII 的密碼）不在本版範圍，維運須改用 ASCII 憑證。日後若需要，採混合方案：由 Engine 自帶的維護工具把機密以 UTF-8 位元組寫成通用密鑰型項目，Engine 同時讀取兩種項目；列為日後擴充，不在本次範圍（另開 ADR）。
- **載入與重載：** Engine 啟動時載入金鑰庫並保存在記憶體；若組態指定了金鑰庫但無法開啟（檔案缺失、密碼錯誤、格式不符、檔案毀損），啟動失敗，原因只含類別（失敗類別的對應見 [WI-41](../work-items/WI-41-keystore-secrets.md)）。格式不符須由 Engine 明確檢查，不得依賴 JDK 在 `keystore.type.compat` 預設下的相容行為（該設定使要求 PKCS12 的讀取可能也接受 JKS 檔；其實際行為由 WI-41 實測確認）。載入時能偵測的問題一律明確拒絕：非金鑰庫格式的檔案、不支援的項目類型（支援：機密項目、受信任憑證項目、私鑰項目，見決策 12）、機密項目內容含非可列印 ASCII 字元者（視為已損毀或違反字元集，不使用且不輸出值；在機密清單與資源狀態中呈現為別名狀態 `invalid_secret`，見決定 11）。**不可偵測的損毀**（例如非 ASCII 字元被破壞後恰好落在可列印範圍）無法在載入時辨識，以「連線時認證失敗」呈現；維運手冊須明言這一點。未指定金鑰庫時，Engine 可啟動，但引用別名的資源之「檢查」與使用都失敗。管理員可用重載端點在不重啟下重新讀取檔案；重載是整體的：失敗時維持原記憶體內容。重載後，別名內容有變的資源，其之後被取得的 run 使用新機密（新世代）；進行中的 run 不受影響。不採用檔案變動時自動重載，使生效時點可預期並有稽核紀錄。
- **輪替：** 更新機密是「刪除別名、重新匯入別名」：工具對既有別名的匯入會失敗，必須先刪除。維運在金鑰庫檔案的副本上操作，完成後以原子替換（複製、修改副本、更名覆蓋）取代原檔，再由管理員觸發重載。工具會把別名轉為小寫，Engine 以 `Locale.ROOT` 的小寫正規化對應。維運手冊以密碼檔參數提供金鑰庫密碼，避免密碼出現在命令列與行程清單。可選（不阻擋）：以提高金鑰庫的 PBE 迭代次數強化離線破解成本，見「實測結果」。金鑰庫密碼的輪替需要同時更新密碼來源並重啟 Engine。
- **遮罩：** API 與 Console 永遠不回傳機密值。資源回傳別名與狀態（`未設定`、`已找到`、`找不到`、`機密無效`〔`invalid_secret`，別名存在但值含非可列印 ASCII，不使用〕）；機密清單只列別名與引用它的資源，不列值，也不列項目內容。
- **錯誤與 log：** 回傳給 pipeline 與寫入 run log 的實體錯誤訊息只含錯誤類別（例如連線失敗、逾時、被拒絕），不含連線字串與驅動訊息原文；原文與例外寫入 Engine log，以 `errorId` 對應（沿用 08-api「未預期的伺服器錯誤」做法）。Engine 的 log 與 trace 同樣不寫入機密。另對已知機密值做字串比對遮蔽，作為最後一道防線；這是盡力而為，不能代替上述「不傳遞」原則。
- **備份：** 金鑰庫檔案是部署的組態產物，由維運與資料庫備份分開保管，金鑰庫密碼再與金鑰庫檔案分開保管。在沒有金鑰庫的環境還原資料庫時，引用別名的資源「檢查」會回報找不到。
- **部署掛載（行為層級，檔案由 tdd-coder 另行撰寫）：** Docker 以唯讀方式掛入金鑰庫檔案，並以 Docker secret 提供密碼；systemd 把金鑰庫放在僅服務帳號可讀的組態位置，密碼以 systemd 的憑證機制或僅服務帳號可讀的環境檔提供。Engine 發現金鑰庫檔案對其他使用者可讀時記錄警告。金鑰庫檔案的位置不得在資源根目錄、pipeline 共享目錄與 run 私有目錄之下。
- **限度：** 機密在 Engine 行程記憶體中以明文存在；同一 JVM 內的 unsafe pipeline 可讀取行程環境與記憶體，因此能取得由環境變數提供的金鑰庫密碼。這是協作式模型的既有限度（ADR-002）；同 JVM 內無法補強，唯一的緩解是對 unsafe pipeline 的授權保持審慎（[ADR-006](ADR-006-unsafe-policy.md)）。HTTP 回應本文若回射了金鑰，Engine 不處理本文；資料庫查詢可以讀出資料庫中的任何資料，由資料庫帳號權限約束。

#### 實測結果（JDK 25.0.4.1，2026-10-07）

| 項目 | 結果 |
|---|---|
| ASCII 機密往返 | 以工具匯入密碼項目的 ASCII 機密（含空白、各種符號、700 字元）讀回後逐字相同 |
| 非 ASCII 機密 | 連單一 é 都被 JDK 的 PBE 編碼破壞且無法還原；純 Java API 寫入同樣如此。決定：機密限可列印 ASCII |
| 更新 | 匯入既有別名會失敗；須先刪除再匯入 |
| 別名大小寫 | 工具將別名轉為小寫；Engine 以 `Locale.ROOT` 小寫正規化 |
| 開檔失敗型態 | 密碼錯誤為 I/O 例外，訊息為完整性檢查失敗；檔案截斷或垃圾檔為檔案結尾例外。兩者可區分，但密碼錯誤的辨識依賴例外訊息文字，JDK 升級時須重新驗證 |
| 列出指令 | 列出、詳細與 RFC 輸出都不顯示機密值 |
| 預設保護 | PKCS12 預設為 PBEWithHmacSHA256AndAES_256、10000 次迭代。實際解出並確認的只有檔案中的 MAC 參數；機密項目的加密演算法來自 JDK 文件，未直接解出 |
| `keystore.type.compat`（WI-41 實測，JDK 25.0.4.1，2026-10-07） | 預設為開時，要求 PKCS12 的讀取**會**開啟 JKS 檔（回報的類型仍是 PKCS12）；JCEKS 檔不論設定都無法以 PKCS12 讀取；設定為關閉時 JKS 與 JCEKS 都被拒絕。決定：Engine 自行檢查檔頭，PKCS12 以 DER 序列（位元組 0x30）開頭，JKS 與 JCEKS 有各自的魔術數字，不是 PKCS12 者在載入前以「格式不符」拒絕，結果與該設定無關；測試鎖定該設定開啟與關閉下的行為，以及 JDK 本身的相容行為（JDK 升級時重新驗證） |
| 開檔失敗的辨識（WI-41 實測） | 密碼錯誤：I/O 例外，其原因為 `UnrecoverableKeyException`（完整性檢查失敗），Engine 依原因的型別辨識，不依訊息文字；檔案截斷與空檔：檔案結尾例外（空檔也歸為檔案毀損）；垃圾檔：依內容不同可能是檔案結尾例外或 DER 長度錯誤，因此由檔頭檢查判為格式不符；其餘例外歸入「無法開啟」。JDK 升級時須重新驗證 |

可選強化（不阻擋）：提高金鑰庫建立時的迭代次數（`java.security` 的 PKCS12 迭代次數屬性，建立與更新金鑰庫的工具側設定），降低離線暴力破解速度；對讀取端無影響。是否採用由維運決定，WI-42 的維運手冊列為選用步驟並須實測。

### 7. 靜態分析、白名單與沙箱

- 白名單與 unsafe 判定不需要調整：存取端都在 core 契約內。需要調整的是文件的措辭：「資源鎖是約定式、不綁定實際網路動作」（ADR-007、[07](../07-nfr-risks.md)）只對 `counter` 型別仍然成立；對其他三種型別，safe 的 pipeline 除經存取端外沒有其他途徑接觸該實體，限制因此是強制的。
- Unsafe 的 pipeline 仍可直接使用 JDK 連到同一個實體，繞過容量與中介；這是協作式模型的既有限度。資料庫密碼與 API 金鑰不會因此外洩（pipeline 沒有拿到它們），但容量與並行限制可被繞過。
- `network` 宣告的主機若與某個 `openai-compatible` 或 `jdbc-pool` 的主機相同，Engine 在上傳時對該 pipeline 產生警告（不影響判定），提示應改走資源。管理員在資源設定的位址是管理員的信任決定，不受 pipeline 的 `network` 清單約束。
- 管理員可把資源位址指向 Engine 所在網路的內部服務，這是管理員信任範圍內的設定；Engine 限制的是 pipeline 側（不能自選主機與路徑）。

### 8. 生命週期與 API

資源的修改與檢查沿用 `PATCH`，新增刪除與檢查端點，並新增機密的唯讀清單與重載端點。完整契約在各工作項實作時併入 [08-api](../08-api.md)，本節只定行為。

| 端點 | 行為 |
|---|---|
| `POST /api/v1/resources` | 建立資源。本文新增 `type` 與型別專屬設定與 `secretAlias`；省略 `type` 視為 `counter`，使既有呼叫方式維持有效。422 `invalid_resource` 的 `problem` 擴充：型別不明、設定欄位缺漏或不合規、資料庫種類不支援、連線屬性不在允許清單、路徑不在資源根目錄內、機密別名不合規、請求參數預設不合規 |
| `GET /api/v1/resources`、`GET /api/v1/resources/{name}` | 回傳新增 `type`、非機密設定、`secretAlias` 與機密狀態、最近一次實體檢查結果與時間、宣告了這個資源的 pipeline 定義（含數量）。不含機密值 |
| `PATCH /api/v1/resources/{name}` | 可修改容量、啟用、型別專屬的非機密設定、機密別名。型別與名稱不可改。對持有者的影響見第 5 點 |
| `DELETE /api/v1/resources/{name}` | 新增，管理員專用。204 成功；404 `resource_not_found`；409 `resource_in_use`：目前有持有者或等待者（需等待結束、先停用，或強制釋放持有者）。沒有持有者與等待者時可以刪除，即使仍有 pipeline 定義或 trigger 宣告了它：之後這些 pipeline 的建立 run 被拒絕為 `unknown`，與「資源尚未定義」的現行語意一致。接受 `preview=true`（沿用白名單的預覽慣例）：回應 200，說明會受影響的定義與 trigger 數，不改變任何東西 |
| `POST /api/v1/resources/{name}/check` | 新增，管理員專用。主動驗證實體（檔案路徑可用、資料庫連得上並完成健康查詢、服務端點可連）與機密別名是否存在，回應 200，本文含 `ok` 與失敗類別，不含原因細節；結果記錄為最近一次檢查。不取得容量，不影響進行中的 run |
| `GET /api/v1/secrets` | 新增，管理員專用。列出金鑰庫的別名、各別名被哪些資源引用；不含值。409 `secret_store_not_configured`：Engine 未組態金鑰庫 |
| `POST /api/v1/secrets/reload` | 新增，管理員專用。重新讀取金鑰庫（見第 6 點）。200 回傳別名數與「有變更的別名被哪些資源引用」，不含值；409 `secret_store_not_configured`；422 `secret_store_unreadable`（無法開啟，記憶體內容維持原狀） |
| 強制釋放 | 端點不變；語意補充：對有存取端的型別，該持有者的存取端同時失效（見第 3 點） |

刪除會一併清除該資源的設定與其連線池與用戶端世代；`file` 型別的刪除不刪除實際檔案；機密別名與金鑰庫不受影響。變更者記錄為 token 對應的名稱。

### 9. 與 ADR-007 的相容與遷移

- 既有資源全部成為 `counter` 型別，容量、啟用、持有與等待語意不變。
- 既有 pipeline 的名稱宣告維持有效且語意不變；已上傳的 jar 不需重新上傳。需要存取端的新 pipeline 才使用型別宣告。
- 既有的呼叫方式（只送名稱與容量）維持有效；回應多出的欄位是向後相容的新增。
- ADR-007 的整體取得、先進先出、等待逾時、取消、終止時釋放、不持久化、重啟時全部中斷等決策不變。ADR-007、ADR-009、05、06、07 的相關描述已隨本 ADR 修訂；08 隨各工作項實作同步修訂：路由與錯誤碼受 `ApiDocumentationTest` 約束，必須與實作同時變更，因此每個新增或變更端點的工作項在實作時更新 08，不預先列出尚未實作的路由。

### 10. 可觀測性

- Metric：沿用資源的等待時間、持有時間、佇列長度，並加上型別標籤（標籤只用資源名稱與型別，不放 SQL、路徑、網址或模型的使用者輸入）。另依型別：`jdbc-pool` 的使用中連線數、取得失敗數、查詢耗時；`openai-compatible` 的進行中請求數、依狀態類別的請求數與延遲、以及服務回報的 token 用量（若有）；`file` 的操作數與路徑檢查失敗數；所有型別的實體檢查結果；機密重載的次數與結果。
- Log：run 的 log 記錄資源的取得、存取端失效與實體錯誤類別；不記錄 SQL 參數、請求與回應本文、機密。
- Trace：run 的 trace 之下，每次資源操作一個 span，只記錄資源名稱、型別與操作類別；SQL 文字、提示內容與網址的查詢字串預設不記錄。
- 稽核：資源的建立、修改、刪除、檢查、強制釋放與機密重載都記錄管理員名稱。

### 11. Console

資源頁（現行：[ResourcesPage](../../../../console/src/pages/ResourcesPage.svelte)、[ResourceFormDialog](../../../../console/src/admin/ResourceFormDialog.svelte)）的調整，行為層級：

- 建立表單先選型別，再依型別顯示欄位：`counter`（名稱、容量）；`file`（資源根目錄下的路徑、容量）；`jdbc-pool`（資料庫種類、主機、埠、資料庫名、使用者名稱、機密別名、額外連線屬性、每 run 連線額度、逾時、容量）；`openai-compatible`（根位址、機密別名、organization 與 project、額外標頭、預設模型與允許的模型清單、請求參數預設與是否鎖定與上限、逾時、每 run 同時請求數、容量）。表單不收機密值，機密別名以「金鑰庫現有別名」供選擇。名稱與型別建立後唯讀。
- 資源卡片顯示型別標籤、非機密設定摘要、機密別名與狀態（未設定、已找到、找不到、機密無效）、最近一次實體檢查的結果與時間、型別專屬的使用量（連線使用中數、進行中請求數），並保留現行的容量、持有者、等待者。
- 新增「檢查」與「刪除」動作。刪除沿用確認對話框：先以預覽顯示會受影響的 pipeline 與 trigger 數；若回應 `resource_in_use`，說明原因並引導停用或強制釋放。
- 新增機密檢視（置於資源頁內，由 [WI-49](../work-items/WI-49-console-resources-page-rework.md) 實作）：列出別名與引用者，提供「重載」動作與結果；說明新增或更換機密需要維運以金鑰庫工具操作。

### 12. 憑證：信任錨與 mTLS 用戶端憑證（補充決定）

金鑰庫除機密項目外，也存放兩種憑證項目：受信任憑證項目（用途一：信任內網自簽或內部 CA 的伺服器憑證，例如 HTTPS 的 OpenAI 相容服務、PostgreSQL 的 TLS）與私鑰項目（用途二：mTLS 用戶端的私鑰與憑證鏈）。範圍較大，實作拆為獨立工作項 [WI-52](../work-items/WI-52-tls-trust-and-mtls.md)；WI-41 只負責載入並辨識三種項目類型。

- **資源參照：** `openai-compatible`（根位址為 `https` 時）與 `jdbc-pool` 的設定各增兩個選填欄位：`trustAliases`（受信任憑證項目的別名，可多個）與 `clientCertAlias`（私鑰項目的別名，單一）。與既有 `secretAlias`（機密項目）共用同一個別名命名空間，以項目類型區分；別名指向的項目類型不符時，設定被拒絕（`invalid_resource` 的 `problem` 新增「別名類型不符」），檢查也回報同一類別。別名狀態沿用 `not_set`、`found`、`missing`、`invalid_secret`，另增 `wrong_type`（別名存在但類型不符，例如 `trustAliases` 指向機密項目）。
- **私鑰的保護密碼：** 與金鑰庫密碼相同。理由：JDK 的 PKCS12 實作對私鑰項目使用金鑰庫密碼保護，沒有獨立的金鑰密碼（以工具建立時分開指定的金鑰密碼會被忽略或警告；此行為待實測確認）。限度：取得金鑰庫密碼即取得所有私鑰，與機密項目的保管模型一致，沒有額外保護層。ASCII 限制不適用於私鑰與憑證；金鑰庫密碼本身是否限 ASCII 待實測（見待確認問題），在確認前建議使用可列印 ASCII。
- **信任模型：** 設定了 `trustAliases` 時，該資源的連線「只信任指定的憑證」，取代 JVM 預設信任（等同固定信任錨）；未設定時使用 JVM 預設信任。理由：管理員明確列出信任對象時，期望的語意就是「只信這些」，公開 CA 不應能冒充內部服務；要同時信任公開 CA，管理員把該 CA 憑證也匯入金鑰庫並列入。代價：服務端改用別的 CA 時須更新金鑰庫並重載。信任設定只作用於該資源的連線，不修改 JVM 全域預設的安全上下文。
- **主機名稱驗證不可關閉：** 沒有任何設定欄位、連線屬性或全域旗標可以關閉主機名稱驗證或憑證驗證；`jdbc-pool` 的 TLS 以驗證主機名稱的模式固定在資料庫設定檔，管理員不能選擇較弱的模式。內部服務若憑證主旨與連線主機不符，須由維運重發憑證。
- **邊界：** 私鑰、憑證與由它們建立的安全上下文只在 Engine 內使用，由 Engine 代理連線；存取端不回傳也不接受它們，pipeline 取不到。API、Console、log、trace 對憑證只出現別名、主旨、到期日與 SHA-256 指紋，絕不出現私鑰、私鑰的任何衍生資料或金鑰庫密碼。
- **到期可觀測性：** 檢查端點對資源所參照的每個憑證回報主旨、到期日、剩餘天數與指紋；剩餘天數低於警告門檻（Engine 組態，預設 30 天）時回報警告，已過期則檢查失敗（類別為憑證已過期）。另有各憑證別名剩餘天數的 metric。
- **輪替與重載：** 沿用整體重載與新世代語意：重載後內容（以指紋判斷）有變的憑證別名，其引用資源之後被取得的 run 使用新的信任與用戶端憑證，進行中的 run 不受影響；重載回應列出有變更的別名與引用者，不含任何憑證以外的內容。
- **實作路徑與風險（待實測，細節與驗收在 WI-52）：** HTTP 用戶端：由受信任憑證與私鑰項目建立安全上下文交給 Engine 使用的 HTTP 用戶端，須實測主機名稱驗證預設為開啟、不被 JDK 的系統屬性關閉。`jdbc-pool`：PostgreSQL 驅動以「socket 工廠類別名稱」接收 TLS 設定，無法直接傳入安全上下文物件；方案一為 Engine 內建的工廠類別，依連線池身分取得該池的安全上下文（類別名稱由資料庫設定檔固定，不接受管理員提供，與「不接受 socket 工廠屬性」的規則相容）；方案二為把憑證與私鑰寫成暫存檔再交給驅動的檔案型屬性，因私鑰落地而否決。推薦方案一，驅動版本與工廠的相容性、主機名稱驗證是否生效、以及連線池重建的世代切換均待實測。

## 取捨

| 項目 | 得到 | 失去 |
|---|---|---|
| Engine 中介（方案 B） | 機密不外洩；上限由 Engine 強制；safe 的 pipeline 無法繞過 | pipeline 表達力受限於契約；core 契約與開發入口實作量增加 |
| 封閉型別集合 | 每個型別可審核；表單與可觀測性明確 | 新型別與新資料庫需要發佈 Engine |
| 只做 `openai-compatible`，不做通用 HTTP | 請求參數可分層管理，攻擊面小 | 非 OpenAI 相容的 HTTP 服務暫時無法經資源使用 |
| PKCS12 金鑰庫，維運以工具管理 | 單一加密檔案、標準格式；API 與資料庫不接觸機密值；不需要密碼學實作 | 新增或輪替機密需要維運操作與重載；需要保管金鑰庫密碼；機密限可列印 ASCII；非 ASCII 損毀有一部分無法在載入時偵測 |
| 驅動隨 Engine 發佈、設定檔集中資料庫差異 | 驅動可鎖定版本與稽核；新增資料庫不改契約 | 新增資料庫需要發佈 Engine |
| 容量維持 run 級（整個 run 持有） | 無死結；語意與 ADR-007 一致；連線池大小可推導 | 對 run 只偶爾呼叫模型的使用，吞吐低於請求級限流 |
| 連線池大小由容量與額度推導 | 池內沒有等待，保留無死結性質 | 管理員不能單獨調大池而不調容量 |
| 窄 SQL 存取而非 JDBC 型別 | pipeline 保持 safe；機密與驅動物件不外洩 | 不能直接使用需要 JDBC 型別的函式庫 |
| 刪除允許仍被宣告的資源 | 管理員不被 pipeline 的宣告綁住 | 之後相關 pipeline 的 run 被拒絕；以預覽與 trigger 數降低意外 |

## 後果

- 共享資源從「純計數」變成「有實體對應、由 Engine 中介」的概念；`counter` 型別保留原有語意。
- 需要新增或修改：資料模型（資源型別、設定、機密別名、檢查結果）、API 契約（08-api 與 `ApiDocumentationTest` 所列路由與錯誤碼）、core 的宣告契約與存取端契約、開發入口的本機實作、Engine 組態（金鑰庫路徑與密碼來源、資源根目錄）、部署文件與部署檔（金鑰庫掛載）、Console 資源頁、文件（05、06、07、08、ADR-007 與 ADR-009 的相關描述）。工作項見文末。
- 資源狀態與連線池仍在 Engine 記憶體，沿用單實例限制；多實例前，容量需改為共享儲存，連線池與額度需跨實例分配，金鑰庫需在每個實例提供（[07](../07-nfr-risks.md)）。
- 新增的風險（已併入 07）：
  - 管理員設定的位址可指向內部服務：只有管理員能設定，pipeline 側不能自選主機與路徑，不跟隨離開根位址的重新導向。
  - 檔案路徑穿越與別名：限定資源根目錄，解析符號連結，不與 ADR-009 的目錄重疊。
  - 機密經錯誤訊息或回應回射外洩：錯誤只給類別、剝除授權標頭、字串遮蔽為最後防線，HTTP 本文回射為接受的限度。
  - 金鑰庫與其密碼的保管：金鑰庫檔案與密碼分開保管，檔案權限僅服務帳號，備份與還原由維運負責；密碼來源為環境變數時 unsafe pipeline 可讀取。
  - 機密字元集與不可偵測的損毀：機密限可列印 ASCII；載入時能辨識的違規明確拒絕，辨識不到的損毀呈現為連線時認證失敗，維運手冊明言並要求更新後以「檢查」驗證。
  - 連線與請求在卡住的 run 手上占用：強制釋放使存取端失效並回收實體。
  - 資料庫帳號權限過大：Engine 不解析 SQL，以最小權限帳號作為營運要求。
  - 連線屬性注入：只接受資料庫設定檔允許清單內的屬性，不接受自由格式連線字串。
  - 模型服務長時間生成占用容量過久：run 級持有的既有取捨；以持有時間 metric 觀察，必要時另開 ADR 引入請求級限流。
  - 開發入口與 Engine 的行為差異：兩者共用同一份契約，並以同一組行為驗收條件驗證。
- 日後需要非 ASCII 機密時，採混合方案（Engine 自帶維護工具寫入、同時讀取兩種項目），另開 ADR。
- 日後需要自助管理機密（經 API 寫入金鑰庫或資料庫加密）、請求級限流、JDBC 型別暴露、放置驅動 jar 載入、通用 HTTP 型別、更多型別或外掛時，各自另開 ADR。
