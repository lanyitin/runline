# 3 架構方案比較與推薦

狀態：已核可（2026-10-11）。本文回答：webhook 檔名、檔案存取、VAD 執行、階段形態各有哪些選項，為何如此推薦。

## 3.1 webhook 帶檔名

| 方案 | 優點 | 缺點 |
|---|---|---|
| A 每個檔案一個 trigger | 不改 Engine | 每檔都要管理員操作，不可用 |
| B 呼叫端提供的參數（採用） | 符合需求；密鑰驗證先於讀本文，限定於 trigger 明列的參數 | 改 Engine 與文件 |
| C 掃描收件目錄 | 不改 Engine | 失去「帶檔名」語意，須處理寫入未完成與重複處理 |

結論：B（使用者已選定）。

## 3.2 檔案存取

| 方案 | 優點 | 缺點 |
|---|---|---|
| 部署設定指定收件根目錄，pipeline 自行檢查相對路徑（採用） | 不新增資源型別；根目錄不受手動 run 的參數影響 | 路徑檢查由 pipeline 負責，須嚴格測試 |
| 新增 `directory` 資源型別 | 由 Engine 強制範圍 | ADR-019 的型別集合是封閉的，成本高 |
| 把根目錄當 pipeline 參數 | 簡單 | 開發人員手動 run 可指向任意目錄，擴大讀取範圍 |

結論：第一項（使用者已選定「管理員指定收件根目錄」）。

## 3.3 VAD 的執行位置

| 方案 | 優點 | 缺點 |
|---|---|---|
| A 主機上的 Python 命令列工具 | 官方 silero-vad，行為與社群一致 | 主機需 Python 與 torch 或 ONNX；多一個語言與安裝項 |
| B ONNX Runtime 放進 pipeline jar | 單一 jar | 每個 run 有獨立 class loader，而原生程式庫在同一 JVM 只能被一個 class loader 載入，第二個 run 可能載入失敗；jar 含原生程式庫，可能超過上傳預設的 50 MiB；需第三方函式庫與白名單條目（ADR-022 的「薄 jar」原則被破壞） |
| C 獨立的 JVM 小工具，ONNX Runtime 在它自己的行程內，pipeline 以子行程呼叫（採用，使用者已選定） | 主機不需 Python；pipeline 維持薄 jar；原生程式庫與 class loader 問題不存在；工具可單獨測試與升級 | 多一個要安裝的 jar（主機已有 JRE）；JVM 啟動約一秒，故工具一次呼叫處理整個檔案 |
| D 獨立 HTTP 服務 | pipeline 可回到 safe | 多一個長駐元件；本案仍需 unsafe 讀收件目錄，收益小 |

結論：C。工具只負責「模型推論」，輸出整個 WAV 每一個固定長度視窗的語音機率；門檻、最小靜音、最小語音長度等判定邏輯在 pipeline 內以 JDK 實作。VAD-A 與 VAD-B 因此是同一份機率的兩組判定參數，調參不需重跑模型。代價是判定邏輯（對應官方的語音區間偵測規則）須在 pipeline 重現，以官方 Python 實作對同一音訊產出的結果作為驗收基準。

## 3.4 階段形態

| 方案 | 優點 | 缺點 |
|---|---|---|
| 一個 pipeline、階段循序、每階段結果寫入資料庫（採用） | 單一部署單元；Lemonade 一次只載一個模型家族；結果可查 | 單次 run 很長 |
| 每階段一個 pipeline，以事件串接 | 可單獨重跑 | 平台沒有 pipeline 間事件；過度設計 |

結論：第一項；階段依模型分批（先全部轉錄，再全部 gemma4）以減少模型切換。
