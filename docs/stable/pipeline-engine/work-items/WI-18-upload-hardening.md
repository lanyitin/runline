# WI-18 上傳與服務端的安全補強

本文回答：WI-06、WI-08 完成後，上傳與服務端還有哪些安全與營運缺口需要補強。狀態：已核可（2026-10-04）。相依：WI-06、WI-08。

## 背景

[WI-06](WI-06-upload-and-discovery.md) 以上傳大小上限、分析的類別數與時間上限防護上傳，下列缺口未涵蓋：

| 缺口 | 風險 |
|---|---|
| 壓縮檔解壓後的大小沒有上限 | 小型惡意 jar 解壓後耗盡記憶體或磁碟（解壓炸彈） |
| pipeline 名稱沒有在上傳時驗證 | 目錄名稱只允許字母、數字、`.`、`_`、`-`；名稱含其他字元的 pipeline 可成功上傳，卻在 run 的初始化階段失敗 |
| 伺服器錯誤回應輸出例外的內部原因 | 洩漏內部資訊 |
| 遙測的服務名稱沿用範本值 | 追蹤與指標無法正確歸屬 |
| 上傳、查詢、刪除與 run 相關 API 未出現在 API 文件 | 使用者無從得知契約 |
| 優雅關閉時進行中請求與連線的處置沒有專門驗證 | 進行中的請求在關閉時是否完成、連線是否釋放，未被保證 |

## 行為與驗收條件

- 上傳時對 jar 的解壓後總大小、單一項目大小與項目數量設有上限；超過任一上限即拒絕上傳，回傳可理解的錯誤並指出被超過的是哪一項，且不留下任何資料。上限由組態決定並有合理預設。分析與探索過程在超過上限前停止，不展開超量資料。
- 以真實編譯並壓縮出的高壓縮比 jar 驗證上述防護確實觸發，且正常大小的 jar 不受影響。
- 上傳時驗證 pipeline 名稱：不符合目錄名稱規則的名稱被拒絕，錯誤指出是哪個 pipeline 與允許的字元範圍，且不留下任何資料；同一 jar 中任一 pipeline 不合規即整個上傳被拒絕。
- 伺服器端未預期的錯誤，對呼叫端只回傳一般性的錯誤訊息與可供查找的識別碼，不含例外的內部原因、堆疊或設定值；完整原因寫入 log。既有的錯誤語意（認證、權限、驗證失敗）不變。
- 遙測的服務名稱反映本專案（Engine），並可由組態設定；log、trace、metric 皆使用同一名稱。
- API 文件涵蓋上傳、查詢、刪除，以及 run 的建立、取消、查詢、log 查詢與串流、unsafe 設定等 API：誰能呼叫（角色）、傳入什麼、回傳什麼、錯誤代碼與語意，並標示需要 Bearer token。
- 優雅關閉有自動化驗證，涵蓋 WI-08 尚未驗證的部分：收到終止訊號後，進行中的 HTTP 請求在寬限時間內完成、不再接受新請求、資料庫連線被釋放，程序在寬限時間內結束。進行中 run 的處置（標記為中斷）已由 WI-08 驗證，不重複。
- 建置、全部既有測試（含打包形態的測試）在 JDK 25 下通過，`ktfmtCheck` 通過；既有測試數量不減少。

## 架構約束

- 只修改 engine 模組；core、runner、analyzer、devkit 不受影響。
- 不改變既有 API 的成功行為與認證、權限語意（[ADR-012](../adr/ADR-012-api-authentication.md)）。
- 上限與服務名稱由環境變數提供，符合 12-Factor；token 與機密不得出現在 log、trace 或錯誤訊息中。
- 測試使用真實 PostgreSQL（Testcontainers）與真實編譯的 jar，不使用 Stub 或 Mock。
- 不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
