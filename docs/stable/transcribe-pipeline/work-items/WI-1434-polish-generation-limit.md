# WI-1434 潤飾階段的生成量上限

本文回答：潤飾呼叫出現與摘要相同的失控生成時，如何限制。狀態：已核可（2026-10-13）。補充 [WI-1432](WI-1432-arr-run-findings.md)（該項只對摘要加 token 上限）。相依：WI-1432。儲存庫：T（runline-transcribe）。

## 觀察（事實）

arr 的 VAD 0.3 實驗 run（`8e58e505`，部署的 jar 尚無 WI-1432）中，潤飾 g23 的重試與備援兩次呼叫各產生約 32.5k completion token、各耗時約 519 秒，皆以 `finish_reason=length` 結束；答案寫完後模型繼續輸出「Wait, the input is: …」。摘要 g16 同樣發生一次。三次呼叫佔該 run 1,789 秒中的 1,557 秒。失控發生在潤飾與摘要，兩者同為 Gemma 的對話呼叫。

## 行為與驗收條件

1. 潤飾請求帶生成量上限，與 WI-1432 的摘要上限同機制：超過時走既有 `TRUNCATED` 處理（重試、降級、計數）。
2. 上限依該組輸入的規模決定（輸出約與輸入同量級加固定餘裕），而不是單一固定值，使正常的大組不被截斷、失控的呼叫在數十秒內結束。換算規則與餘裕值寫入 README 與 runbook（單一寫處），由實作者依 arr 兩次 run 的 exchange 資料（正常回答的 token 數分佈）提出，架構師核可。
3. 備援呼叫（重試後再試的同一請求）沿用同一上限，不因重試而放寬。
4. 其他階段（核對、翻譯）是否同樣需要，依同一份資料評估並回報；不在本項直接加入。
5. 既有行為不變：條目時間不變式、降級規則、其他階段的輸出。

## 架構約束

- 不修改 Engine 或共享資源定義。
- 對真實 Lemonade 的驗證由 arr 上的下一次 run 完成。

## 範圍外

- 潤飾 g18、g23 的 `TIME_CHANGED`（模型把 `00:01:22,050` 寫成 `00:00:22,050`）屬獨立問題，由既有不變式擋下並降級，不在本項處理。
