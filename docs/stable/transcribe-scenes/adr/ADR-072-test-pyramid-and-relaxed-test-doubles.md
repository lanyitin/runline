# ADR-072 測試金字塔：行為規則下沉到快速測試，放寬行程內測試替身

本文回答：T 的測試為什麼慢到每個小功能都要等 30 分鐘以上、是否與「禁止 Mock／Stub」有關，以及如何把回饋時間降到可接受。狀態：已核可（2026-10-15）。補充 [ADR-065](ADR-065-test-suite-speed.md)（分組、並行、去等待，已部分完成）；放寬 `.claude/agents/tdd-coder.md` §2「禁止本地 Stub／Mock」的範圍，見決策 3。

## 背景

- 規模（T，唯讀盤點）：211 個測試檔、約 1,416 個測試；其中 41 個 `*RunTest` 類別約 390 個測試是端到端：每個測試啟動一次完整的 devkit JVM 執行（README 估計約 2.5 秒：JVM、紀錄資料庫、VAD 工具、ffmpeg），沒有 sleep 或退避。
- 單是 390 個端到端測試就約 16 分鐘（序列），並行 4 個 JVM 後約 4 至 5 分鐘；使用者實際等待 30 分鐘以上，所以時間不只在測試本體。尚未量測的部分：Gradle 的組態與編譯（主程式、測試、量測與假服務多個來源集）、依賴下載（例如 `fetchAligner` 約 2 GB）、外部行程測試、並行時的資源競爭、每次工作都跑的範圍大於需要。
- 驗證邏輯（重試政策、答案解析、及早止損、續跑規則、降級原因）目前多半以「整條 pipeline 跑一次」來斷言；一條規則的一個分支就要付一次 2.5 秒。這是慢的主因之一。
- 與「禁止 Mock／Stub」的關係：規則本身不是慢的來源（假服務是真的 HTTP 伺服器，行程內啟動只要毫秒到秒）；但規則使測試只能「從外面打」——沒有行程內的替身可以快速驅動內部邏輯，於是所有行為都被擠到端到端層。放寬規則可以讓下層測試成為可能，但**不放寬也有三個不涉及規則的槓桿**（行程內執行、分層、只跑需要的）。
- 使用者的判斷：每新增一個小功能就等 30 分鐘以上不合理；願意放寬 Mock／Stub 限制，只要能縮短單元測試時間，邊界可以很寬；全套只在使用者指定時執行。

## 決策

1. **先量測，用同一把尺**：量測要涵蓋「一次完整的工作回饋」的全部成本，而不只是測試本體：Gradle 組態與編譯、依賴準備、每個測試類別與測試的耗時、分類（純邏輯、行程內整合、端到端、外部行程、量測工具）、並行利用率。後續所有改動都以這份量測比較。**在量測回報前，本 ADR 的目標值與下列分層只是方向，不是承諾。**
2. **分層，行為規則下沉**：
   - 純邏輯層：答案解析、重試與止損的判斷、降級規則、續跑的選擇規則、報告內容的組成等，以直接呼叫的測試驗證，不起 JVM、不起 HTTP、不起資料庫（毫秒級）。
   - 行程內整合層：同一個 JVM 內，以真實 SQLite 檔（或記憶體資料庫）與行程內的模型服務替身驅動 pipeline 的階段；不起子行程。
   - 端到端層：只保留少量（原則上每個階段與每個外部契約一至數個）完整的 devkit 行程測試與契約測試，驗證接線、參數、部署相關行為。
   - 每個既有行為規則只在最低可驗證的一層斷言；高層只保留「接線正確」的最小斷言。遷移時不得降低檢查力（逐項對照，見 WI-1480）。
3. **放寬測試替身的範圍**：凡是能縮短測試時間的替身都允許，不限於內部介面。
   - 允許：行程內的手寫 in-memory 實作、可程式化的替身、Stub、Mock 工具，可用在任何邊界——包括資料庫、模型服務、外部行程、時鐘、檔案系統——只要它讓測試更快且仍以結果驗證行為。
   - 仍須保留：測試套件中有少量真實或契約測試守住對外協定（資料庫、模型服務的 HTTP 協定、外部行程），讓替身與真實行為的漂移被發現；這是套件組成的要求，不是對替身用法的限制，數量與位置由 WI-1480 依量測決定。
   - 仍禁止：在 production 程式中為測試加後門或 `if (test)` 分支；為了讓測試變綠而寫死回傳值、與被測行為無關的斷言；以「只驗證替身被呼叫」取代行為斷言（行為以結果——輸出、紀錄、狀態——斷言為主，互動斷言限於確實是契約的部分，例如重試次數、請求內容）。
   - 此決策的執行方式：tdd-coder 定義 §2 已依本決策修改。
4. **回饋分層與相關測試規則**：
   - 日常工作：純邏輯層加受影響階段的行程內整合層（目標：單一工作項的相關測試 ≤ 3 分鐘）。
   - 端到端層與全套（三層加量測工具）只在使用者指定時執行；tdd-coder 不自行觸發（tdd-coder 定義 §1.1 已依本決策修改）。
   - 後果：接線層的回歸在使用者執行端到端層之前不會被發現；風險由使用者在合併與部署前的時機自行把關。
5. **目標值**（使用者確認合理；仍待量測確認）：純邏輯層全部 ≤ 1 分鐘；單一工作項的相關測試 ≤ 3 分鐘；全套 ≤ 10 分鐘。量測顯示不可行時由 tdd-coder 回報可達數字，由架構決定。

## 取捨

- 得到：日常回饋從 30 分鐘以上降到數分鐘；失敗的定位更近（在規則層就失敗，不是整條 pipeline 失敗）；並行派工時各自的測試不再互相搶資源。
- 失去：
  - 替身與真實行為可能漂移，所以協定邊界保留端到端與契約測試；
  - 遷移要逐項對照，有一次性成本，且遷移期間兩層會並存；
  - 放寬規則需要紀律：用替身驅動邏輯，不用替身證明相容性。
- 不採用：
  - 只調並行與機器資源（上限在端到端的單價，成效有限）；
  - 刪除或停用測試、降低斷言（tdd-coder 定義已禁止）；
  - 把慢測試移到沒人跑的流程。
