# 非功能性考量與風險

本文回答：系統的弱點在哪裡、各風險如何緩解或接受。

## 風險與緩解

| 風險 | 說明 | 處置 |
|---|---|---|
| 無強制沙箱 | JVM 已無可靠的行程內沙箱；context 為協作式，pipeline 可直接使用 JDK 的 IO 類別繞過 | 接受。以 unsafe 標記與營運者政策管理；明確告知此限度 |
| 靜態分析可被繞過 | 反射、動態載入、字串組出類別名稱都不會被 import 掃描發現 | 接受。分析結果定位為風險提示，並在報告中註明未涵蓋動態行為 |
| 無法強制終止 run | 同一 JVM 內不能安全強制停止執行緒 | 取消與逾時為協作式；逾時後標記 run 為「逾時未結束」並計入並行額度，直到實際結束 |
| 資源無法隔離 | 記憶體、CPU 與 Engine 及其他 run 共用 | 以並行 run 上限降低影響；超載風險接受 |
| 全域狀態共用 | 系統屬性、標準輸出入影響整個 Engine | 由 Runner 在邊界處攔截標準輸出入並歸屬到 run |
| pipeline 結束 JVM | 所有 run 共用 Engine 的 JVM；pipeline 或第三方庫呼叫結束 JVM 的功能時，Engine 行程整個結束，其他 run 與 API 一併中斷。JVM 已無法阻擋此呼叫 | 接受：部署平台自動重啟，Engine 啟動時把進行中的 run 標記為中斷 |
| class loader 洩漏 | 執行緒或靜態參照殘留導致 loader 無法回收 | run 結束後檢查殘留執行緒；以回收情況作為監控指標 |
| Cron 重複觸發 | 多實例時同一時刻重複觸發 | v1 單實例；資料庫的唯一性仍保證同一排程時間只建立一個 run；多實例前需先處理各實例各自排程的問題 |
| Cron 的夏令時間語意 | 有夏令時間的時區下，間隔小於一小時的工作在回撥的那一小時內沒有觸發；跳時的不存在時間順延觸發 | 接受（[ADR-005](adr/ADR-005-trigger-binding.md)）；預設時區為 UTC，不受影響 |
| Cron 函式庫無新版本 | 使用的 cron 解析函式庫最後一次發佈為 2023 年 | 接受；函式庫被限制在單一類別，日後可局部替換 |
| Webhook 沒有速率限制 | 驗證失敗的呼叫只記錄 log 與 metric；大量請求仍消耗資源 | 接受；密鑰為高熵隨機值，無法被實際猜出；速率限制由部署層（反向代理）負責 |
| Webhook 去重視窗 | 去重只在觸發紀錄的保留期限內有效；Engine 在觸發認領後、結算前終止，該 delivery 重送得到接受回應但不補觸發 | 接受（[ADR-005](adr/ADR-005-trigger-binding.md)）；視窗由組態決定，預設 7 天 |
| Jar 供應鏈 | 上傳的 jar 可能含惡意或有漏洞的相依 | 上傳需認證並記錄上傳者；相依以樹狀展開掃描，違規附路徑 |
| 解壓炸彈 | 小型惡意 jar 解壓後耗盡記憶體或磁碟 | 上傳大小上限之外，對解壓後總大小、單一項目大小與項目數量設上限（[WI-18](work-items/WI-18-upload-hardening.md)） |
| 樹狀分析成本與誤判 | 大型相依樹展開耗時；白名單過窄使多數 pipeline 被判 unsafe（JDK 的 `java.io` 等套件未列入時尤其明顯） | 為分析設定時間與規模上限，超限視為 unsafe 並註明原因；白名單節點視為受信任、不再展開，以控制規模 |
| 白名單變更 | 白名單修改後既有判定可能過時 | 判定記錄所用白名單版本；變更時立即重判（同一交易，可先預覽；手動重判可更新分析規則改變後的判定）。重判逐一分析所有已儲存的 jar，耗時與總大小成正比，期間持有白名單的互斥鎖（見 [08-api](08-api.md)「規模與限度」） |
| 共享目錄被同時寫入 | 同一 pipeline 的多個 run 同時讀寫共享目錄會互相干擾 | 不做協調；需要互斥者用共享資源（[ADR-007](adr/ADR-007-shared-resources.md)） |
| 磁碟用量 | 共享目錄跨 run 持續累積，私有目錄在失敗後保留 | Engine 組態的用量上限、保留期限，並有用量 metric 與管理員清空功能 |
| run、log 與觸發紀錄無限累積 | run 紀錄、log 與觸發紀錄在資料庫持續成長；每分鐘一次的 cron 一年約增加五十萬筆觸發紀錄 | 依保留期限清理（[WI-20](work-items/WI-20-run-retention.md)）：背景以固定間隔分批刪除，單次處理量有上限；未結束的 run 與待處理的觸發紀錄不被清理；去重視窗設有下限（24 小時） |
| 跳出目錄範圍 | 相對路徑或符號連結可能指向範圍外 | context 拒絕跳出的操作；經 JDK 直接存取的程式碼不受控，屬 unsafe 範疇 |
| 共享目錄遺失 | 磁碟區故障會讓快取消失 | 視為可重建；pipeline 不得依賴它作為唯一的資料來源 |
| pipeline 名稱與目錄名稱不相容 | 目錄名稱只允許字母、數字、`.`、`_`、`-`；名稱含其他字元的 pipeline 會在初始化階段失敗 | 上傳時驗證 pipeline 名稱並拒絕不相容者（[WI-18](work-items/WI-18-upload-hardening.md)） |
| 共享資源鎖是約定式 | 鎖不綁定實際網路動作，pipeline 未宣告就連線不會被攔下 | 接受；與協作式 context 的限度一致 |
| 共享資源占用過久 | 初始化階段取得、run 結束才釋放，吞吐低 | 接受（[ADR-007](adr/ADR-007-shared-resources.md)）；以持有時間 metric 觀察 |
| 共享資源持有者卡住 | 無法強制終止的 run 長期占用資源 | 不自動釋放以保住互斥；提供持有時間 metric 與管理員強制釋放 |
| 共享資源狀態遺失 | Engine 狀態在記憶體，重啟後消失 | 重啟時所有進行中 run 本就標記為中斷，資源一併釋放；多實例前需改為共享儲存 |
| 單實例的實作限度 | run 排程佇列在記憶體，重啟時進行中的 run 一律中斷；cron 排程器與啟動時將待處理觸發標記為中斷的步驟都假設單一行程；資料庫沒有連線池，每次呼叫開新連線，每個執行中的 run 持有一條 log 連線；每行 log 為一次同步寫入 | v1 接受；輸出量大的 pipeline 與多實例部署前需改為連線池、批次寫入與共享的排程狀態；多實例時啟動步驟可能把他實例進行中的觸發誤標為中斷 |
| 設定與建立 run 的競態 | 讀取 unsafe 設定到寫入 run 之間有極短的時間窗，期間設定被變更會使 run 記錄的設定與實際判斷不一致 | 接受；run 記錄的是建立時讀到的設定 |
| 錄製涵蓋不全 | 只含錄製時走過的路徑 | 提案僅供參考，採用前人工檢視 |

## 可觀測性

- Log：每個 run 的 log 歸屬到該 run，並可查詢。
- Trace：每個 run 一條 trace，包含 trigger 來源與主要階段。
- Metric：進行中 run 數、排隊數、逾時未結束數、class loader 回收數、unsafe 比例、上傳判定結果、共享資源的等待時間／持有時間／佇列長度、trigger 的觸發／被拒絕／失敗／重複／驗證失敗數。

## 安全

- 管理與上傳 API 需認證與授權（[ADR-012](adr/ADR-012-api-authentication.md)）。
- Webhook 密鑰與 API token 不得出現在 log、trace 或錯誤訊息；資料庫只保存 webhook 密鑰的雜湊。
- 執行 unsafe pipeline 需有該 pipeline 的明確授權，並記錄在 run 上。

## 容量

v1 預期規模小（單團隊）。並行 run 上限以 JVM 記憶體為依據，由組態設定；實際數值待壓測後決定。
