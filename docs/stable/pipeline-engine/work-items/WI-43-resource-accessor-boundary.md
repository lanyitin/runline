# WI-43 資源存取端、檢查端點與 `file` 型別

本文回答：Engine 如何把型別化資源的受控存取端交給 run、如何回收與失效、管理員如何檢查資源，以及第一個有實體的型別 `file` 如何以真實檔案系統驗證這些通用機制。狀態：已核可（2026-10-06）。相依：WI-39、WI-40。決策見 [ADR-019](../adr/ADR-019-typed-shared-resources.md) 第 3、4（`file`）、8 點與 [05](../05-ipc.md)「資源存取端」。

本項合併原 WI-43（存取端邊界）、[WI-44](WI-44-resource-check-endpoint.md)（檢查端點）、[WI-45](WI-45-file-resource.md)（`file` 型別），一次交付；後兩份文件只保留指向本項的說明。檔名沿用 `WI-43-resource-accessor-boundary.md`。

## 背景

`counter` 沒有存取端。有實體的型別（`file`、`jdbc-pool`、`openai-compatible`）由 Engine 持有實體，run 只拿到受控的存取端。`file` 是最單純的實體：不需機密、不需外部服務，只需要檔案系統。本項以真實的 `file` 型別與真實檔案系統驗證與型別無關的通用機制（邊界、取用規則、回收與失效、檢查、開發入口），不使用僅存在於測試的替代型別；後續型別（WI-46、WI-48）沿用同一組機制，只加入各自的操作與檢查內容。

型別集合是封閉的，本項不引入任何擴充點，也不引入測試專用的型別註冊機制。

## 內部步驟（依序 TDD，每步完成後再進下一步）

1. **存取端邊界與回收、失效**：以 `file` 的最小操作（讀取、寫入）為載體，建立契約、取用規則、備妥、回收與強制釋放失效、開發入口本機實作與錄製。載體所需的 `file` 型別骨架（型別註冊、資源根目錄組態、路徑限定）在此步一併建立，完整行為在步驟 3 補齊。
2. **檢查端點與檢查結果**：通用的 `check` 端點、結果保存與呈現，`counter` 與 `file` 的檢查內容。
3. **`file` 型別完整行為與部署**：路徑與符號連結限制、完整操作、互斥與容量、可觀測、資源根目錄的部署。

三步的驗收條件全部在本項完成後才算通過。

## 行為與驗收條件

### 一、存取端邊界、回收與失效（步驟 1）

**契約與邊界**
- core 定義存取端的契約；跨越 class loader 邊界時只使用 JDK 內建型別，實體與 Engine 內部型別不穿過邊界。以真實的 class loader 隔離與真實 `file` 資源驗證（沿用既有隔離測試方式）。
- 使用存取端的 pipeline 仍為 safe：以真實編譯的測試 jar（使用 `file` 存取端）驗證，資源宣告與存取端使用都不改變判定。

**取用規則**
- Pipeline 只能依名稱取用「自己宣告了型別且已持有」的存取端。取用未宣告、只宣告名稱、或型別不符的資源，得到明確的失敗；沒有「執行中取得資源」的操作（沿用 WI-09）。
- 只宣告名稱的資源只取得容量，行為與現行完全相同；以同一資源分別被「只宣告名稱」與「宣告 `file` 型別」的 run 使用驗證。
- 宣告 `file` 型別但資源是 `counter`（或反之）時，建立 run 回 `type_mismatch`（沿用 WI-40，此時以真實的 `file` 資源重新驗證兩個方向）。

**初始化與備妥**
- 取得容量成功後，Engine 為每個宣告了型別的資源備妥存取端，初始化完成時存取端已可用。備妥失敗（實體不可用，例如根目錄被移除或權限被收回）時 run 失敗並註明資源不可用，不進入 pipeline 本體，且已取得的容量被釋放（之後的 run 可取得該資源）。
- 存取端綁定該 run 與取得當下的資源設定：持有期間資源設定被修改（例如路徑改指向另一個檔案），該 run 繼續使用舊設定，之後取得的 run 使用新設定；以兩個 run 分別寫入的實際檔案驗證。

**回收與失效**
- Run 以任何方式終止（成功、失敗、取消、中斷）時，Engine 回收該 run 的所有存取端：終止後該存取端的任何操作都失敗，且不會對檔案產生任何效果。
- 管理員強制釋放持有者時，存取端同時失效：之後的操作失敗並註明原因為強制釋放；容量釋放後下一位等待者取得時，檔案不會同時被兩個 run 使用，前者失效後的寫入不會出現在檔案中。強制釋放端點的其他行為不變，08-api 補充此語意。
- 停用資源使等待者失敗，不影響持有者的存取端；降低容量不收回持有者的存取端。
- 「進行中的長時間操作被取消」（連線、請求、查詢）無法以瞬間完成的檔案操作驗證，由 WI-46（進行中請求）與 WI-48（進行中查詢與交易回滾）以各自的真實實體驗證；本項的契約須讓這類取消可被表達。

**錯誤與記錄**
- 回傳給 run 的實體錯誤只含錯誤類別，不含絕對路徑或系統訊息原文；原文與例外寫入 Engine log，以 `errorId` 對應。
- Run 的 log 記錄資源取得、存取端失效與實體錯誤類別，不記錄檔案內容與路徑。Run 的 trace 每次資源操作一個 span，只記錄資源名稱、型別與操作類別。

**開發入口**
- 開發入口以同一份契約提供本機實作：資源定義由本機組態提供（不連 Engine），`file` 以本機組態的根目錄提供；單一 run 沒有競爭，初始化立即成功。
- 錄製在開發入口記錄「使用了哪個資源（名稱與型別）與動作類別」，不記錄內容；metadata 提案據此產生型別宣告（[ADR-004](../adr/ADR-004-recording.md)）。Engine 的 run 不帶錄製選項。
- Engine 與開發入口以同一組行為驗收測試驗證：取用規則、失效、錯誤類別、路徑限制、操作、錄製。

### 二、檢查端點與檢查結果（步驟 2）

- `POST /api/v1/resources/{name}/check`（管理員）：回 200，本文含 `ok` 與（失敗時）失敗類別，不含原因細節、位址、路徑或機密；404 `resource_not_found`；開發人員 403，無 token 401。停用的資源也可檢查。
- 檢查內容由型別提供：`counter` 沒有實體，回 `ok`；`file` 驗證路徑可用，失敗類別至少區分根目錄不可用、父目錄不可建立、不可讀寫。檢查機制須能由後續型別加入各自的驗證與失敗類別，以及機密別名是否存在於金鑰庫的檢查（別名缺失類別，由 WI-46 與 WI-48 在引入第一個接受別名的型別時加入並驗證）。
- 檢查不取得容量，不影響進行中的 run、等待者與持有者；有整體逾時上限（由 Engine 組態設定），逾時為一種失敗類別。以真實會阻塞的檔案系統物件（例如沒有對端的具名管線）驗證逾時；本機平台無法建立時回報，不得宣稱已驗證。同一資源同時被檢查時結果一致且不互相破壞。
- 最近一次檢查的結果與時間保存於資料庫（[06](../06-data-model.md)），資源的查詢回傳之；從未檢查為空。資源設定或別名被修改時，最近一次結果清除；其他資源操作不改變它。以真實 PostgreSQL 與真實檔案系統驗證。
- 稽核與可觀測：檢查記錄管理員名稱與結果類別；有各型別的檢查結果 metric（標籤只用資源名稱與型別）。
- 08-api 同步更新：新端點、回應欄位、資源回應中的最近檢查欄位；`ApiDocumentationTest` 通過。

### 三、`file` 型別完整行為與部署（步驟 3）

**組態與根目錄**
- Engine 組態提供資源根目錄（環境變數，命名依 `RUNLINE_` 慣例，寫入 04）。根目錄與 pipeline 共享目錄、run 私有目錄的位置不得相同或互為上下層，否則啟動失敗並列出鍵名。（金鑰庫檔案不得位於資源根目錄之下的檢查由 [WI-41](WI-41-keystore-secrets.md) 實作。）
- 根目錄不存在或不可讀寫時 Engine 仍可啟動；資源的檢查與初始化失敗，註明資源不可用。

**資源設定**
- `file` 資源設定為「相對於資源根目錄的路徑」與容量，不接受機密別名。絕對路徑、跳出根目錄的相對路徑、符號連結解析後跳出根目錄的路徑都被拒絕（422 `invalid_resource`，`problem` 為路徑不在資源根目錄內）。
- 建立、修改與檢查時驗證路徑可用：父目錄存在或可建立、可讀寫。

**存取端操作**
- 提供對該一個檔案的讀取、寫入（覆寫）與附加，以位元組與字串兩種形式（只用 JDK 內建型別）；不暴露路徑，不能列出或存取同目錄的其他檔案。單次讀取大小有上限（Engine 組態），超過回傳錯誤類別。
- 每次操作時重新驗證路徑未被替換為指向根目錄外（符號連結被改動後的操作被拒絕），以真實符號連結驗證。
- 錯誤只含類別，不含絕對路徑。

**互斥與容量**
- 容量 1：兩個不同 class loader 的 run 同時宣告同一個 `file` 資源時，同時只有一個持有，另一個等待並依先進先出取得（沿用 ADR-007）；持有者終止後立即換手。容量 N：同時最多 N 個 run 持有；Engine 不提供檔案內容層級的協調（驗證 N=2 時兩個 run 可同時持有，並在文件註明）。
- 初始化階段取得容量後再確認路徑可用；不可用則 run 失敗並註明資源不可用，不進入 pipeline 本體，已取得的容量被釋放。
- 強制釋放使存取端失效（沿用第一節）。刪除資源（WI-40）不刪除實際檔案。

**可觀測與靜態分析**
- Metric：`file` 的操作數與路徑檢查失敗數；trace 與 log 規則沿用第一節，不記錄路徑與內容。
- 使用 `file` 存取端的 pipeline 仍為 safe（真實編譯的測試 jar）。

**部署**
- 04 與兩份平台指南、`deploy/` 的檔案說明並提供資源根目錄的掛載（Docker 的持久磁碟區、systemd 的狀態目錄），強調備份與容量由部署環境負責；以真實 Docker 驗證掛載的根目錄可寫、Engine 啟動後以 `file` 資源寫入的檔案在容器重建後仍在。
- 08-api 同步更新（`type=file` 的設定欄位、`invalid_resource` 的新增 `problem`）；`ApiDocumentationTest` 通過。

## 架構約束

- 容量取得、等待、釋放語意不變（ADR-007）；本項不引入請求級或交易級的取得與釋放。
- 契約在 core，Engine 與開發入口各自實作；探索與分析不得執行 pipeline 邏輯（[ADR-003](../adr/ADR-003-jar-and-discovery.md)）。
- 型別集合封閉，不開放外掛，也不為測試加入型別註冊的擴充點；通用機制一律以真實的 `file` 型別驗證。
- 不改變 ADR-009 的共享目錄與私有目錄行為；`file` 資源是它之外的獨立範圍。
- 路徑限制與互斥只用真實檔案系統、真實符號連結與真實 class loader 隔離驗證，不使用 Stub 或 Mock；需要替代品時使用自製的簡易真實實作（Fake）；資料庫使用真實 PostgreSQL（Testcontainers）；嚴格 TDD；不新增 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
