# WI-1438 TEN VAD 命令列工具與可行性關卡

本文回答：第二個 VAD 工具要達成什麼行為，以及它在 arr 上是否可行。狀態：已取代，不派工（[WI-1440](WI-1440-denoise-before-vad.md)、[ADR-046](../adr/ADR-046-denoise-before-vad.md)；保留供日後參考）。相依：WI-1407。儲存庫：T（獨立建置單元，與 pipeline jar 分開）。

## 行為與驗收條件

1. **可行性關卡（先做，結果回報後才繼續）**：TEN VAD 首選在 Java 行程以 ONNX Runtime 執行官方 ONNX 模型（不引入 Python）。事實：官方 ONNX 模型（`src/onnx_model/ten-vad.onnx`，315,449 位元組，sha256 `e10b98a0cab1c98e847fbdda14cb3d45a38336d47535a3f63a0fb6c4e0f4cdf4`，輸入名 `input_6`）只含神經網路；官方「Python ONNX 範例」實為 C++ 擴充模組，前處理（LPCNet 衍生的 STFT、pitch 估計、biquad 等特徵擷取）在 C++ 中，不在模型內。因此首選方案必須在 Java 重現這段前處理。確認：特徵擷取以 Java 實作後，輸出與官方實作對同一輸入的逐幀機率差異在容許誤差內（目標：逐幀最大差異 ≤ 0.005，且以 0.5 判定的幀不同者 ≤ 0.1%；容許值依實測定稿）；授權條款原文與 NOTICES 的重點寫入專案文件。
   - 做不到容許誤差，或前處理無法合理重現：使用者已允許退路——改用官方預編譯的原生函式庫（Linux x86_64）加 Java 包裝，仍為獨立行程、同一種命令列契約。切換前先把可行性結果回報架構師；退路也不可行時（例如沒有可用的 Linux 函式庫、無法在容器載入），停下來回報，不自行改用 Python。
2. **命令列契約**：與 silero 工具同形——輸入 16 kHz 單聲道 WAV，標準輸出為整個檔案每個固定視窗的語音機率，並說明視窗長度與取樣率；診斷走標準錯誤；成功結束碼 0，失敗非 0 並說明原因；同一輸入逐值相同；一次呼叫處理整個檔案。
3. **輸入檢查**：檔案不是 16 kHz 單聲道 WAV 時失敗並說明；無語音的音訊輸出全低機率且結束碼 0。
4. **版本固定**：TEN VAD 的版本與模型（或函式庫）雜湊固定並記錄於專案文件；缺少或雜湊不符時失敗並指出原因，不連網下載。
5. **對照基準**：以官方實作對同一 WAV 產出的逐幀機率為基準。homelab-deployer 已對 arr 同一支影片的 `orig.wav`（hop 256，14,628 幀）產出兩份：原生函式庫版（`ten256.probs`）與官方 ONNX 範例版（`onnx256.probs`，與前者逐幀差異：平均 0.00009、最大 0.0007）；Java 版對它們的差異須在容許誤差內（容許值依實測定稿並寫入專案文件）。基準檔隨專案保存的方式由實作者提案（檔案大小與授權）。
6. **測試**：以真實 ONNX Runtime（或退路下的真實原生函式庫）與真實音訊樣本測試，不使用替身；樣本使用可再散布的語音。
7. **部署**：產出可在 arr 的 Engine 容器內以 `runline-vad` 同樣方式執行的單位（掛載路徑與命令名稱由實作者提案，與 silero 工具不衝突）；部署由 homelab-deployer 在核可後執行。

## 架構約束

- 不連網；僅 CPU；工具不含判定參數（門檻、最小靜音等屬 pipeline 側，WI-1439）。
- 工具是獨立行程，不進 pipeline jar；pipeline 只依契約。
- 授權條款對 runline 散佈的影響記錄在專案文件，是否散佈由使用者決定。
