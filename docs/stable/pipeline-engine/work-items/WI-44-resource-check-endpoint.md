# WI-44 檢查端點與實體狀態

本文回答：管理員如何主動驗證資源的實體與機密別名，以及最近一次檢查結果如何保存與呈現。狀態：已核可（2026-10-06）。相依：WI-40、WI-41。決策見 [ADR-019](../adr/ADR-019-typed-shared-resources.md) 第 8 點。

## 背景

有實體的資源需要在不取得容量、不影響 run 的情況下驗證設定是否可用。本項提供通用的檢查機制與結果保存；各型別的具體檢查內容隨 WI-45、WI-46、WI-48 加入，在此之前以測試用 Fake 型別驗證機制。

## 行為與驗收條件

- `POST /api/v1/resources/{name}/check`（管理員）：回 200，本文含 `ok` 與（失敗時）失敗類別，不含原因細節、位址、路徑或機密；404 `resource_not_found`；開發人員 403。停用的資源也可檢查。
- 檢查的內容：型別專屬的實體驗證（由各型別提供），以及機密別名是否存在於金鑰庫（未組態金鑰庫或別名不存在為失敗，類別與 WI-41 的狀態一致）。`counter` 沒有實體與別名，檢查回 `ok`。
- 檢查不取得容量，不影響進行中的 run、等待者與持有者；有整體逾時上限（由 Engine 組態設定），逾時為一種失敗類別。同一資源同時被檢查時結果一致且不互相破壞。
- 最近一次檢查的結果與時間保存於資料庫（[06](../06-data-model.md)），資源的查詢回傳之；從未檢查為空。資源設定或別名被修改時，最近一次結果清除；機密重載與其他資源操作不改變它。
- 稽核與可觀測：檢查記錄管理員名稱與結果類別；有各型別的檢查結果 metric（標籤只用資源名稱與型別）。
- 08-api 同步更新：新端點、回應欄位、資源回應中的最近檢查欄位；`ApiDocumentationTest` 通過。

## 架構約束

- 檢查與取得容量是分開的操作；不引入請求級取得。
- 失敗類別是穩定的代碼，原因細節只寫 Engine log（以 `errorId` 對應），不外洩機密與內部位址。
- 測試使用真實 PostgreSQL（Testcontainers），不使用 Stub 或 Mock；需要替代品時使用自製的簡易真實實作（Fake）；嚴格 TDD；不新增 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
