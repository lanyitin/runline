# WI-26 測試的逾時保護

本文回答：如何確保測試不會因為等待一個永遠不回應的對象而卡死。狀態：已核可（2026-10-05）。相依：WI-23。

## 背景

[WI-20](WI-20-run-retention.md) 的執行中，打包形態測試曾在 `startEngine` 卡住超過十分鐘，原因看起來是既有資源測試使用的 HTTP 請求沒有設定逾時，Engine 沒有回應時請求會無限等待；之後在五次重跑中無法重現。測試中任何沒有逾時的等待（網路請求、行程等待、執行緒的等待、取得鎖、讀取輸出）都可能使整個驗收卡死，且卡死沒有失敗訊息可供診斷。

## 行為與驗收條件

- 盤點所有模組（core、runner、analyzer、devkit、engine，含打包形態測試與測試支援程式）中沒有逾時的等待，逐一列出位置與處置：
  - HTTP 請求（用戶端本身與每個請求）；
  - 外部行程的啟動、等待結束與讀取輸出；
  - 執行緒、執行器與 future 的等待；
  - 取得鎖與等待條件；
  - 容器（Testcontainers）的啟動與資料庫連線。
- 每個沒有逾時的等待都加上合理的逾時，逾時時測試失敗並給出可診斷的訊息：指出在等什麼、等了多久，必要時附上目前的狀態（例如行程的輸出尾端、Engine 的日誌尾端）。不得以放寬斷言或縮小被驗證的行為換取通過。
- 打包形態測試啟動的真實行程，在測試結束、失敗或逾時時都會被終止，不留下殘留行程；以測試或檢查驗證。
- 逾時值依被等待事件的合理上限決定，並集中管理（單一處可調整），不散落為各處的魔術數字；在回報中說明各逾時值與理由。
- 逾時保護本身有驗證：對至少一種等待（例如一個不回應的 HTTP 伺服器或一個不結束的行程），以真實的對象驗證逾時確實觸發、訊息可診斷；此驗證在移除逾時時會失敗（暫時移除再還原）。
- 修正的有效性以重複執行驗證：打包形態測試連續執行至少 20 次，完整測試（含打包形態）連續執行至少 5 次，全數通過；回報重複執行的指令與每次結果。若重複執行中仍出現卡住或不穩定，記錄其內容與頻率。
- 不刪除任何既有測試、不放寬任何既有斷言；測試數量不減少，新增的驗證除外。
- 若盤點發現卡住的原因來自正式程式碼（例如 Engine 在某情況下不回應請求或不關閉），停下來回報，不自行修改正式程式碼。
- 建置、全部測試在 JDK 25 下通過，`ktfmtCheck` 通過。

## 架構約束

- 只修改測試與測試支援程式；不修改任何模組的正式程式碼。
- 測試使用真實 PostgreSQL（Testcontainers）與真實行程，不使用 Stub 或 Mock；時間以可控制的時鐘提供，不以睡眠換取通過。
- 不新增外部相依；不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
