# #6：Wiki 映像的頁面對應、連結改寫、刪除同步與憑證

本文回答：stable 如何對應成 Wiki 頁面、文件間連結如何處理、被刪除的文件如何反映，以及誰有權寫入 Wiki。狀態：已核可。Issue：#6、#9。補充 [#1](1-wiki-is-readonly-mirror.md)，不取代它。

## 背景

現況量測（stable 共 351 個檔案，皆為 Markdown）：

- 同名檔案大量重複（例如各主題都有 `01-requirements.md`、`README.md`），目錄深度最多三層。
- 內文有約 1,700 個相對連結，其中 1,657 個指向 stable 內的 Markdown，3 個指向目錄（`adr/`），3 個只有頁內錨點，54 個指向 stable 之外的儲存庫檔案，其中至少一個指向另一個儲存庫。

Forgejo 實測結果（對 `forgejo.dev.lan` 上的本儲存庫）：

- Wiki 功能已啟用；Wiki 倉庫的預設分支是 `main`，實測前為空。
- 頁名帶路徑分隔時被接受；Forgejo 內部將路徑分隔轉成編碼字元，清單 API 回傳的頁名與原標題一致，因此能由頁名還原原路徑。大小寫不同的頁名是各自獨立的頁面。
- Wiki 是扁平的：放在 Wiki 倉庫子目錄中的檔案不會成為頁面，層級只能靠頁名表達。
- Actions 的內建 token 可透過 API 建立頁面，也可透過 git 推送寫入 Wiki，沒有權限錯誤。此結果只在 push 觸發的工作流驗證過。
- runner 已信任 `forgejo.dev.lan` 的憑證，不需要關閉 TLS 驗證或額外信任 CA。
- 單頁讀取的 API 實測失敗，原因未明；單向同步不需要讀取。
- 尚未驗證：數百頁、三層路徑下，連結在網頁上的實際可點擊行為。

## 決策

**頁面對應：路徑即頁名。** Wiki 頁名取 stable 的相對路徑（去掉副檔名），層級以路徑分隔表達，因此同名檔案不衝突，也能從頁名還原原路徑。首頁目錄與側邊欄依主題階層列出。

**連結改寫：保留可點擊的文件網。**

| 連結類型 | 處理 |
|---|---|
| 指向 stable 內 Markdown | 改成指向對應 Wiki 頁，保留錨點 |
| 指向 stable 內目錄 | 改成指向該目錄的入口頁（有 README 的主題）或首頁目錄 |
| 頁內錨點 | 不變 |
| 指向 stable 之外、但在本儲存庫內 | 改成指向 `main` 上該檔案的儲存庫網址 |
| 指向其他儲存庫或無法解析 | 保留顯示文字，移除連結，並在同步日誌列出 |
| 外部網址 | 不變 |

來源檔案的連結改寫只發生在映像中，不修改 stable 本身。

**刪除同步：完整映像。** 每次同步以當下的 stable 完整重新產生 Wiki 內容並覆蓋，stable 中刪除或改名的文件在 Wiki 同步消失。這同時讓重複同步不產生差異。

**憑證：Actions 內建 token，最小權限。** 同步工作流使用 Actions 自動提供的內建 token，不建立專用 secret。工作流明確宣告只需要的權限，不使用寬權限。內建 token 只在該次執行有效。

## 取捨

- 路徑即頁名：頁名較長，但可逆且無碰撞；替代方案（攤平並加前綴編號）可讀性差，且新增主題時易衝突。
- 改寫連結：增加實作複雜度，但不改寫則約 1,700 個連結在 Wiki 失效，映像失去意義。
- 完整覆蓋：每次同步工作量與 stable 規模成正比（目前數百個檔案），可接受；換得簡單與可驗證的一致性。
- 內建 token：不需要保存與輪替長期憑證，暴露面僅限單次執行；代價是其實際權限範圍受儲存庫 Actions 設定影響，且只驗證過 push 觸發的情境。其他觸發情境、或儲存庫設定改變後不再可寫時，同步會失敗，改用專用 secret 須重新決策。

## 後果

- Wiki 的任何手動修改都會在下次同步被覆蓋。
- 連結改寫規則成為映像的契約，文件作者仍按 stable 現有的相對連結寫法，不需為 Wiki 另寫。
- 指向儲存庫外的連結在 Wiki 無法點擊，需在同步日誌中可見。
- 使用者不需要為此功能建立任何 secret。
