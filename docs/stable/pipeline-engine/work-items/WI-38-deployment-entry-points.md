# WI-38 Engine 的部署入口：遷移、結束代碼與健康檢查

本文回答：打包後的 Engine 如何在沒有 Gradle 的部署環境中執行遷移、如何以平台友善的結束代碼結束，以及容器內如何做健康檢查。狀態：已核可（2026-10-05）。相依：WI-18、WI-29。決策見 [ADR-018](../adr/ADR-018-liveness-readiness-probes.md)「部署檔案與需評估的事項」。

## 背景

遷移目前是 Gradle 任務（`migrate`），部署環境（Docker、systemd）沒有 Gradle；JVM 因終止訊號結束的代碼為 143，systemd 視為失敗；JDK 基底映像不一定附帶 HTTP 用戶端。

## 行為與驗收條件

- **遷移入口**：可由打包後的產物（`engine.jar`）以與 Gradle 任務相同的行為與環境變數（`POSTGRES_URL`、`POSTGRES_USER`、`POSTGRES_PASSWORD`）執行遷移；成功結束代碼為 0，失敗為非 0 並輸出原因（不含密碼）。Engine 啟動時未遷移即失敗的既有行為不變。呼叫方式寫入 04 的組態說明。以真實 PostgreSQL（Testcontainers）驗證：空資料庫遷移成功、再次執行為無操作、無法連線時失敗。
- **結束代碼**：Engine 收到終止訊號並完成優雅關閉後以 0 結束；啟動失敗（組態錯誤、未遷移、目錄不符）以非 0 結束。`packagedTest` 驗證（真實行程）。若評估認為 0 不可行，停下來回報，由架構決定（systemd 需列 143 為成功代碼）。
- **健康檢查工具（先評估後實作）**：評估兩個選項並回報：（a）映像加入輕量的 HTTP 用戶端；（b）由打包產物提供自我檢查的命令列入口（呼叫就緒或存活探測並以結束代碼表達，逾時小於 3 秒）。回報各自的映像大小、維護成本與對 Engine 命令列契約的影響，經架構決定後，才實作選定的選項；選項（a）不需要程式碼變更，只影響 WI-39。
- 既有的優雅關閉、啟動檢查與 API 行為不變；建置、全部既有測試（含 `packagedTest`）在 JDK 25 下通過，`ktfmtCheck` 通過；既有測試數量不減少。

## 架構約束

- 遷移與 Engine 使用同一份程式碼與設定（04「資料庫遷移」）；Engine 啟動時仍不自行遷移。
- 機密不得出現在 log、錯誤訊息或命令列參數；不新增外部相依。
- 測試使用真實 PostgreSQL（Testcontainers）與真實行程，不使用 Stub 或 Mock。
- 不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
