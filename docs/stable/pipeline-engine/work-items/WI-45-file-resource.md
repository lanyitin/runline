# WI-45 `file` 型別資源

本文回答：管理員如何把一個檔案定義為共享資源，pipeline 如何互斥地讀寫它。狀態：已核可（2026-10-06）。相依：WI-39、WI-43、WI-44。決策見 [ADR-019](../adr/ADR-019-typed-shared-resources.md) 第 4 點「`file`」。

## 背景

多個 run 需要寫同一個檔案時，以容量 1 的 `file` 資源互斥，由 Engine 保證路徑可用且限定在資源根目錄之下，避免繞過 [ADR-009](../adr/ADR-009-file-scopes.md) 的範圍。檔案所在儲存的持久與備份由部署環境負責。

## 行為與驗收條件

**組態與根目錄**
- Engine 組態提供資源根目錄（環境變數，命名依 `RUNLINE_` 慣例，寫入 04）。根目錄與 pipeline 共享目錄、run 私有目錄的位置不得相同或互為上下層，否則啟動失敗並列出鍵名；金鑰庫檔案不得位於資源根目錄之下（補上 WI-41 的對應檢查）。
- 根目錄不存在或不可讀寫時 Engine 仍可啟動；資源的檢查與初始化失敗，註明資源不可用。

**資源設定**
- `file` 資源設定為「相對於資源根目錄的路徑」與容量，不接受機密別名。絕對路徑、跳出根目錄的相對路徑、符號連結解析後跳出根目錄的路徑都被拒絕（422 `invalid_resource`，`problem` 為路徑不在資源根目錄內）。
- 建立、修改與檢查時驗證路徑可用：父目錄存在或可建立、可讀寫。

**存取端操作**
- 提供對該一個檔案的讀取、寫入（覆寫）與附加，以位元組與字串兩種形式（只用 JDK 內建型別）；不暴露路徑，不能列出或存取同目錄的其他檔案。單次讀取大小有上限（Engine 組態），超過回傳錯誤類別。
- 每次操作時重新驗證路徑未被替換為指向根目錄外（符號連結被改動後的操作被拒絕）。
- 錯誤只含類別，不含絕對路徑。

**互斥與容量**
- 容量 1：兩個不同 class loader 的 run 同時宣告同一個 `file` 資源時，同時只有一個持有，另一個等待並依先進先出取得（沿用 ADR-007）；持有者終止後立即換手。容量 N：同時最多 N 個 run 持有；Engine 不提供檔案內容層級的協調（驗證 N=2 時兩個 run 可同時持有，並在文件註明）。
- 初始化階段取得容量後再確認路徑可用；不可用則 run 失敗並註明資源不可用，不進入 pipeline 本體，已取得的容量被釋放。
- 強制釋放使存取端失效（沿用 WI-43）。刪除資源不刪除實際檔案。

**檢查、可觀測與靜態分析**
- 檢查（WI-44）驗證路徑可用，失敗類別至少區分根目錄不可用、父目錄不可建立、不可讀寫。
- Metric：`file` 的操作數與路徑檢查失敗數；trace 與 log 規則沿用 WI-43，不記錄路徑與內容。
- 使用 `file` 存取端的 pipeline 仍為 safe（真實編譯的測試 jar）。

**開發入口**
- 本機實作以本機組態的根目錄提供同契約；與 Engine 以同一組行為測試驗證（路徑限制、操作、錯誤類別）。

**部署**
- 04 與兩份平台指南、`deploy/` 的檔案說明並提供資源根目錄的掛載（Docker 的持久磁碟區、systemd 的狀態目錄），強調備份與容量由部署環境負責；以真實 Docker 驗證掛載的根目錄可寫、Engine 啟動後以 `file` 資源寫入的檔案在容器重建後仍在。
- 08-api 同步更新（`type=file` 的設定欄位、`invalid_resource` 的新增 `problem`）；`ApiDocumentationTest` 通過。

## 架構約束

- 不改變 ADR-009 的共享目錄與私有目錄行為；`file` 資源是它之外的獨立範圍。
- 路徑限制的驗證只用真實檔案系統與真實符號連結，不使用 Stub 或 Mock；需要替代品時使用自製的簡易真實實作（Fake）；嚴格 TDD；不新增 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
