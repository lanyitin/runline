# WI-1437 翻譯階段的生成量上限

本文回答：翻譯呼叫如何避免與潤飾、摘要相同的失控生成。狀態：已核可（2026-10-13）。補充 [WI-1434](WI-1434-polish-generation-limit.md)。相依：WI-1434。儲存庫：T（runline-transcribe）。

## 背景

翻譯與潤飾同為以 VAD-A 組為單位、SRT 進 SRT 出，輸出與輸入同量級，也是 Gemma 的對話呼叫。arr 的實驗中摘要與潤飾各出現過約 3.2 萬 token 的失控生成；翻譯目前只靠單次呼叫的牆鐘上限（`modelCallTimeoutSeconds`，預設 180 秒）擋住，最壞每次呼叫 180 秒。WI-1434 的評估指出翻譯風險最高，輸出為繁體中文，token 與字元的比例與來源語言不同。

## 行為與驗收條件

1. 翻譯請求帶生成量上限，與潤飾同機制：超過時走既有 `TRUNCATED` 處理（重試、降級、計數）。
2. 上限依該組輸入規模決定，並考慮輸出為繁體中文時 token 與字元的比例；餘裕值為管理員可調的參數（命名與預設值由實作者提案、架構師核可），寫入 README 與 runbook（單一寫處）。
3. 重試與備援沿用同一上限。
4. 核對階段不在本項；其單次輸入小，是否加固定上限由 arr 下一次 run 的核對 `completion_tokens` 最大值決定，另案。
5. 既有行為不變：條目時間不變式、降級規則、其他階段的輸出。

## 架構約束

- 不修改 Engine 或共享資源定義。
- 規則與預設值是推導值，需在 arr 上驗證：正常翻譯的 `completion_tokens` 與輸入 SRT 字元數的比例、大組不被誤截斷、被截斷時的耗時。
