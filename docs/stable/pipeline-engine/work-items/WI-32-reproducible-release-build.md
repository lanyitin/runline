# WI-32 位元組級可重現的發佈建置

本文回答：如何讓同一個 commit 的發佈建置在固定平台上產出逐位元組相同的 jar。狀態：已核可（2026-10-05）。相依：WI-28、WI-31。決策見 [ADR-016](../adr/ADR-016-engine-build-info-endpoint.md)。

## 背景

發佈產物需可由 commit 稽核：同一 commit、乾淨工作樹、固定建置平台，產物的 SHA-256 相同。驗證只在發佈建置執行，不納入日常 `check`；沒有 CI，驗證在本機。

## 行為與驗收條件

- 發佈建置（WI-28 的發佈旗標）下，`engine.jar` 與 `engineDistribution` 的各 jar 的封裝是可重現的：項目順序固定、項目時間戳記固定（取自 commit 時間或固定常數）、檔案權限固定、不含建置者資訊；shadow 合併的資源（服務宣告、manifest）順序與內容固定。
- 前端輸出是確定性的：精確鎖定相依、Node 與建置工具版本固定、輸出檔名雜湊只由內容決定、不寫入建置時間或絕對路徑、輸出順序固定；前端產物進入 jar 時不經改變內容的步驟。
- 發佈建置的專案版本不含建置時間或序號；建置資訊只含 commit 衍生的值（沿用 WI-28）。
- 固定平台：本項定義並文件化「固定建置平台」（例如固定的容器映像加固定的 Node 與 JDK 版本）與如何在本機使用它；平台的定義方式回報，由架構確認後定案。
- 提供單一 Gradle 入口執行可重現驗證：在固定平台上從乾淨狀態（清除建置輸出與前端快取）連續兩次發佈建置並比對各 jar 的 SHA-256，不同則失敗並指出哪個檔案不同。此驗證只在發佈建置執行，不屬於 `check`。
- 髒工作樹或取不到 commit 時，發佈建置失敗（沿用 WI-28）。
- 跨平台的位元組一致為盡力而為：回報在目前開發機（若與固定平台不同）上比對的結果，不列為驗收。
- README 說明如何執行發佈建置與可重現驗證。
- 既有建置、測試與 `ktfmtCheck` 通過；日常 `check` 的執行時間不因本項明顯增加。

## 架構約束

- 不改變 Engine 的行為與 API；只調整建置。
- 不新增 CI；驗證以本機真實建置完成（回報指令與雜湊）。
- 不使用 Stub 或 Mock；比對對象是真實建置出的 jar。
