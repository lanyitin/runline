# 架構方案比較與推薦

本文回答：關鍵取捨有哪些選項、為什麼推薦現在的選擇。

## 1. 執行隔離

| 選項 | 優點 | 缺點 |
|---|---|---|
| A 每次 run 一個子行程 | 可限制記憶體與 CPU，可強制終止，崩潰不影響 Engine | 啟動慢、需行程間通訊；不符合使用者的架構要求 |
| B 同一 JVM、每次 run 獨立 root class loader | 啟動快、可回收、pipeline 看不到 Engine 內部類別 | 無資源限制、無法強制終止、全域狀態共享 |
| C 同一 JVM、共用應用程式 class loader | 最簡單 | pipeline 能看到 Engine 內部，無隔離 |

**推薦 B。** 這是使用者既定的架構要求，且 A 與 B 之間的差異由 Runner 的邊界設計吸收（見 [ADR-001](adr/ADR-001-isolated-classloader.md)），日後若要改採 A，Runner 的入口契約不需改變。C 不採用。

## 2. Unsafe 判定

| 選項 | 優點 | 缺點 |
|---|---|---|
| 1 僅依 metadata 自我宣告 | 簡單 | 宣告可能與實際程式碼不符 |
| 2 metadata 完整度加靜態 import 白名單 | 上傳時即可判定、不執行程式碼；能抓出明顯越界 | 反射與動態載入可繞過；是風險提示而非安全邊界 |
| 3 執行期攔截（agent／instrumentation） | 涵蓋面較廣 | 複雜、有效能成本，且仍無法攔截任意 IO 的最寬鬆模式 |

**推薦 2。** 成本低、結果可在上傳時呈現，並誠實標示其限度（見 [ADR-002](adr/ADR-002-context-and-unsafe.md)）。

## 2.1 第三方函式庫的處理

| 選項 | 優點 | 缺點 |
|---|---|---|
| 只掃 pipeline 自身類別 | 誤判少、速度快 | 第三方庫帶來的風險完全看不到 |
| 掃整個 jar 的所有類別 | 涵蓋全面 | 未被使用的類別也會造成誤判 |
| 從入口出發逐層展開類別參照成樹，只看可達類別 | 只計入真正可能被用到的依賴；能顯示風險由哪條依賴路徑引入 | 分析成本較高；動態載入不可達 |

**推薦樹狀展開**（使用者已指定），報告附上路徑。分析對象是編譯後的類別參照，而非原始碼 import，才能涵蓋以完整名稱直接引用的類別。

## 2.2 共享資源協調

| 選項 | 優點 | 缺點 |
|---|---|---|
| A 初始化階段一次取得全部宣告的資源 | 無死結、可事先驗證 | 占用整個 run，吞吐較低 |
| B 宣告名稱，執行中以範圍方式取得 | 粒度細 | 可能死結，需逾時與順序規範 |

**採用 A**（使用者指定），詳見 [ADR-007](adr/ADR-007-shared-resources.md)。

## 3. Metadata 取得方式

| 選項 | 優點 | 缺點 |
|---|---|---|
| 手寫 | 完全可控 | 容易漏寫或過度寬鬆，導致大量 unsafe |
| 錄製後產生提案，再由人確認 | 貼近實際行為，降低門檻 | 只涵蓋錄製時走過的路徑 |

**推薦錄製產生提案**，採用前由開發人員檢視（見 [ADR-004](adr/ADR-004-recording.md)）。
