# WI-1016 SQLite 資料庫檔第一次開啟的競爭

本文回答：多個 run 同時第一次開啟一個尚不存在的 SQLite 資料庫檔時，為什麼會失敗，以及修正要達成什麼。狀態：已核可（2026-10-09）。

背景：[WI-1003](WI-1003-sqlite-database-kind.md) 的驗收條件 5 要求多個 run 同時使用同一資料庫時，寫入互相等待而不是失敗。WI-1004 的實作回報指出，數個 run 同時第一次開啟「尚不存在的」資料庫檔時，會出現 `CONNECTION_FAILED`（推測是建立檔案與切換日誌模式的競爭）；檔案已存在後同時使用正常。digest-rss 的 run 因語言模型資源容量為 1 而序列化，目前不受影響，但這是 Engine 側對一般 `sqlite` 資源的缺陷。工作儲存庫：runline。

## 驗收條件

1. 重現：用真實 SQLite 與多個同時開始的 run（或等價的並行存取端），對尚不存在的資料庫檔同時第一次開啟，能穩定重現失敗；測試先失敗並確認失敗原因是這個競爭，不是環境。
2. 修正後：同樣情境下所有 run 都成功，資料庫檔只被建立一次，日誌模式與外鍵設定在每條連線上都生效。
3. 失敗時的錯誤類別維持：檔案真的無法建立或開啟（父目錄不存在、無權限）仍回 `CONNECTION_FAILED`，不被修正吞掉。
4. 資料庫檔已存在的並行寫入行為不變（WI-1003 的既有並行測試維持通過）。
5. Engine 與 devkit 的 `sqlite` 共用行為套件新增此案例並兩邊通過。
6. 08-api 的 `sqlite` 段落說明第一次開啟的行為（若描述有變），`ApiDocumentationTest` 維持通過。

## 架構約束

- 只修正第一次開啟的競爭；不改變資源模型、API 欄位結構與 core 的存取端契約。
- 以真實 SQLite 與真實檔案系統驗證，不使用 Stub 或 Mock。
