# WI-27 版本庫的初始整理與初始 commit

本文回答：如何在建立第一個 commit 前整理版本庫，使其只包含應被版本控制的內容。狀態：已核可（2026-10-05）。相依：無（WI-00 至 WI-26 已全部驗收）。

## 背景

版本庫位於 `main` 分支，尚無任何 commit，全部檔案都是未追蹤。專案沒有忽略規則，直接加入全部檔案會把建置產物、IDE 與個人環境檔、測試殘留一併提交。

## 行為與驗收條件

### 忽略規則
- 專案根目錄有忽略規則，使下列內容不被版本控制：
  - 建置產物與快取：各模組與根目錄的建置輸出、Gradle 與 Kotlin 的快取與工作目錄、Kotlin/JS 的鎖定與暫存目錄。
  - IDE 與工具的個人設定：IntelliJ、VS Code 與 superdesign 的設定目錄。
  - 個人環境檔：根目錄的 mise 設定檔（含本機的容器 socket 路徑）。
  - 執行期與測試產生的檔案：開發入口預設的錄製與工作目錄（`.runline/`）、測試寫入的暫存檔。
  - 本機覆寫的 Claude Code 設定（若存在）；`.claude/` 中的 agent 定義與共用設定納入版本控制。
- `.devcontainer/`、`docs/`、各模組的原始碼與建置設定、Gradle wrapper、`gradle/` 目錄、`gradle.properties`、`README.md` 納入版本控制。
- 忽略規則本身以最小且可理解的條目表達，每個條目對應上述類別；不得忽略任何原始碼、文件或建置設定。

### 殘留檔案的清理
- 刪除下列殘留檔案：開發入口測試寫入的空檔 `devkit/out.txt`、`engine/src/test/kotlin/support/StuckServer.kt.bak`。
- 清理 `docs/draft/`：移除已晉升到 stable 的 draft 原檔（`02-current-state.md`、`ADR-004-recording.md`、`WI-04-recording.md`、`WI-27-repository-baseline.md`），保留目錄的方式由使用者另行決定；清理前確認每一份都已存在於 `docs/stable/` 對應位置。
- 找出並說明其他不應被提交的檔案（例如測試或工具在工作樹中產生的暫存檔、備份檔），列出清單；不確定是否應刪除者不刪除，列在回報中由使用者決定。
- 修正導致 `devkit/out.txt` 這類殘留的來源：若是測試在專案目錄內寫入檔案，改為寫入暫存目錄，使測試不再汙染工作樹；測試數量不減少、斷言不放寬。

### 驗證
- 整理前後，完整測試（含打包形態的測試）的數量與結果相同（0 失敗、0 略過）；`ktfmtCheck` 通過。
- 以 `git status` 確認：納入版本控制的檔案清單符合上述分類，沒有建置產物、IDE 設定、個人環境檔或殘留檔案；回報納入的檔案數量與分類統計。
- 確認沒有機密或個人路徑被提交：搜尋將被提交的檔案，不含本機使用者目錄的絕對路徑（文件中作為範例的除外，須逐項說明）、token 或密鑰。

### 初始 commit
- 在 `main` 建立單一初始 commit，包含上述納入版本控制的全部檔案。
- commit 訊息：第一行為簡短摘要；內文以條列說明專案是什麼（Kotlin 撰寫的 pipeline 執行引擎）、五個模組各自的責任、文件位於 `docs/stable/`；結尾依使用者指定附上共同作者行。
- 建立 commit 後 `git status` 乾淨；不推送到任何遠端，不建立分支或標籤，不修改使用者的 git 設定。

## 架構約束

- 只做版本庫整理與一次 commit：不修改任何模組的正式程式碼與行為；測試的修改僅限於讓測試不在專案目錄內寫入檔案。
- 只有使用者明確要求建立 commit 時才進行 commit（本工作項的核可即為該要求）；commit 之前須先完成上述清理與驗證。
- 不新增外部相依；不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
