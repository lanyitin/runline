# WI-1001 Engine 部署提供瀏覽器環境

本文回答：Engine 部署要提供什麼，瀏覽器與 SQLite 才能在其中運作。狀態：已核可（2026-10-08）。

目標：`deploy/` 的 Docker 與 systemd 兩種部署，都能讓 Engine 啟動有畫面的 Chrome，並信任 homelab 根憑證，同時滿足 SQLite 驅動的原生程式庫在部署環境運作的要求。工作儲存庫：runline。

## 驗收條件

1. Docker 部署的 Engine 環境含真實 Chrome 與虛擬顯示，顯示位置由環境變數提供；systemd 部署文件說明主機需要的前置條件與顯示來源。
2. 根憑證信任由部署組態提供（不寫死在 pipeline），並有驗證步驟：以真實的私有 CA 服務連線成功、換成未信任的則失敗。
3. 就緒探測（ADR-018）行為不變；Chrome 不可用不影響 Engine 就緒。
4. 發佈建置的可重現性（WI-32）不被破壞，或明確說明 Chrome 不在可重現範圍內。
5. 04-deployment 與維運文件更新，含遺留 Chrome 行程的處理建議。
6. 以 WI-1000 的量測方法在部署出的環境再驗證一次指紋，結果附上。
7. GPU：Docker 部署文件與範例組態說明如何把 `/dev/dri` 交給 Engine 容器（裝置掛載，以及以 root 或加入裝置所屬群組兩種方式），systemd 部署說明主機端的對應；沒有 GPU 時仍可啟動並明確警告渲染器為軟體渲染。
8. 可由組態要求硬體渲染：啟用時，若渲染器為軟體渲染，digest-rss 的 run 在開始時就以明確原因失敗（不開始擷取）；預設不啟用（WI-1000 的條件通過情形下軟體渲染可接受）。此檢查由部署提供的資訊與 pipeline 的啟動檢查共同完成，具體分工由實作決定並寫入部署文件。
9. 容器必須有 init 行程回收殭屍行程：Java 為 PID 1 時不會回收被取消而遺留的 Chrome 輔助行程，這些行程成為殭屍而使「取消後行程全數結束」的判斷失敗（WI-1000 在 Linux 容器的量測，缺 init 時 13 個測試有 3 個失敗）。Docker 部署的範例組態啟用 init，並以取消測試在部署出的容器內驗證；systemd 部署由 systemd 回收，文件說明即可。
10. 虛擬顯示的硬體 GL：WI-1000 的來源文件指出虛擬顯示本身可能沒有硬體 GL 路徑，即使掛載了 GPU 仍回報軟體渲染。部署驗證時記錄在目標主機上實際的渲染器；若硬體不可用，文件列出可選做法（例如提供有 DRI 的顯示伺服器）及取捨，並依 WI-1000 的判定規則處理，不在本項自行選擇。
11. SQLite 原生程式庫在目標架構運作：部署出的 Engine（Docker 映像為 linux/amd64，另含 glibc 與 musl 的取捨說明）能開啟並寫入一個 WAL 模式的 SQLite 資源，並連續多次 run 成功；結果附上。WI-1003 只在 macOS aarch64 與 Linux aarch64 實測過。
12. 原生程式庫的載入條件：JDK 載入原生程式庫時會警告受限方法將在未來版本被封鎖。部署文件與範例組態說明對應的啟動設定，並評估是否在 `engine.jar` 的 manifest 宣告原生存取；採用與否寫入文件，不改變 Engine 對外 API。
13. 暫存目錄：原生程式庫解壓到 JVM 的暫存目錄。Docker 與 systemd 的範例組態確保該目錄可寫且可執行（不是 `noexec`），否則說明如何設定專用目錄；以 `noexec` 暫存目錄模擬失敗並驗證錯誤訊息足以判斷原因。

## 架構約束

- 12-Factor：組態經環境變數；不在映像中放機密。
- 不修改 Engine 的對外 API。
- 本項的實測驗收須等 WI-1000 判定（WI-1000 已判定為條件通過，殘餘風險由 WI-1011 驗證）。
