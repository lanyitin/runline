# WI-20 run、log 與觸發紀錄的保留期限清理

本文回答：run 紀錄、log 與觸發紀錄如何依保留期限清理，避免資料庫無限成長，並讓 webhook 的去重視窗明確。狀態：已核可（2026-10-04）。相依：WI-08、WI-07。

## 背景

[06](../06-data-model.md)規定 run 與 log 依保留期限清理，期限由組態決定。[WI-08](WI-08-run-orchestration.md) 建立了 run 與 log 的儲存，[WI-07](WI-07-triggers.md) 建立了觸發紀錄，三者都沒有清理，在資料庫中持續成長：每分鐘一次的 cron 一年約增加五十萬筆觸發紀錄。

webhook 的去重由觸發紀錄的唯一性保證，因此其保留期限就是去重視窗（[ADR-005](../adr/ADR-005-trigger-binding.md)）。

## 行為與驗收條件

### run 與 log
- run 與其 log 依保留期限清理，期限由組態決定；超過期限且已進入終態的 run 與其所有 log 被一併移除。
- 未進入終態的 run（排隊、等待資源、初始化、執行中、逾時未結束）不被清理，不論其建立時間多久。
- 保留期限以 run 的結束時間起算；組態可分別設定 run 紀錄與 log 的保留期限，log 的期限不得長於 run 紀錄。未設定時使用合理預設。

### 觸發紀錄與去重視窗
- 觸發紀錄依保留期限清理。webhook 的觸發紀錄保留期限等於去重視窗，預設 7 天；cron 的觸發紀錄預設保留 30 天；兩者皆由組態決定。
- 去重視窗內，重複的 delivery 識別碼只建立一個 run；視窗之後，同一識別碼可再次被接受。
- 保留期限以觸發時間起算。處於「待處理」的觸發紀錄不被清理。
- 清理觸發紀錄時，其所建立的 run 不受影響；run 被清理時，觸發紀錄保留並清除其 run 參照。
- 去重視窗不得短於一個預設以外的下限（由實作依單次重送的合理時間決定並說明）；組態低於下限時啟動失敗並指出鍵名。

### 共同行為
- 清理以固定間隔在背景進行，間隔由組態決定；Engine 啟動時也執行一次。單次清理的處理量有上限，使清理不長時間占用資料庫，大量過期資料分多次清完。
- 清理不影響進行中的請求：正在被查詢或串流的 run 若在清理期間過期，該次查詢或串流仍完成，之後該 run 回應「不存在」。
- 清理不刪除 pipeline 定義或 artifact；被 run 或 trigger 引用的 artifact 仍受「拒絕刪除」保護，且 run 被清理後，該 run 帶來的保護解除。
- 清理有 log 與 metric（清理的 run 數、log 筆數、觸發紀錄筆數、耗時、失敗）；失敗不使 Engine 停止服務，下一次排程重試。
- 單實例：不處理多實例同時清理，但清理的動作對重複執行是安全的（冪等）。
- 保留期限為組態值，與 pipeline 私有目錄的保留期限（[WI-11](WI-11-workspace-directories.md)）各自獨立。
- 建置、全部既有測試（含打包形態的測試）在 JDK 25 下通過，`ktfmtCheck` 通過；既有測試數量不減少。

## 架構約束

- 只修改 engine 模組；core、runner、analyzer、devkit 不受影響。
- 清理條件與動作使用真實 PostgreSQL（Testcontainers）驗證，時間以可控制的時鐘提供，不以睡眠等待；需有測試驗證去重視窗內外的行為與並行重送。
- 保留期限與間隔由環境變數提供，符合 12-Factor；缺漏或格式錯誤時啟動失敗並指出鍵名。
- 若需要新的資料庫遷移，沿用既有的獨立一次性遷移機制，Engine 啟動只檢查版本。
- 不新增外部相依；不新增 git hook 或 CI；完成程式碼變更時依專案規則先以 ktfmt 格式化。
